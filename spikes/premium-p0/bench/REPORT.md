Caveats the maintainer should decide before P2: (1) ZDR is a retention promise, not a jurisdiction: several cheap endpoints are operated by providers in other regions (the list shows the operator; Mistral offers `/eu`). The consent copy and privacy policy must match the provider actually pinned. (2) `flex` and `priority` are service tiers of one endpoint with different prices; pin `max_price` to the tier you intend. ## 3. How to run

```bash
cd spikes/premium-p0/bench
npm install
npm run dry-run                      # offline, mock transport, ~5 s: models bench + image bench, writes results/*-dryrun.{json,md}
npx tsx scripts/fetch-nutrition5k.ts --n 60   # photos + gold (see fetch-dataset.md); dry-run uses data/manifest.json when present
npx tsx scripts/estimate-cost.ts [--models a,b --reps 3 --photos 60 --settings 16]
npm run shortlist                    # refresh the ZDR shortlist and fixtures/models.snapshot.json (GET only)
```

Live runs (spend money; you do this):

```bash
export OPENROUTER_API_KEY=...        # the throwaway key; read from the environment only, never written or logged
npx tsx scripts/bench-models.ts --live --max-usd 0.5 --reps 3 [--stream] [--models ...]
npx tsx scripts/bench-images.ts --live --max-usd 2   --models openai/gpt-6-luna,qwen/qwen3-vl-30b-a3b-instruct --photos 40
```

- `--live` refuses to start without `--max-usd` and without the key, and cannot be combined with `--dry-run`. Before each call the script adds a worst-case estimate (prompt tokens at the prompt price plus `max_tokens` at the completion price) to the spend so far (sum of `usage.cost`) and stops, writing a partial report marked "STOPPED early", if that would pass the cap. Calls run sequentially, so overshoot is bounded by one call.
- Requests send `provider: { zdr: true, data_collection: "deny", require_parameters: true, allow_fallbacks: false, max_price: {prompt, completion} }`, strict `json_schema`, and `reasoning.effort: "low"` where the model supports reasoning. No key means no network traffic except the public GETs.
- `bench-models.ts`: fixtures are the app's real schemas and prompts (`fixtures/schemas.ts` names the source function of each): meal photo, label photo, two `trackMeal` texts, the workout plan, three coach chats (pt/en/es) and two synthetic tool round trips (a call, then a tool result and a final text). Metrics per model and request type: strict-schema validity (Ajv against the strict schema; truncation by `length` counts as invalid), empty/refusal rate, HTTP error rate, latency p50/p95, TTFT with `--stream`, prompt/completion/reasoning tokens and `usage.cost`. The plan's pass bar: >= 99% validity, p95 < 15 s, macro accuracy within 5 points of the reference (accuracy is measured by `bench-images.ts`, since the text fixtures have no gold). **With 3 reps per request type, 99% is not measurable; use `--reps 10` for the models that survive.**
- `bench-images.ts`: for each photo it sends the original and every long edge (512/768/1024/1280/1568) x JPEG quality (60/75/85), `fit: inside`, never enlarged. Per setting and model it reports kcal MAPE and macro MAPE against gold, kcal difference vs the full-resolution run, mean bytes, image tokens (prompt tokens minus a text-only baseline call per model; max and p95), latency and cost. Recommendation: the smallest-bytes setting whose kcal **and** macro error are both within 2 points of the full-resolution run, and `IMAGE_TOKENS_MAX` = max image tokens observed over all models and settings x 1.25. Label legibility is not scored automatically: the `label` photos are compared by their kcal and macro error, and the maintainer should also eyeball one label per setting.
- The mock numbers (random-ish errors, invented tile token counts) only prove the pipeline. Do not quote them.

## 4. Estimated live cost

`scripts/estimate-cost.ts` uses the snapshot prices and pessimistic tokens: meal photo 2.6k in / 1.05k out (reasoning included), workout plan 1.4k / 2.5k, the other calls 0.5-2.3k in / 0.3-0.9k out. One rep of `bench-models` is 12 calls plus the second leg of the two tool tests.

| Run                                                                                                                             | Calls        | Estimated cost                                         |
| ------------------------------------------------------------------------------------------------------------------------------- | ------------ | ------------------------------------------------------ |
| `bench-models`, 6 default models, 3 reps                                                                                        | about 6 x 36 | **$0.09** (about $0.02 per model); 10 reps about $0.30 |
| `bench-images`, 6 default models, 60 photos x 16 settings                                                                       | 5766         | **$3.88**                                              |
| `bench-images`, 3 models (luna, mistral-small-2603, qwen3-vl), 40 photos x 16 settings                                          | 1923         | **$1.81**                                              |
| `bench-images`, 2 models (luna, qwen3-vl), 40 photos x 10 settings (`--edges 512,768,1024 --qualities 60,75,85` plus full = 10) | 802          | **$0.76**                                              |

Sizing a `$5` key: buying credits costs the amount plus the 5.5% fee with an **$0.80 minimum**, so $5 of credits costs $5.80. Recommended order, about **$2.1 total**: (1) `bench-models` on all six with `--reps 3` (about $0.09) to drop models that fail validity; (2) `bench-images` on the 2-3 survivors with 40 photos (about $0.8-1.8); (3) `--reps 10 --stream` on the final two models (about $0.15). That leaves most of a $5 key unused. The estimate can be wrong in either direction by 2x if a model burns reasoning tokens; the `--max-usd` guard is what protects the key, and the key's own dashboard limit ($5, no auto top-up) is the second wall.

## 5. What exactly needs you

1. **OpenRouter account**, prepaid credits of about $5 (costs about $5.80 with the fee), **auto top-up off**, a dedicated API key with a $5 limit, and the privacy setting **"ZDR only"** (plan P0). This is the only thing that needs a card.
2. **About 20 of your own photos** (see `fetch-dataset.md`): packaged foods, labels, dim light, restaurant plates, mixed plates, at native phone resolution, with gold values. Nutrition5k is plated cafeteria meals at 640x480 and cannot decide the resolution question above 640 px, nor the label or dim-light questions.
3. A decision on **provider jurisdiction** among ZDR endpoints (section 2 caveats).
4. Running the G5 probes in section 1 (zero-balance code, no-ZDR-endpoint error, generation lookup delay, auto top-up default). Each is one or a few requests and costs cents.
