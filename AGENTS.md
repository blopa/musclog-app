## Repo Structure: Dual-Purpose (App + Website)

This repository serves two distinct purposes that share the same Expo Router project:

- **`app/app/`** — All mobile app screens (iOS & Android). These are the core product screens: nutrition, workout, profile, progress, settings, onboarding, etc.
- **`app/(website)/`** — The institutional/marketing website (landing page, privacy policy, etc.). This is only rendered on the web platform. Route group `(website)` keeps it isolated from the app routes.

**Key conventions for the website:**

- Files ending in `.web.tsx` inside `app/(website)/` are the web-specific implementations (e.g. `home.web.tsx`). Their non-web counterparts (e.g. `home.tsx`) exist as native stubs or redirects.
- Website components live in `components/website/` (e.g. `StoreButtons`, `WebsiteBackgrounds`, `WebsiteWrapper`).
- Static SEO is emitted by each route’s `generateMetadata()` export using `components/website/websiteMetadata.ts`; SDK 58 does not prerender `expo-router/head` tags. `WebsiteSeo.tsx` updates the same metadata after client language changes. `WebsiteShell` provides shared public-page chrome, including the production `/` landing page (which renders directly instead of exporting an empty redirect). `components/website/websiteRoutes.json` is the **single** route registry for fixed website routes: each entry holds the route's canonical `path`, an optional `robots` directive (omit it for indexable routes), and an optional `llms` blurb. Markdown blog post routes, category listings, and their derived pagination routes are the exceptions; `scripts/generate-web-seo-files.js` derives all of those URLs from the Markdown posts and adds them to the sitemap, but it derives them through `components/website/blogRoutes.js` rather than building the paths itself — see the blog rule below. `websiteMetadata.ts` reads the registry for canonical URLs and robots meta; the generator reads it to regenerate `public/robots.txt`, `public/sitemap.xml` and `public/llms.txt` on every `npm run web` / `npm run build-android-web`. Adding a fixed public route is therefore **two** edits: the `websiteRoutes.json` entry, plus its `website.seo.routes.<key>` title/description in each `lang/locales` `website.json`. Do not reintroduce a second copy of the fixed route list in the generator script or in `public/llms.txt` — those three `public/` files are generated, never hand-edited. Sitewide `Organization`/`WebSite` JSON-LD is rendered directly in prerendered markup by `WebsiteShell` via `components/website/WebsiteStructuredData.tsx`; add a page-specific schema there too (e.g. `FaqPageJsonLd`, `SoftwareApplicationJsonLd`, `BlogPostingJsonLd`) when a route's content maps cleanly to a schema.org type — never fabricate fields like `aggregateRating` that aren't backed by real data.
- Blog images live under `public/images/blog/` and are referenced with absolute `/images/blog/...` URLs from post Markdown. Run `npm run compress-blog-images` after adding PNG/JPEG assets: `scripts/compress-blog-images.js` caps them at 1792px wide, writes q85 WebP only when it is smaller, updates every Markdown reference, and removes the replaced source. Existing WebP files and tiny PNGs that would grow are left unchanged.
- Blog source files live recursively under `app/(website)/posts`; every file/directory segment must be URL-safe (letters, numbers, hyphens, or underscores), and frontmatter requires `title`, `date` (`YYYY-MM-DD`), `category`, and `tags`; `description` is optional. `category` is a lowercase, kebab-case translation key whose label must exist at `website.blog.categories.<key>` in every `lang/locales/*/website.json`; the listing, article page, article metadata, and category page localize it at render time. Category labels link to `/blog/category/<key>`, whose later pages live at `/blog/category/<key>/page/<number>`. `blog/index.web.tsx`, `blog/page/[page].web.tsx`, `blog/[...slug].web.tsx`, and the routes under `blog/category/[category]/` use Expo static data loaders plus `utils/blogPosts.server.ts`; the dynamic routes export `generateStaticParams`, and their unsuffixed `.tsx` siblings are the usual native redirects. The first all-posts listing stays at `/blog`; later pages are statically exported at `/blog/page/<number>`.

  **`components/website/blogRoutes.js` owns every blog URL shape and the pagination arithmetic behind them**, alongside the `SAFE_SLUG_SEGMENT` / `SAFE_CATEGORY_KEY` patterns and the `blogConfig.json` page size. It is plain CommonJS for the same reason `websiteRoutes.json` is plain data: `scripts/generate-web-seo-files.js` runs outside the app bundle and must read the identical rules the router uses. Four consumers depend on that — `utils/blogPosts.server.ts`, the sitemap generator, `BlogPostListing`, and `BlogListingPage` — and they previously held four copies of the "page one is the bare path, later pages get a `/page/N` suffix" rule plus two copies of the page-count arithmetic, which let the sitemap advertise pages the router does not build. `utils/__tests__/blogRoutes.test.ts` pins that the generator and the loaders still agree, in both directions. Never rebuild a `/blog/...` path by hand.

  **One component renders every listing page: `components/website/BlogListingPage.tsx`** (SEO + `CollectionPage` JSON-LD + `BlogPostListing`), taking an optional `category` exactly as `BlogPostListing` does. The three listing routes previously composed three different sets of metadata around the same list. The one asymmetry is deliberate: `/blog` is a fixed route, so `WebsiteSeo` reads its title and description from `websiteRoutes.json`, while a category has no registry entry and supplies them from its translated label. Header and metadata copy both come from `useBlogListingCopy`, so a heading and its `<meta description>` cannot describe different things.

  The single listing-size setting is `components/website/blogConfig.json`, re-exported as `BLOG_POSTS_PER_PAGE`; change it there rather than duplicating a number. Post Markdown is rendered server-side with `markdown-it` (`html: false`) and `highlight.js`, so the browser receives safe rendered HTML rather than the parser/highlighter or Markdown source. Three constraints:
  - **The index is `blog/index.web.tsx`, not `blog.web.tsx`.** Expo writes each loader payload as an extensionless file named after the route's context key, so `blog` (file) and `blog/` (directory of per-post loaders) would collide and fail the export with `EISDIR`. Any `foo.tsx` + `foo/[x].tsx` pair that both export loaders has this problem; put the index inside the directory.
  - **The share row at the end of a post (`components/website/BlogPostShare.tsx`) must pass `resetButtonStyle={false}` to every `react-share` button.** react-share's reset writes `background`, `border`, `padding` and `border-radius` as **inline** styles, which beat every Tailwind class on the same element — leave it on and the buttons render as bare glyphs with no chrome, silently and with no type error. The icons are deliberately monochrome (`iconFillColor="currentColor"` over a transparent background) and take their network's brand color only on hover, through the `--share-color` custom property each button sets inline for `.blog-share-button` in `global.css`; a per-network hover color cannot be a Tailwind class or an inline style. The shared URL comes from `absoluteUrl` in `websiteMetadata.ts` — do not add a fourth copy of the site origin. `components/website/__tests__/BlogPostShare.test.ts` pins all of it.
  - **Dev-only loader path needs `patches/expo-router+58.0.23.patch`.** `useLoaderData` passes the filesystem context key for grouped website routes, so in development the client requested a loader path containing route groups that the public manifest does not have; the patch strips `(group)` segments from the loader path in development only (production keeps them because static export writes loader files under them). Expo Router 57.0.26 fixed the other two defects the earlier 57.0.18 patch carried — it now reads a catch-all file's platform extension correctly (`[...slug].web.tsx` is the web variant of `[...slug]`) and strips it in `getContextKey` — so those hunks are gone. `utils/__tests__/expoRouterLoaderPatch.test.ts` still pins all three behaviors. Keep the patch until the equivalent fix ships upstream, and revalidate index/post navigation in both environments when upgrading Expo Router.

  Expo Router 57 static manifests retain the unresolved catch-all template alongside generated paths, so `loadBlogPostForRoute` must keep handling the literal `[...slug]` build-time loader call until that behavior changes upstream.

  **`utils/blogPosts.server.ts` is stubbed out of the native bundle, and the `await import()` in the route files is not what does it.** expo-router's native `require.context` regex (`_ctx.android.js`) has an optional `(?:\.ios|\.web)?` group, so it matches `blog/index.web.tsx` and `blog/[...slug].web.tsx` on Android and iOS too — platform selection happens later, when `getRoutes` builds the tree, by which point Metro has already added the files to the graph. Metro also resolves `import()` statically (React Native has no code splitting), so the deliberately-dynamic imports in those loaders still pull the module in, and its `node:fs/promises` import fails the native bundle with `Unable to resolve module node:fs/promises`. `metro.config.js` therefore resolves `blogPosts.server` to `blog-posts-server-stub.js` whenever `platform !== 'web'`, the same way `sharp` is stubbed; this also keeps `gray-matter`, `markdown-it` and `highlight.js` out of the app bundle. The stub throws rather than returning empty posts, and `utils/__tests__/blogPostsServerNativeStub.test.ts` pins both the resolver rule and the stub's export surface. **Do not "fix" this with a `blogPosts.server.native.ts` platform sibling** — the Jest `node` project uses `@react-native/jest-preset`, whose `haste.platforms` includes `native`, so that file would hijack `utils/__tests__/blogPosts.server.test.ts` and test the stub instead of the real parser. Any new web-only module that imports Node built-ins needs the same treatment.

- The website uses standard HTML elements (`<div>`, `<section>`, `<a>`) and Tailwind/NativeWind utility classes — **not** React Native primitives.
- **Link to another website page with a plain `<a href>`, not expo-router's `Link`.** On web `Link` renders a react-native-web `Text`, which starts a fresh style context: it inherits neither `color` nor `font-size`/`font-weight` from its HTML ancestors, and `group-hover:`/`hover:` classes on it lose to the inline `style` prop that any base color must therefore be set with. The blog list's post titles shipped near-black on a dark card for exactly this reason — an `<h2 className="text-white text-3xl">` wrapping a `Link` styles nothing. The nav in `WebsiteWrapper.web.tsx` still uses `Link` with an explicit inline `color`; that pattern works only because those links need no hover-color change. Reach for `<a>` first, and if you do use `Link`, put every typography and color declaration on the `Link` itself.
- When working on website files, treat them as a standard React web app, not a React Native app.
- Website layout is in `app/(website)/_layout.web.tsx`; it wraps pages with the nav/footer chrome.
- **Web icon fonts register during root layout rendering**, through `registerWebIconFonts` in `app/_layout.tsx`. Expo SDK 57 imports routes outside its server font context, so a module-scope call crashes static export. Keep the call inside the render for per-page font collection; an effect would omit it from the server HTML. The native helper is a no-op.
- **Below `lg`, the primary navigation lives in the header's burger menu (`MobileMenu` in `WebsiteWrapper.web.tsx`), not in the footer.** The footer previously carried a `md:hidden` pill cluster duplicating the nav; that copy is gone, and adding a primary destination is now one edit to `MobileMenu`'s `menuLinks`. The footer keeps only secondary and legal links (privacy, terms, contact, license, cookie settings), which it shows at every width. Three constraints on the panel: it is **portalled to `<body>`** because the header's `backdrop-blur-md` makes it a containing block for `fixed` descendants, so a full-viewport backdrop rendered inside the header would be clipped to the header; it therefore carries its **own `lg:hidden`** (the header cluster's does not reach it) plus a `matchMedia('(min-width: 1024px)')` listener, without which growing past the breakpoint would leave the body scroll locked by an invisible panel; and it closes on the backdrop and Escape rather than a document-level `pointerdown` listener, so the store/QR popovers it contains — themselves portalled to `<body>`, and thus "outside" the panel — do not tear it down when clicked. Focus moves into the panel on open and back to the trigger on close, since the portal puts it last in tab order.
- **Website preferences**: `WebsitePreferences.tsx` owns the single compact header control for language and theme on desktop and mobile. Keep the styled radio choices (language flags, theme swatches, and checkmarks) in Language/Theme tabs inside its portalled, viewport-constrained panel; theme changes update both the browser mirror and app settings. Do not add separate picker pills or duplicate theme options in the burger menu.
- **Popover vertical placement has one implementation: `computePopoverTop` in `components/website/popoverPlacement.ts`.** `DownloadModal` and `StoreButtons`' QR popover both anchor under a trigger and must flip above it when the space below cannot hold them; the QR popover lacked the flip and rendered off-screen once the burger menu placed it low in the panel. Height is measured after the first render, so the helper returns a downward position while `popoverHeight` is 0 and settles on the second pass — do not "fix" that by measuring during render. Horizontal placement stays per-component (the two want different anchoring).

**When making changes:**

- Changes to `app/app/` affect the mobile app only.
- Changes to `app/(website)/` affect the public website only.
- Shared logic (services, database, utils) lives outside both and is used by both platforms.

## Tech Stack

- **Framework**: React Native (Expo SDK 58) with Expo Router
- **Android release optimization**: `app.json` enables both `enableMinifyInReleaseBuilds` and `enableShrinkResourcesInReleaseBuilds` through `expo-build-properties`, so production Android builds run R8 and remove unused resources. Keep both flags together; resource shrinking requires minification. Because this repo commits its native projects, `android/gradle.properties` is the generated mirror used by builds that do not run Prebuild; keep it synchronized through Prebuild whenever the Expo config changes.
- **EAS upload archives**: The committed `android/` and `ios/` source projects are build inputs and must remain in EAS uploads. `.easignore` excludes only their generated build directories/caches, the shallow-clone `.git` directory, tests, local tooling, the web-only `public/` directory, website-only blog posts, and exercise images fetched at runtime. Keep the native-output patterns and the exact `.git` entry intact; `.git/` alone does not make EAS CLI remove the shallow clone it creates while assembling an archive. Validate changes with `eas build:inspect --platform android --stage archive`.
- **Node version**: EAS reads neither `.nvmrc` nor `engines`, so `eas.json`'s `base` profile pins an exact Node release and every build profile must `extend` it. Without it EAS builds on its default Node 22 / npm 10, which rejects the npm 11 lockfile in `npm ci` (see `FIXES.md`). Bump the Node major in `engines`, `.nvmrc`, `eas.json` and `.github/workflows/*` together; `utils/__tests__/easNodeVersion.test.ts` enforces it. Keep `cli.version` a major-only floor (`>= N.0.0`): the EAS builder reads `eas.json` with the `eas-cli` in its own image, which lags npm, so copying a just-released version there fails every build (see `FIXES.md`).
- **Styling**: NativeWind (Tailwind CSS). `react-native-css-interop` 0.2.6's `parseDeclaration` was missing a `return` in its `case "box-shadow"`: the switch fell through into `case "aspect-ratio"`, which reads `value.ratio[0]` off a box-shadow value and throws `TypeError: Cannot read properties of undefined (reading '0')` — with a stack trace pointing at `parseAspectRatio`, nowhere near the real culprit. Only a **fully parsed** literal `box-shadow` in `global.css` tripped it; Tailwind's own `shadow-*` utilities compile to `box-shadow: var(--tw-shadow), …`, and lightningcss leaves anything containing `var()` unparsed, so they took a different branch. The crash also only hit **native** — `expo export:embed` runs the CSS through css-to-rn, while the web build goes through PostCSS — so a literal box-shadow could look fine on web for weeks and then break the next Android build. **Fixed upstream in 0.2.7**, so `patches/react-native-css-interop+0.2.6.patch` is gone; `utils/__tests__/nativewindBoxShadowPatch.test.ts` still pins the behavior, so do not downgrade below 0.2.7.
- **Database**: WatermelonDB (SQLite for Native, LokiJS for Web)
- **Charts**: Victory Native (Skia) for Native, Victory (SVG) for Web
- **AI**: OpenAI & Google Gemini (Generative AI)
- **Localization**: i18next with `expo-localization`
- **Health Data**: Health Connect (Android) via `react-native-health-connect`. **Do not add `expo-health-connect` back**: it is the same author's _standalone_ config plugin from before `react-native-health-connect` shipped its own, and as of rnhc 4.x both packages register an autolinked Expo module under the **identical** `expo.modules.healthconnect` namespace, so `:app:mergeDexRelease` fails with `Type expo.modules.healthconnect.BuildConfig is defined multiple times` (release-only — the duplicate class never surfaces in a dev/debug bundle). `react-native-health-connect`'s own `app.plugin.js` (listed in `app.json` `plugins`) writes the exact same `ACTION_SHOW_PERMISSIONS_RATIONALE` intent-filter + `ViewPermissionUsageActivity` alias into the manifest, so nothing is lost by dropping the standalone plugin.
- **Error Tracking**: Sentry (`@sentry/react-native`)
- **Food Scanning**: OCR (tesseract.js / rn-mlkit-ocr) and barcode scanning (quagga2 / react-zxing)
- **Camera**: all native camera work goes through `react-native-vision-camera` — the smart camera (barcode / AI food scanning) via the `components/CameraView.tsx` wrapper, and video capture on the reps-recording test screen (`app/app/test/reps-recording.tsx`) using the `Camera` component directly. **Do not add `expo-camera` (or any second CameraX-based library) back**: vision-camera 4.7.3 links against CameraX-internal classes from its pinned CameraX version, and a second library pulling a newer CameraX (e.g. 1.6.0, which removed `Camera2CameraInfoImpl`) wins Gradle resolution and crashes the app at boot with `NoClassDefFoundError` (see git history: `plugins/withCameraXVersionPin.js` briefly worked around exactly this). Two `CameraView.tsx` props are load-bearing for shutter latency and must not be "optimized" away without re-verifying on a **release** build (`npm run build-android-apk-local` + `adb logcat`, filter `CameraView`/`CameraCaptureFlow` — the historical 25s-shutter incident never reproduced in dev builds): `androidPreviewViewType="texture-view"` (the snapshot shutter needs a reliable `getBitmap`; SurfaceView/PixelCopy has device-specific null/black failures that silently reroute into the slow takePhoto fallback) and `photoQualityBalance="speed"` (never "balanced" = CameraX ZSL, which stalls for tens of seconds on some devices and silently downgrades on others, masking the stall in dev). Every shutter press emits phase telemetry; slow or fallback shots surface as Sentry `camera-shutter-*`/`camera-warm-up-*` events.
- **VisionCamera is stubbed on web in `metro.config.js`** (`vision-camera-web-stub.js`): the package throws `VisionCamera currently does not work on web` at module evaluation, and expo-router's `require.context` can still reach native-only `.tsx` siblings of `.web.tsx` files (e.g. `app/app/test/reps-recording.tsx`). Web camera UI lives in `CameraView.web.tsx` and `.web` route stubs; do not import vision-camera from a web-reachable module expecting it to work.
- **Every capture is cropped; barcode scanning has no shutter at all**: both entry points of `useCameraCaptureFlow` (`hooks/useCameraCaptureFlow.ts`) — a shutter capture and a gallery pick — end in the same `cropAndProcess` step, so the user can trim the shot and `process` only ever receives a cropped image. There is deliberately **no** "skip the crop" option: barcode scanning reads the live preview and offers no manual capture, so the one case that would have wanted it cannot occur. Whether a shutter button exists is the owner's call, expressed by passing or omitting `SmartCameraShell`'s optional `onShutterPress` — `SmartCameraModal` passes `undefined` while `isBarcodeScanning`, `BarcodeCameraModal` never passes one (it only uses `pickFromGallery`). Do not reintroduce a `cropOnShutter`-style flag, and do not make the shell decide this from `cameraMode`. `patches/@bsky.app+expo-image-crop-tool+0.5.1.patch` also moves `openCropperAsync` to `Queues.MAIN` (it only does `startActivityForResult`, a Main-thread op anyway, so it never waits behind the shared background queue described below); keep that patch as cheap defense-in-depth even though the SecureStore fix removes the underlying contention.
- **First gallery pick after boot stalled ~25s — root cause was SecureStore head-of-line-blocking Expo's single-threaded module queue (critical)**: on the **first** gallery pick within ~25s of a cold boot, tapping "load from gallery" showed a ~25s spinner before the picker/crop UI appeared (observed Pixel 10 / Android 17); the second pick — and any pick after idling ~25s post-boot — was instant. A lazy per-call cold start cannot be cleared by merely _waiting_ 25s, which disproves the earlier "one-time native init inside `openCropperAsync`/the system picker" theory. **Confirmed mechanism**: every Expo `AsyncFunction`/`Coroutine` on the default queue runs on ONE shared background thread — `expo.modules.AsyncFunctionQueue`, a single `HandlerThread` (`AppContext.modulesQueue`; see expo-modules-core `AppContext.kt`). `expo-secure-store` 57.0.3's `getValueWithKeyAsync`/`setValueWithKeyAsync` are `Coroutine`s whose `getItemImpl`/`setItemImpl` do **no** `withContext`/`Dispatchers` switch, so their Android Keystore/SharedPreferences work (slow on a cold first access — Keystore init + RSA/AES keygen) runs **directly on that shared thread**, head-of-line-blocking every other default-queue function — including the crop tool's `openCropperAsync` and expo-image-picker's `launchImageLibraryAsync`. Boot reads SecureStore (encryption key + `SettingsService.migrateApiKeysToEncrypted`), so the cold Keystore stall lands exactly when the user first opens the gallery. Corroborated by [expo/expo#34531](https://github.com/expo/expo/issues/34531). **Fix**: `patches/expo-secure-store+58.0.2.patch` moves SecureStore's Android async ops onto a dedicated serial I/O queue (`Dispatchers.IO.limitedParallelism(1)`), off the shared thread. **SDK 57 ships SecureStore as a prebuilt AAR** (`local-maven-repo/…/expo.modules.securestore-57.0.3.aar`), so the patched `.kt` is ignored unless `package.json` keeps `expo.autolinking.android.buildFromSource: ["expo-secure-store"]` — both pieces are load-bearing; revalidate on every Expo/SecureStore upgrade. Two supporting boot-load reductions: `getEncryptionKey()` (`utils/encryption.ts`) coalesces concurrent reads per storage key (also fixes a latent fresh-install race that could generate/persist mismatched keys → undecryptable data), and `SettingsService.migrateApiKeysToEncrypted` is now a `runOnce` boot migration. Do not reintroduce eager duplicate SecureStore reads at startup. The stall only ever reproduces on a **release** build — verify with `npm run build-android-apk-local` + `adb logcat` (filter `CameraCaptureFlow` for the `gallery picker` phase timing).
- **Gallery pick uses the modern system Photo Picker, no permission prompt — one shared entry point app-wide**: `utils/galleryImagePicker.ts` exports `pickImageFromGallery` (calls `ImagePicker.launchImageLibraryAsync` with no `legacy` flag, opening Android `ACTION_PICK_IMAGES` / iOS `PHPicker` — both return only the user-picked item through a temporary content grant and need **no** media-library permission, so callers must not add a `requestMediaLibraryPermissionsAsync` check back in) and `pickAndCropImageFromGallery` (composes `pickImageFromGallery` with `openCropperAsync` from `utils/file.ts`, returning the cropped path or `null` if either step is cancelled). `legacy: true` (the old `ACTION_GET_CONTENT` document UI) was a failed workaround for the stall documented below (the picker component was never the cause) and must not be reintroduced. `pickImageFromGallery` has no platform-specific behavior — expo-image-picker works the same way on web (a hidden `<input type=file>`) — so unlike `openCropperAsync` it deliberately has **no** `.web.ts` counterpart; do not reintroduce one. **`pickImageFromGallery` takes no quality argument and picks at `quality: 1`**: every caller re-encodes through `openCropperAsync`, so compressing at the pick step too would stack a second lossy pass (a requested `0.8` actually landing at ~`0.64`). The crop step is the single place output quality is chosen — `pickAndCropImageFromGallery(compressImageQuality)` and `useCameraCaptureFlow`'s `quality` option both mean exactly that. This matters most on the smart-camera path, where the photo must stay legible for OCR and barcode decoding. Every gallery-pick entry point in the app shares these two functions — `CoachModal` (chat image attachments — previously used `expo-document-picker`'s file browser, which felt inconsistent with the rest of the app), `CreateMealModal`, `CreateCustomFoodModal`, and `CreateExerciseModal` call `pickAndCropImageFromGallery` directly; `hooks/useCameraCaptureFlow.ts` (`pickFromGallery`, smart camera modals) calls `pickImageFromGallery` and `openCropperAsync` separately because it needs distinct phase-timing logs and error messages for each step — so every "pick from gallery" flow in the app has the identical picker + crop UX. Do not call `ImagePicker.launchImageLibraryAsync` directly from a new call site; add it to `pickAndCropImageFromGallery`'s callers instead. `useCameraCaptureFlow`'s `pickFromGallery` still logs the `gallery picker` phase timing (`adb logcat`, release build) so a residual queue stall would still surface.
- **Export**: xlsx + html-to-image for data export features. `expo-print` renders the cycle appointment summary to a PDF (print dialog on web); it is native, so adding or upgrading it needs `npm run prebuild` (and `pod install` on iOS)
- **JSX transform**: SDK 58 uses Expo’s resolved Babel JSX transform; the old exact `@babel/plugin-transform-react-jsx` optional-dependency pin is removed. Keep NativeWind, Reanimated and WatermelonDB decorator transforms in the existing Babel configuration.

## Coding Guidelines

### Architecture

- **Blank lines after blocks/functions**: ESLint's autofixable `padding-line-between-statements` rule requires an empty line before the next statement after a block-like statement, an `if`, or a function declaration (including exported declarations and variable-assigned block-bodied arrow/function expressions). It does not insert padding inside `if`/`else` chains or before a closing brace. Run `npm run lint:eslint-fix` to apply it. The core rule is available in our pinned ESLint 9; migrate it to ESLint Stylistic before upgrading to ESLint 11.

- **No barrel files or re-export-only wrappers**: Import implementations directly from their owning files. Do not create `index.ts` aggregation modules, files whose only purpose is to re-export another module, or platform wrappers that merely alias a shared component. A barrel is allowed only when an external package boundary or framework API explicitly requires that exact entry point; document that requirement in the file. `database/services/index.ts` was one of these and is gone — import each service from its own file (`@/database/services/NutritionService`), and mock it the same way in tests, since a `jest.mock('@/database/services', ...)` now silently mocks nothing. `utils/uuid.ts` was another: generate ids with `randomUUID` from `expo-crypto` directly, never a hand-rolled `Math.random()` v4 (`MigrationService` carried a second private copy of that polyfill long after the first was removed).
- **Keep documentation in sync (required)**: When a change alters behavior, architecture, file layout, or an invariant, update the relevant root document in the same change: `AGENTS.md` for implementation rules, `CURRENT_FEATURES.md` / `FUTURE_FEATURES.md` for product status, `DESIGN.md` for UI standards, `FIXES.md` for incidents and workarounds, `RESEARCH.md` for durable rationale, and `README.md` for project-level usage. Treat a stale filename, function, flag, or approach as a bug. Do not create another Markdown plan or one-off report; merge durable information into one of these files. The one exception is `doc/redesign/`, which holds the active de-slop plan (`DESLOP_PLAN.md`) and its audit baseline (`design-baseline.json`): work a phase from there, mark its findings `fixed` in the baseline in the same change, and fold the resulting rules into `DESIGN.md`.
- **Feature list sync (required)**: Whenever a user-facing feature is added, removed, or significantly changed, update `CURRENT_FEATURES.md`. If the change also affects the curated overview, update `README.md`. Future work belongs in `FUTURE_FEATURES.md`.
- **Tests are required for every behavior change**: Every new feature, bug fix, or change to existing behavior must include appropriate automated test coverage. Add a new regression test or update the existing tests so they verify the intended behavior and would catch the bug or regression. Run the relevant test suite, along with type checking and any applicable lint or translation checks, and make sure it passes before considering the work complete. Never weaken, delete, or skip a valid test merely to make a change pass; update expectations only when the intended behavior has genuinely changed.
- **Layered Structure**: Schema (`database/schema.ts`) -> Models (`database/models/`) -> Repositories (`database/repositories/`) -> Services (`database/services/`).
- **Repositories**: Complex queries live in `database/repositories/` (e.g., `WorkoutLogRepository`, `MenstrualCycleRepository`). Prefer repositories over direct model queries for non-trivial reads.
- **App Services**: Non-database services (AI, notifications, Health Connect sync) live in top-level `services/`.
- **Data Persistence**: Use WatermelonDB for local storage. Ensure models are registered in `database/database-instance.ts`.
- **Calendar day keys**: Fields that represent a calendar day (`user_metrics.date`, diary pickers) store **local** midnight ms. Use `utils/calendarDate.ts` (`localDayStartMs`, `localDayHalfOpenRange`, etc.); do not use `Date.UTC` or `setUTCHours(0, …)` for those stored values.
- **`nutrition_logs.date` is a consumed datetime**, not a day key: it stores the local **datetime** (day + time-of-day) the food was consumed in ms, so the time-of-day is preserved. Calendar-day grouping/filtering still goes through `utcNormalizedDayKey` / `dayKeyRange` (with `dayRangeClauses` from `database/dayKeyQuery.ts` for the widened DB clauses and `range.filterRecords` to trim the overscan), which re-apply the stored `timezone` offset and strip to Y/M/D, so day-based reads are unaffected. When writing it, combine the picked day + time with `combineLocalDateAndTime` (or `instantForDateTimeInTimezone` to anchor to a record's stored timezone); use `withCurrentTimeOnDay` for non-interactive "log now for this day" paths. Never floor it with `localDayStartMs`. `created_at` is strictly the record-creation instant and `updated_at` the last-update instant — do not read consumed time from them.
- **Encryption**: Sensitive metrics (weight, body fat) and nutrition logs must be encrypted/decrypted using helpers in `database/encryptionHelpers.ts`.
- **Every decrypt is expensive — count them on any path that reads a range of logs.** Each value is its own `CryptoJS.AES.decrypt` with a passphrase, which runs an MD5 key derivation first (~90% of the cost), synchronously on the JS thread. On a multi-year diary, decryption, not the queries, is what made Home slow (see `FIXES.md`). So: decrypt only the fields a path reads (`NutritionLog.getNutrients()` never decrypts the food name and decrypts each macro once — do not reintroduce a `hasSnapshot()` + `getDecryptedSnapshot()` pair); share concurrent reads of the same window instead of computing it twice (`getLatestHistoricalNutritionWindow` does, in-flight only); and never add a boot task that decrypts every row on each launch — make such a repair `runOnce`, or select its rows on a plaintext column.
- **Food quality badges (Nutri-Score / Eco-Score / NOVA / labels)**: Never re-inline a provider's field names (`nutriscore_grade`, `ecoscore_grade`, `nova_group`, …). Each source normalizes into `FoodDisplayQuality` (`utils/foodDisplayQuality.ts`) exactly once, at its own mapper — `getOffDisplayQuality` (`utils/openFoodFactsMapper.ts`), `getMusclogDisplayQuality` (`utils/musclogProduct.ts`) — and UI reads them through `getExternalProductDisplayQuality(source, details)` in `utils/externalFoodProduct.ts`, passing a source already resolved by `inferBarcodeNutritionSource`/`resolveExternalFoodSource` rather than re-sniffing product shapes. `foodRecordDisplayQuality` reads the badges back off a stored food (or a mapped search result); `applyDisplayQualityToFoodRecord` writes them on the save path. USDA carries no quality data and resolves to `undefined`.
- **Unit system (metric / imperial)**: The database **always** stores metric values (kg, cm, g, kcal). Users choose metric or imperial in settings (`SettingsService.getUnits()`). Conversion helpers live in `utils/unitConversion.ts`:
  - **Saving user input → DB**: Convert display values to metric with `displayToKg`, `displayToCm`, `displayToGrams`, or the generic `displayValueToMetric(value, metricType, units)`.
  - **Reading DB → display**: Convert metric to display with `kgToDisplay`, `cmToDisplay`, `gramsToDisplay`, or the generic `metricValueToDisplay(value, metricType, units)`.
  - **Unit labels**: Use `getWeightUnit(units)`, `getHeightUnit(units)`, `getMassUnitLabel(units)`, or `metricDisplayUnit(metricType, units)` — never hardcode "kg", "lbs", "g", "oz" in UI.
  - **Type classification**: `isWeightMetricType(type)` (kg↔lbs: weight, muscle_mass, lean_body_mass) and `isLengthMetricType(type)` (cm↔in: height, chest, waist, hips, arms, thighs, calves, neck, shoulders).
  - **No conversion needed**: Macros (protein, carbs, fat, fiber) are always in grams, calories in kcal, body fat / BMI / FFMI are unitless — these stay the same in both systems.
- **Carbs vs fiber convention (critical)**: There are two conventions in the codebase — **do not mix them**:
  - **Food items / nutrition logs** (`NutritionLog`, `inferCaloriesFromMacros.ts`, `NutritionCharts.tsx`, food DB mappers): `carbs` = total carbohydrates **including** fiber, matching the US nutrition label standard. Digestible carbs = `carbs − fiber`. Use `digestibleCarbs(carbs, fiber)` from `utils/carbsConvention.ts` (never re-inline `Math.max(0, carbs - fiber)`) for energy and for comparing consumed carbs against the (net) carbs goal — the carbs progress bar must show digestible carbs so it doesn't double-count fiber, which has its own bar.
  - **Source carbs are not all "total" — normalize at ingestion** (`utils/carbsConvention.ts`): the "carbs = total incl. fiber" invariant is **established at ingestion**, not assumed. All food-source mappers **must** run `carbs` through `totalCarbsForFoodSource(source, …)` before storing (it looks the source's convention up in `FOOD_SOURCE_CARBS_CONVENTION`, so a convention change is a one-line edit). Per-source conventions, verified against the standards (June 2026):
    - **USDA** `Carbohydrate, by difference` (1005) already includes fiber → `'total'` (no transform, but still routed through the helper for a future-proof entry point). <https://fdc.nal.usda.gov/>
    - **US/Canada (FDA)** "Total Carbohydrate" is by-subtraction and includes fiber. [21 CFR 101.9(c)(6)](https://www.ecfr.gov/current/title-21/section-101.9)
    - **EU (Reg. 1169/2011, Annex I)** declares _available_ carbohydrate (fiber **excluded**, fiber counted at 2 kcal/g) → `'net'` (total = carbs + fiber). <https://eur-lex.europa.eu/eli/reg/2011/1169/oj> · [US-vs-EU explainer](https://blog.trustwell.com/how-carbs-are-calculated-in-different-countries)
    - **OpenFoodFacts** stores a single `carbohydrates` field without recording the convention, so it is mixed → `'off-mixed'`, resolved in three steps: (1) prefer `carbohydrates-total`; (2) else reconcile the **stated label energy** against both interpretations (they differ by exactly `4 × fiber` kcal/100g) and keep `carbs` as-is only when the energy clearly fits the total interpretation; (3) else assume EU/net and add fiber. Step 2 is conservative — pass the raw stated kcal, never an inferred one. [openfoodfacts-server#5675](https://github.com/openfoodfacts/openfoodfacts-server/issues/5675)
    - **Musclog REST API** scrapes EU (Dutch) supermarkets (Albert Heijn, Lidl, Jumbo, …) mapping the label "Koolhydraten" (available carbohydrate) → `carbs` → `'net'`. If its upstream ever changes, update the `musclog` entry in `FOOD_SOURCE_CARBS_CONVENTION`.
    - **AI / LLM estimates** (`'ai'` → `'net'`): the macro-estimation prompt's energy note (`kcal = 4·carbs + 2·fiber`, `utils/prompts.ts`) is the net convention, so the model returns net carbs. Every AI persistence path (`NutritionService.logCustomMeal`/`logCustomMealsBatch`, `nutritionAI.ts`, `MyMealsModal`) **must** run AI carbs through `totalCarbsForFoodSource('ai', …)` before storing.
    - **Manual entry** (`CreateCustomFoodModal`): the user picks, via the `INCLUDE_FIBER_IN_CARBS_SETTING_TYPE` setting (Advanced settings → Nutrition; seeded from units in `prod.ts` — imperial/US label = include fiber, metric/EU label = exclude), whether the typed carbs field already includes fiber. Convert with `totalCarbsFromSource(manualEntryCarbsConvention(includeFiberInCarbs), …)` before saving; the field label + hint copy follow the same setting.
  - **Protein is never a share of calories when a weight is known** (`calculateMacros`, `utils/nutritionCalculator.ts`). With body fat opted in, weight_loss/hypertrophy use g/kg FFM; otherwise protein is `PROTEIN_G_PER_KG_BODYWEIGHT` (weight_loss 2.0, hypertrophy/strength 1.8, general 1.6, endurance 1.4; at least 2.0 in any deficit) × `proteinReferenceWeightKg` — the goal weight when one is set, else current weight capped at a BMI-30 reference for the user's height (140 kg does not ask for 280 g; BMI 25 would have cut a muscular 100 kg lifter's target, and without body fat on file BMI cannot tell them from an obese user). When the anchor would not fit the calorie budget, `splitAroundProtein` caps protein at `MAX_PROTEIN_CALORIE_SHARE` (75%) of it and sets `MacroSplit.proteinLimited`, instead of returning macros that add up to more than the target. The old percentage split made protein FALL in a cut, and body fat is opt-in, so most users were on it. Every caller passes `heightCm`, `goalWeightKg` and `weightGoal`; only a caller with no weight at all gets the percentage split. The three shares always add up to 100 (fats take the rounding remainder).
  - **User nutrition goals** (`NutritionGoalsBody`, saved goal records, onboarding results): `carbs` = **net/digestible carbs only** (fiber is a separate, additive macro). Total calories = `protein * 4 + carbs * 4 + fats * 9 + fiber * 2`. Never subtract fiber from carbs in this context.
  - **Food serving weights**: Stored in grams, displayed as g or oz. Use `gramsToDisplay`/`displayToGrams` and `getMassUnitLabel`. The `ServingSizeSelector` component handles this automatically.
  - **Every new feature** that displays or accepts weight, height, body measurements, or food serving sizes **must** use these conversion helpers. Test with imperial mode enabled.
- **Workout-set lifecycle is independent from RPE**: `workout_log_sets.completion_status` is the sole runtime source of truth and is one of `planned`, `performed`, or `skipped`; `difficulty_level` is an optional 1–10 effort rating and must never be fabricated merely to make a set count as performed. Session progress counts performed + skipped sets as resolved, while volume, analytics, history summaries, PRs, and progression use performed sets only. Every new set writer must assign a status explicitly. The nullable schema column and legacy `is_skipped` column exist only for upgrade compatibility: native v26 SQL and the bounded, run-once web `WorkoutSetStatusMigration` translate old rows, and `restoreDatabase` applies the same relationship-aware inference only to pre-v26 backups; current-format imports must pass the strict status/RPE schema unchanged. Runtime readers must not infer lifecycle from RPE or repair old rows on access. Code that needs plain set data uses the single `_raw` boundary in `database/workoutLogSetSnapshot.ts`; do not copy raw-column projections into analytics or UI code.
- **`loadMultiplier` is a bodyweight-relative load benchmark, not an intensity knob**: it is the load a trained lifter typically works with on that exercise, expressed as a multiple of bodyweight and measured the way the app logs it (per hand for dumbbells). The scale is anchored by the frozen entries in `data/legacyExercisesData.json`: Deadlift 1.8, Squat 1.4, Bench Press 1.0, Chest Press Machine 0.9, Lat Pulldown 0.7, Overhead Press 0.6, Barbell Curl 0.42, Leg Press 3.5, Lateral Raise 0.10. `scripts/exercise-load-multiplier-anchors.js` maps those values onto equivalent free-exercise-db movements, while `scripts/exercise-load-multiplier-policy.js` owns the remaining family rules. Both consumers depend on that reading — `utils/workoutEnergyCalculator.ts` scales mechanical work by it, and `utils/exerciseGoalProjection.ts` computes `estimated1RM / (bodyWeight * loadMultiplier * genderFactor)` and calls the lifter advanced above 1.5.
  - **Derive a new value from the closest movement already in the catalogue, never from the equipment type.** A cable variant takes its anchor's value outright; the only permitted discounts are for a real biomechanical difference — unsupported stance (`x0.75`, stance and anti-rotation become the limiter) and unilateral loading (`x0.55`). Being a cable is not itself a reason to discount, and "the stack caps out lower" is not either: the logged weight is already in every formula, so discounting the multiplier for it double-counts. The cable catalogue originally carried a flat 0.5 ceiling for every movement, putting Cable Chest Press at 0.3 against Chest Press Machine's 0.9 and Cable Belt Squat at a third of the Belt Squat Machine it mirrors. `data/__tests__/exercisesData.test.ts` pins the parity ratios and the two discount directions, so a category-wide clamp fails the build.
  - **For a bodyweight exercise the multiplier is not a benchmark — it is the fraction of body mass the movement actually shifts**, and it is derived, not estimated. Segment masses come from [de Leva (1996)](<https://doi.org/10.1016/0021-9290(95)00178-6>), adjusting Zatsiorsky-Seluyanov: a pull-up lifts the whole body less the hands (`1 - 2 x 0.0061 = 0.99`), a hanging leg raise lifts both legs (`2 x (thigh+shank+foot) = 0.41`), a quadruped glute kickback one leg (`0.20`). The push-up family is measured on force plates instead — [Suprak, Dawes & Stephenson (2011)](https://pubmed.ncbi.nlm.nih.gov/20179649/) report 69% of body mass at the top of the ROM and 75% at the bottom, so it is stored as `0.70`. **Do not add per-user anthropometrics to this**: body mass and height cancel out of the derivation (the fractions are fractions _of_ body mass, and `workoutEnergyCalculator` already multiplies by `weightKg` and `heightCm`), and sex moves the fractions only 0.1–6% — under the model's own noise floor, with `genderFactor` already applying a blanket adjustment. Store sex-neutral values.
  - **A stored `0` means "no displacement to credit", and it must stay a hard zero.** It is used for isometric holds, cardio, stretching, and mobility drills where the rep-based mechanical-work model has no useful displacement to score. Coercing a non-positive multiplier to a neutral `1` in the calculator — the first attempt at the bodyweight fix — scores a plank like a full-bodyweight rep, so the fix belongs in the data, not in a fallback. `utils/exerciseGoalProjection.ts` is the exception and still guards its divisor, because there `0` would produce `Infinity` and tier every such goal as advanced (`?? 1.0` does not catch a stored `0`).
- **`muscle_group` holds two vocabularies and readers must handle both**: the bundled catalogue and `CreateExerciseModal` write the coarse names (`legs`, `arms`, `core`, `abdomen`, … — generated in `data/exercisesData.json`), while exercises migrated from the legacy database carry fine-grained ones (`quads`, `biceps`, `abs`, …). The `MuscleGroup` union in `database/models/Exercise.ts` is the single place both are enumerated. **Never match group names yourself** — go through `muscleGroupFamily(group)` / `MUSCLE_GROUP_FAMILY` in `database/models/muscleGroupFamily.ts` (a separate, WatermelonDB-free file so pure consumers can import it as a value), which collapses both vocabularies into one body region. A hand-written `Set<MuscleGroup>` that names only one vocabulary is a silent, total failure rather than a type error: `workoutEnergyCalculator`'s `LEG_GROUPS` listed only the fine-grained names, so all 60 bundled leg exercises — every one stored as `legs`, none as `quads` — fell through to the generic branch and lost both the longer leg displacement and the `0.88x` bodyweight contribution. Because `MUSCLE_GROUP_FAMILY` is a `Record<MuscleGroup, …>`, widening the union fails the build until the new name's family is declared, and every consumer stays correct for free.
- **The bundled catalogue is the 873-entry free-exercise-db import**: `data/exercisesData.json` contains structural data and `data/exercisesEnUS.json` contains its English names/descriptions, generated by `scripts/generate-exercises-data.js` from [free-exercise-db](https://github.com/yuhonas/free-exercise-db), a public-domain project released under CC0. Structural mapping and multiplier rules live in the focused `scripts/exercise-catalogue-mapping.js`, `scripts/exercise-load-multiplier-anchors.js`, and `scripts/exercise-load-multiplier-policy.js` modules. Upstream has no popularity rank: `scripts/exercise-popularity-policy.js` owns the exactly 100 stable slugs selected from usage-based rankings, and the generator emits `isPopular: true` only for those rows (never `false`). Keep that selection slug-based, do not infer popularity from the alphabetical `exerciseIndex`, and do not fan one generic ranked movement out across several local variants. The flag is structural catalogue metadata and is not currently persisted to WatermelonDB. `data/exercisesEsEs.json`, `data/exercisesNlNl.json`, `data/exercisesPtBr.json`, and `data/exercisesRuRu.json` contain localized copy generated by `scripts/generate-exercise-locales.js`; edit the generators, not the JSON files. After regenerating upstream data, immediately run `npm run generate-exercise-locales` and `npm run generate-lang`. Localized copy joins structural data through stable `exerciseSlug`; `exerciseIndex` is only 1-based display order. Every database id is the stable `fx-<__freeExerciseDbId>` from `appExerciseId`, and bundled workout definitions name `exerciseSlug` directly — never derive either from position. `AppExerciseCatalogueService.sync` owns the database projection and reconciles structural fields plus the exact active target-muscle link set before `LegacyExerciseCatalogueMigration` may retire old rows. The legacy 256-entry catalogue lives in `data/legacyExercisesData.json` solely for historical migration v18, multiplier anchors, and the Game Boy generator; never point runtime app seeding or the Game Boy table at the other catalogue.
- **Exercise photos follow the catalogue slug**: `scripts/generate-exercise-images.js` writes both 512px q65 WebP frames to `public/images/exercises/<slug>/{0,1}.webp`; `buildExerciseImagePath` and `buildExerciseCloudUrl` in `utils/exerciseImage.ts` are the path and hosted-URL sources of truth. Website renderers combine the relative path with `EXPO_BASE_URL` through `withExpoBaseUrl`, so local and subpath exports do not point at production. Because every filename is `0.webp` or `1.webp`, `exerciseImageCacheKey` must include the parent slug (`<slug>__0.webp`) — keying on the basename collapses the entire catalogue onto one cached image. The retired illustrations live under `public/images/exercises/legacy/exercise<N>.webp` only for user-owned clones created during the production cutover. See `FIXES.md`.
- **Translation**: Check the `lang` directory for translation files. Any new feature implemented must use translation keys and add new keys to the translation files for all available languages. Bundled workout definitions live in `data/workoutTemplatesData.json`; locale-specific copy lives in `data/workoutTemplatesEnUS.json`, `workoutTemplatesEsEs.json`, `workoutTemplatesNlNl.json`, `workoutTemplatesPtBr.json`, and `workoutTemplatesRuRu.json`. `scripts/generateLangFile.js` discovers those copy files and generates `WORKOUT_TEMPLATE_COPIES_BY_LOCALE` in `lang/lang.ts`; `data/workoutTemplates.ts` uses that catalog to merge the active locale's copy by array index and fall back to `DEFAULT_LANG`, so every locale copy file must preserve the definition file's order. Template difficulty is structural data using the lowercase identifiers `beginner`, `intermediate`, and `advanced`; locale files must not duplicate it, and UI translates the identifier only when rendering its label. The definition file's `__title` is a maintainer reading aid only — it is typed on `RawWorkoutTemplateDefinition` (never on `RawWorkoutTemplate`) and `applyWorkoutTemplateCopies` strips it, so titles can only come from the locale copy files; do not rename it back to `title` or read it anywhere.
- **User-visible numbers**: Format with `Intl` via `hooks/useFormatAppNumber.ts` (components) or `utils/formatAppNumber.ts` (pure code), using locale `i18n.resolvedLanguage ?? i18n.language`. Do not use `toFixed`, raw `{n}` in JSX, or `toLocaleString()` without an explicit locale for display. Keep `roundToDecimalPlaces` / DB math separate from display.

### WatermelonDB Usage

- **Transactions**: All writes must be wrapped in `database.write(async () => { ... })`.
- **Avoid Deadlocks**: Never nest `database.write()` calls. Methods decorated with `@writer` should not be called from within another write block — from inside one, reach them through `writer.callWriter(() => record.someWriter())` (or `this.callWriter(...)` when the caller is itself a `@writer` model method), which joins the open transaction instead of enqueuing a second one behind it.
- **Every soft-deletable model overrides `markAsDeleted` with `@writer` — never inherit WatermelonDB's**: this app soft-deletes by stamping `deleted_at`, but WatermelonDB's base `Model.markAsDeleted` tombstones the record for Sync (`_status = 'deleted'`, `deleted_at` untouched) and is **not** a `@writer` — it only asserts it is running inside one. A model that forgets the override therefore fails three different ways, none of them a type error: through `writer.callWriter(...)` it throws `callReader/callWriter call must call a reader/writer synchronously` (the callback never re-enters the work queue); called bare inside a write block it silently writes the wrong thing — a row hidden from WatermelonDB queries while `deleted_at` stays null, so raw SQL reads and the DB export still consider it live; called outside a write block it throws `can only be called from inside of a Writer`. 2.10.5 shipped `WorkoutLog` without the override, so every workout-log delete threw **after** the log had already been tombstoned, orphaning its exercises and sets. `database/models/__tests__/markAsDeleted.test.ts` pins the contract for every table in `schema.ts` that has a `deleted_at` column, so a new model cannot ship without it. Cascades belong in the owning service (`WorkoutService.deleteWorkoutLog`, `WorkoutTemplateService.deleteTemplate`), not in the override — `WorkoutPlan` is the one exception, and it cascades only to its own junction rows. Code that must retire rows in the SAME `database.batch` as their replacements cannot call a `@writer` from inside the open writer; it uses `prepareSoftDelete(record, now)` (`database/prepareSoftDelete.ts`) instead of hand-stamping `deletedAt`/`updatedAt` in a `prepareUpdate` callback, so the stamp has one definition. Everything else still goes through the model's own `markAsDeleted`.
- **Read-then-write must be atomic (no TOCTOU)**: When a write's contents depend on a prior read (e.g. "insert only the rows that don't already exist yet", "seed if missing"), do that read **inside the same `database.write()`** as the write — never read outside the writer and then write. WatermelonDB serialises write blocks, so a read outside the writer leaves a time-of-check/time-of-use window where two concurrent runs both observe the pre-write state and issue conflicting writes. This bit us in production (builds 270/272): the old exercise seeder read existing rows outside its writer, so a re-entrant boot could re-insert a bundled exercise's fixed primary key and throw `sqlite error 1555 (UNIQUE constraint failed: exercises.id)`. If you need a cheap early-out, an outside read is fine **only** as a best-effort optimization — repeat the authoritative check inside the writer. `AppExerciseCatalogueService.sync` performs authoritative row-and-link reconciliation inside one writer; guarded by `database/services/__tests__/exerciseCatalogueServices.test.ts`.
- **A migration and `schema.ts` must declare the same columns, and new measurement columns name their metric unit**: WatermelonDB checks neither file against the other, so a column added to the schema but not to its migration exists on fresh installs and is missing on every upgraded phone. `database/__tests__/migrationSchemaParity.test.ts` diffs them (same type, optionality and index), requires every column of a migration-created table to come from a migration, and requires every number column added from v27 on whose name mentions a weight or distance to end in its metric unit (`_kg`, `_g`, `_m`, `_cm`) — the database is always metric, and the suffix is what stops a display value in pounds or miles being written into it. Its `KNOWN_SHIPPED_DRIFT` lists five columns from v8/v10/v16 whose shipped migration disagrees with the schema (three missing indexes, two `set_type` columns left nullable); a shipped migration can never be edited, and fixing them needs a raw-SQL migration, which triggers the pre-migration snapshot and is ignored on web — never add a new column to that list. Derived columns that a JS boot task fills (`exercises.search_text`) must be selected with a clause that matches on both adapters: LokiJS's add-columns step rewrites every existing record with the column set to `null`, and a Loki `eq(null)` also matches a record lacking the property (pinned by `database/__tests__/exerciseSearchTextWebMigration.test.ts`).
- **Never pass an unbounded id list to `Q.oneOf` — batch through `database/queryByIds.ts`**: replacing a `find()` inside a loop with one `Q.oneOf(ids)` query is the right instinct, but every id becomes a bound parameter and SQLite caps those per statement (`SQLITE_MAX_VARIABLE_NUMBER`), so the fix throws at exactly the sizes that motivated it. `fetchByIds(table, column, ids, ...clauses)` and `fetchMapByIds(...)` chunk at `MAX_QUERY_IDS` (300), collapse duplicate ids, and apply the extra clauses to every chunk; `MAX_BATCH_OPERATIONS` (500) lives there too, for `database.batch` sizing. `cascadeMarkDeleted` is the case that made this load-bearing — it fans out over every child row at a recursion level, so a repair pass over a real table group blows straight past the limit. Push soft-delete filtering into the query (`Q.where('deleted_at', Q.eq(null))`) rather than filtering the fetched rows, so a caller cannot forget it. `NutritionService.fetchLiveFoodsByIds` is the nutrition-side wrapper around exactly that pair; do not re-inline a fourth copy of "query foods by id, build a Map, skip the deleted ones". Pinned by `database/__tests__/queryByIds.test.ts`.
- **Web Compatibility**: On web, `unsafeResetDatabase()` must also be wrapped in a write block.
- **JSON Fields**: Use the `@json` decorator for complex object fields (e.g., `@json('micros_json')`, `@json('week_days_json')`). Keep a plaintext date field alongside encrypted fields when the date is needed for DB queries.
- **Raw SQL — never open expo-sqlite on `musclog.db` (critical, data loss)**: expo-sqlite and WatermelonDB bundle separate SQLite libraries, and POSIX locks never conflict within one process — so an expo-sqlite connection that **closes** always thinks it's the last connection and unlinks the live `-wal`/`-shm` files under WatermelonDB. WatermelonDB then keeps committing into the unlinked file and every commit since the unlink silently vanishes when the process is killed (June 2026 field incident: users lost nutrition logs, no tombstones). Any raw SQL while the app is running must go through `rawQueryViaWatermelon` in `database/wmdbRaw.ts` (reads/PRAGMAs) or `database.adapter.unsafeExecute` (writes). The only native exception that may open expo-sqlite on `musclog.db` is `preparePreMigrationBackupBeforeAdapter()` in `database/preMigrationCapture.ts` (a native-only module imported solely by `database/adapter.ts` before `new SQLiteAdapter`); it reads `user_version` and, **only when a data-touching migration is pending** (purely-additive `createTable`/`addColumns` migrations skip the snapshot so upgrade boots stay fast — gated by `pendingMigrationsCanTouchExistingData` in `database/migrationSafety.ts`), writes a consistent `.db` snapshot with **`VACUUM INTO`** (near-instant — the WAL is folded in, so a session killed with uncheckpointed commits is still captured; far faster than reading every row to JSON, which used to stall upgrade boots for minutes), then closes the raw connection and lets WatermelonDB open the file. `database/preMigrationBackup.ts` registers that `.db` snapshot and, when captured successfully, an AsyncStorage sidecar from the same boot moment. The snapshot is converted to the portable JSON export format **lazily** — only if the user restores or downloads it — by `database/sqliteBackupConvert.ts`, which opens the _copy_ (a different file, so rule #4 below applies), never the live DB, and injects the captured sidecar instead of reading live AsyncStorage (or omits AsyncStorage if no sidecar exists). That isolation is deliberate — the runtime backup module imports no expo-sqlite at all, so the invariant is structural. A **different** db file (the `.db` snapshot, the legacy `workoutLoggerDatabase.db`) may be opened with expo-sqlite at runtime — the hazard is specific to the _live_ `musclog.db`. Do not open expo-sqlite on `musclog.db` during migration callbacks, after boot, or from new paths. Read the incident write-up in `FIXES.md` before adding any raw SQLite access.
- **Boot-time DB-ready gate**: `seedProductionData()` calls `unsafeResetDatabase()` on a fresh install, which temporarily swaps the real adapter for an `ErrorAdapter` that throws `"Cannot call database.adapter.underlyingAdapter while the database is being reset"` on any query. Any code that runs at app startup (e.g. inside a `useEffect` in `AppBoot.tsx`) and touches the DB **must** await `waitForDbReady()` from `database/dbReady.ts` before issuing queries. `seedProductionData()` calls `markDbReady()` when it finishes (both the fast-path and the full reset+seed path). The reverse also holds: any `unsafeResetDatabase()` outside seeding (restore, clear data) **must** first await `waitForBootMigrations()`, because the boot migration chain starts right after `markDbReady()` and a reset under it throws the same error (see `FIXES.md`).
- **On web, `AsyncStorage` IS `window.localStorage` — never call `AsyncStorage.clear()`**: its web implementation is `localStorage.clear()`, a whole-origin wipe that also destroys the stored web recovery points (`musclog_backup_data_*`), the backup index and the schema-version marker — the very backups a restore exists to fall back on. Every wipe path goes through `database/asyncStorageReset.ts`: `clearAppAsyncStorage(preserved)` enumerates and removes app keys, `replaceAppAsyncStorage(pairs, preserved)` swaps in a restored snapshot, and both skip `isWebBackupStorageKey`. `clearAllAppData()` is the one deliberate exception, because removing everything is its purpose. **`isWebBackupStorageKey` is also what the export path filters on** (`captureAsyncStorageDump`): it covers the payloads AND their bookkeeping, where the old prefix-only check let an export embed the recovery-point index and the schema-version marker while deliberately excluding the payloads they point at — so a restore wrote a phantom index whose entries read back `null`. Any new path that enumerates AsyncStorage uses this one predicate; pinned by `database/__tests__/asyncStorageBackupExclusions.test.ts`.
- **A restore swaps AsyncStorage over at the end, and writes before it prunes**: `restoreDatabase()` used to clear AsyncStorage first and restore it last, so for the whole restore — dump, reset, thousands of inserts, the 873-entry catalogue sync — `onboardingCompleted`, `seeding_complete` and `currentUserSyncId` were missing. A failure anywhere in that window left a fully populated database that the next boot's `seedProductionData()` wiped and reseeded, dropping the user into onboarding; and `createPreRestoreBackup()`, which runs inside it, captured an empty `_async_storage_`, so the safety net restored an un-onboarded app. Keep the swap after the database is populated, and keep `replaceAppAsyncStorage`'s write-then-prune order. Pinned by `database/__tests__/importDbAsyncStorageOrder.test.ts`.
- **Musclog 1.x has ONE conversion, `MigrationService`, for both the on-device database and a 1.x JSON backup.** A 1.x export is `{ "<old SQLite table>": rows[] }` with no `_exportVersion` (`isLegacyV1Dump`, `utils/legacyV1Backup.ts`), so `restoreDatabase()` hands it to `restoreLegacyV1Database` (`database/legacyV1Import.ts`) straight after parsing, before the 2.0 validation that would reject it. That loads the rows into an **in-memory** expo-sqlite database (`:memory:`, never a file, so the `musclog.db` rule cannot be broken by accident) as untyped columns, so the migration reads back the same types the 1.x database returned, then resets and seeds through `seedDatabaseContents` (`database/seeders/prod.ts`, the steps first-run seeding uses) with a `MigrationService` built on that source. Three things to keep: load with `withTransactionAsync`, never `withExclusiveTransactionAsync` — the latter runs on a second connection, and a second connection to `:memory:` is a separate, empty database; build the source BEFORE the reset, so a file that cannot be loaded fails while the current data is intact; and pass `valuesEncrypted: false`, because both 1.x export paths wrote `UserMetrics`/`UserNutrition` as plaintext and AES over a plaintext number returns garbage, not an error. Every 1.x table `MigrationService` reads is created even when the backup lacks it, with the columns its SQL filters and joins on, so a new query naming another column must add it to `REQUIRED_COLUMNS`. The 1.x passphrase is the same CryptoJS AES call as 2.0's, so it is removed by the ordinary `decrypt`. Web has no SQLite (its `MigrationService` is a stub), so `legacyV1Import.web.ts` refuses before anything is wiped. Pinned by `utils/__tests__/legacyV1Backup.test.ts`, `database/__tests__/legacyV1Import.test.ts` and `database/services/__tests__/MigrationServiceLegacyJson.test.ts` (which runs the migration's own queries on Node's SQLite). **A 1.x workout session's sets are in `WorkoutEvent.exerciseData` (JSON `[{ exerciseId, sets }]`), never in the `Set` table**: `Set.workoutId` points at the `Workout` template, and reading `Set` by event id attached template sets to whichever event shared the number (1.x ids start at 1 in both tables), losing ~70% of the sets. `WorkoutEvent.status` `scheduled`/`upcoming` rows are placeholders, not history, and are skipped unless they hold sets (`isPerformedWorkoutEvent`); an unmatched nutrition log gets a food of its own rather than being dropped, and the plain-text `Chat` rows become `chat_messages`. A converted log's `template_id` is the NEW template id (via `workoutIdToTemplateId`, never the 1.x numeric id), and its `calories_burned` is filled after the sets exist by `estimateMigratedWorkoutCalories` through `WorkoutService.estimateWorkoutKcal` — the same MWEM estimate a finished live workout gets; 1.x stored none. The body it estimates for is `loadWorkoutEnergyProfile()` (`database/services/workoutEnergyProfile.ts`), read ONCE for the whole migration and passed to every estimate, and the estimates are committed in one `commitPrepared` batch; the arithmetic is the pure `estimateWorkoutKcalFromSets` (`utils/workoutKcalEstimate.ts`). Logs converted before the id fix hold the old numeric id; the run-once boot migration `LegacyWorkoutTemplateIdRepair` points each such orphan (a `template_id` that names no template row at all, deleted ones included) at the one live template carrying its workout name, and leaves it alone when several share the name. That is why "sessions of a workout" is a plain `template_id` match everywhere — never add a name-matching fallback to a read.
- **Web recovery points are database dumps, so their payloads live in IndexedDB, not localStorage**: `database/webBackupPayloadStore.ts` owns them; only the small metadata index stays in localStorage. An origin's localStorage is ~5 MB counted in UTF-16 code units (~2.5M characters), which is less than one ordinary export, so `createPreExerciseCatalogueBackup()` failed on every boot for any real database — and because a failed backup deliberately aborts the cutover, `LegacyExerciseCatalogueMigration` could never run on web (see `FIXES.md`). Reads still fall back to the legacy `musclog_backup_data_*` keys and deletes clear both locations, so do not drop that fallback.

### Component Design

- **Theme**: Use components from `components/theme/` and follow `theme.ts` conventions. User
  preferences are named palette IDs (`kinetic-depth`, `kinetic-light`, `kinetic-shock`,
  `kinetic-volt`, `kinetic-blush`) plus
  `system`; never reduce the stored preference to a boolean. `DEFAULT_THEME_BY_MODE` in the registry
  is the single answer to "the system says light, now what?" — do not spell those two IDs anywhere
  else. `themeMode` remains the derived light/dark value for status bars and NativeWind `dark:`
  variants. `theme.registry.js` is the canonical catalogue: it owns every theme ID, mode and
  primitive palette; `ThemeId`, semantic token trees, CSS/native variables, and `THEMES` are derived
  from it. Add a palette there rather than editing parallel maps, and run `npm run check-palette`.
  **A new app theme is not complete until it is also available on the public website and in the
  Game Boy game.** Keep the same theme identity and palette intent across all three surfaces, add
  the website's theme showcase asset/coverage, and run `npm run gb:gen-themes` to regenerate the
  Game Boy palette tables; never ship a theme on only one or two of them.
  Theme-specific app icon background variants are generated by applying the canonical palette to
  the alpha silhouette in `assets/icon-bg-color.png`, then compositing
  `assets/icon-bg-glass-effect.png` and finally `assets/icon-bg-text.png` over it, writing into
  `assets/theme-icons/icon-bg-<theme-id>.png` with `npm run generate-theme-icon-backgrounds`. The
  generator retains the source alpha channels and uses the glass artwork for its shading and
  highlights, with the wordmark rendered above both. It also writes an opaque copy of each to
  `assets/theme-icons/opaque/`, flattened onto the theme's `surfaceBase`, because iOS rejects
  transparent app icons. Expo's configured app icon (`icon`, `ios.icon`, Android adaptive foreground
  and background color) is the default dark theme's output; the generator does not edit `app.json`.
  **Picking a theme in the app also switches the launcher icon**, and every rule for that lives in
  `constants/themeAppIcons.js` (plain CommonJS, because the config plugin reads it during prebuild):
  the default dark theme is the default icon, every other theme is an alternate named by its
  PascalCase id, and `system` deliberately keeps the default icon — the OS can flip light/dark while
  the app is not running, so the icon could never follow it. `plugins/withThemeAppIcons.js` compiles
  the alternates in (iOS `AppIcon<Name>.appiconset`s plus `ASSETCATALOG_COMPILER_ALTERNATE_APPICON_NAMES`;
  Android adaptive icons plus one `.LauncherIcon<Name>` `activity-alias` each, with
  `.LauncherIconDefault` as the only one enabled in the manifest), and the local module
  `modules/theme-app-icon` switches between them. `services/themeAppIcon.ts`
  (`syncAppIconWithTheme`) is called ONLY from the manual theme pick in `VisualSettingsModal`: iOS
  shows a system alert on every switch, so it never fires on boot, restore or a no-op change. Three
  constraints: **MainActivity is never disabled and has no MAIN/LAUNCHER filter** — it owns the
  `com.werules.logger://` filter both widgets open through and the Health Connect rationale filter,
  which is exactly why `expo-alternate-app-icons` was not used (its Android module disables
  whichever component launched the task, MainActivity included); only the `.LauncherIcon*` aliases
  are toggled, the new one enabled before the old one is disabled. **Android applies the switch when
  the app is next backgrounded**, never in the foreground, because launchers such as Pixel's close
  the task or drop its home-screen shortcut when the alias that launched it is disabled. And
  **adding a theme needs a native rebuild** (`npm run prebuild`) for its icon to exist; until then
  `setAppIcon` rejects and the old icon stays. Pinned by `constants/__tests__/themeAppIcons.test.ts`,
  `plugins/__tests__/withThemeAppIcons.test.ts` and `services/__tests__/themeAppIcon.test.ts`.
  A theme carries no component-level presentation flags: anything a component would branch on is
  expressed as palette values instead (a theme wanting a flat summary card sets its gradient stops
  flat). `ThemeProvider` resolves the preference once, and every `useTheme*` hook selects from that
  context value. **The preference is only readable through the database, so first paint
  reads it from a mirror** — the settings mirror (below) on native, plus `utils/themeMirror`
  (`localStorage`, replayed as CSS variables by `+html.tsx`) on web. A surface that must pin a palette (currently the camera viewfinder) wraps it in
  `ThemeScope` and everything inside keeps using the ordinary `useTheme()` — do not create another
  forced-theme context and do not read `darkTheme`/`lightTheme` from a React component.
- **Geometry and type are rules, not taste** (`DESIGN.md` → Typography; Spacing, shape, and touch). Corner radii come from `theme.shape.js` (`tag` 4, `inner` 6, `control` 8, `card` 12, `sheet` 16), which `tailwind.config.js` and `theme.ts` both read; app code writes `rounded-tag|inner|control|card|sheet|full` and never Tailwind's size-named radii, which are rem-based and so differ between native (rem 14) and web (rem 16). Text stops at bold, small text (`xs`–`base`) at semibold, no text takes negative tracking, and changing or aligned numbers use `tabular-nums`. Buttons are flat and sized from `components/theme/buttonMetrics.ts`, shared by `Button.tsx` and `Button.web.tsx`; cards carry no shadow. `components/__tests__/deslopGuards.test.ts` (Phase 10) holds each rule at zero.
- **A screen's header is `ScreenHeader` (`components/theme/ScreenHeader.tsx`)** — never a hand-rolled title, back arrow or native stack header (`headerShown: true`). Place it inside `MasterLayout` and above the scroll view. Pass `destination` (a `NavItemKey`) when the screen shows the bottom bar: the header is `root` while that destination is one of the user's slots and `pushed` (with back) otherwise, decided by `resolveScreenHeaderForm` — slots are user-configurable, so never hard-code the form. Put it **outside** the screen's `AreaLockGate` with a matching `lockArea`, so back works behind a lock while the subtitle and actions, which describe or open gated records, are hidden. `components/__tests__/deslopGuards.test.ts` (Phase 8) lists the screens on it; add a new top-level screen there.
- **Controls come from `components/theme/`** — `Button`, `TextButton`, `IconButton`, `Chip`, `ListRow`, `SegmentedControl` (full width or `pill` — never both on one screen; `pill` is the inline toggle and, with `fullWidth`, the form for a secondary preference in a settings list), and `NumericTextField` for a typed number held as the user's own string (empty = no value, so effort can stay unrated). `DESIGN.md` → Buttons maps each kind of control to one. Do not hand-roll a pill, a round icon button or a text link with `Pressable` + classes; add a variant to the theme component instead. **Never give a centered `TextInput` a native `placeholder`**: on Android the caret sat at the far edge of an empty field until the first digit was typed (the set-details RIR field). `NumericTextField` draws the placeholder as an overlay and hides it while focused. Pinned by `components/__tests__/themeControls.test.ts`.
- **A plain stored setting is a `SettingDefinition`, not a get/set pair**: `SETTINGS` (`constants/settingDefinitions.ts`) names each setting's storage key, default, `parse` and `serialize` once, and `SettingsService.get(SETTINGS.x)` / `set(SETTINGS.x, value)` / `resetToDefaults([...])` read and write through it, while `SettingsContext` reads the same definition with `readSetting(map, …)` and seeds `DEFAULT_STATE` from its `defaultValue`. The service and the context used to spell every default separately. Add a new simple setting as one definition; keep a dedicated method only when there is real behaviour beyond the stored string (an asymmetric shape like `getHomeActions`/`setHomeActions`, merging like `updateNotificationPreferences`, encryption). A definition's `serialize` may throw to refuse a value that must never be stored (`reviewWeekday`). Tests stub one setting by name with `settingsGetMock({ … })` (`database/services/__tests__/settingsGetMock.ts`), which falls back to each definition's real default.
- **Settings the first frame needs come from `utils/settingsMirror.ts`, not from defaults.** Every setting lives in the `settings` table, which `SettingsProvider` can read only after the database opens and its first query emits — behind the boot migrations, seconds on a large database. So theme, language, units and the app-lock scopes are copied to one AsyncStorage entry (`SETTINGS_MIRROR_STORAGE_KEY`): `hydrateSettingsMirror()` starts at module load in `app/_layout.tsx`, `AppDbReadyGate` awaits it (and applies the mirrored language to i18n) before mounting the providers, `SettingsProvider` seeds its initial state from it, and every settings emission writes it back (`recordSettingsMirror`). The table stays the authority. Add a setting to `MirroredSettings` only if it changes what the first screen shows and is neither secret (AsyncStorage is unencrypted) nor large; it is excluded from backups (`ASYNC_STORAGE_EXCLUDED_KEYS`), so a restore drops it rather than carrying another install's copy across. `LanguageInitializer` does nothing while `isLoading`, because the pre-load `language` is a default and switching to it flashed English. **The lock scopes are read only in the safe direction**: with no mirror, `appLockScopesPending` is true until the table is read, `isScopeLocked(null, …)` locks every scope, and `AppLockOverlay`/`AreaLockGate` draw a neutral cover rather than `LockScreen` — which prompts for authentication the moment it mounts, and most people have no lock. The one exception is a database not ready when `SettingsProvider` mounts: `AppDbReadyGate` only does that for an install that has not finished onboarding, which cannot have a lock, and covering it would hide the onboarding screens. Pinned by `utils/__tests__/settingsMirror.test.ts`, `hooks/__tests__/useSettings.test.ts` and `components/lock/__tests__/lockPending.test.ts`; see `FIXES.md`.
- **Home actions are table-driven, but only half of the table is compiler-enforced**: `HOME_ACTION_KEYS` (`constants/homeActions.ts`) is the ordered, canonical list and `HomeActionKey` is **derived** from it. Adding a key makes the compiler demand the UI config in `components/home/homeActions.ts` and the handler in `app/app/index.tsx`, because both are `Record<HomeActionKey, …>`. It demands **nothing** about the persistence chain the home screen reads the user's selection through, and that chain is four separate edits: `HOME_ACTIONS_SETTING_TYPE` (`constants/settings.ts`), `SettingsService.getHomeActions`/`setHomeActions`, and the `homeActionsRaw` field on `SettingsState` plus the `homeActions` field on `SettingsContextType` (`context/SettingsContext.tsx`) that `useSettings().homeActions` resolves — two fields, not one, for the reason below. v2.12.2 shipped the two `Record`s with none of that chain, so the home screen destructured an `undefined` `homeActions` and crashed — see `FIXES.md`.

  **Every field of `SettingsState` (`context/SettingsContext.tsx`) must be a primitive.** The observer commits a new state object only when `prev[k] !== next[k]`, so a field that is freshly allocated on each derivation makes that check permanently true: every settings write anywhere in the app then produces a new context value and re-renders all ~85 `useSettings()` consumers. `homeActions: HomeActionKey[]` did exactly that, because `parseHomeActions` returns a new array per call — no type error, no failing test, just a permanent re-render. The stored value lives in state as the raw string (`homeActionsRaw`) and the array is parsed once in a `useMemo` on the context value, next to `isAiConfigured`. A `NonPrimitiveFields<SettingsState>` assertion in that file makes a non-primitive field a **build error**, so this is enforced rather than remembered.

  `HOME_ACTIONS_PER_ROW` is the single grid setting and `MIN_HOME_ACTIONS`/`MAX_HOME_ACTIONS` are **derived** from it (the row fills at two rows and looks broken below one); `parseHomeActions` owns validation, de-duplication, both bounds and the default, and every default branch returns a fresh array. The grid width is known in exactly one other place — the `flexBasis` `HomeActionsRow` gives each tile's wrapper — and `ActionButton` is `w-full`, so it carries no layout of its own and stays usable outside this row.

  **Availability is a required field on each `HOME_ACTIONS` entry (`isAvailable`), not an `if` chain.** It was a chain of `if (key === …)` ending in `return true`, which silently made every future key available on every device — the same "a plain list goes stale" failure the nav rule below is built to avoid. As a `Record<HomeActionKey, …>` field the compiler now demands a decision per key, and `useAvailableHomeActions` (`hooks/useAvailableHomeActions.ts`) is the single derivation of the filtered list, so `Platform.OS` is not threaded through callers and the home screen and the picker cannot disagree. Do not re-inline `HOME_ACTION_KEYS.filter(...)`; both consumers did, against this very rule.

  **Every catalogue entry must be reachable on some device.** `log_weight` and `log_cardio` shipped permanently gated off, and cost a config, a no-op handler with a TODO and a label in all five locales each while doing nothing — `components/home/__tests__/homeActions.test.ts` now fails the build on a key no context can make available. An unshipped action belongs in `FUTURE_FEATURES.md`, not in `HOME_ACTION_KEYS`; add it with its destination.

  **A stored selection outlives its own availability, so both consumers reconcile rather than filter.** `reconcileHomeActions` (`components/home/homeActions.ts`) drops what this device cannot offer and tops the result back up to `MIN_HOME_ACTIONS`, returning the SAME array when nothing changed — the signal `VisualSettingsModal` uses to persist the repair once, on open, so the picker and the home row cannot disagree. `components/home/HomeActionsRow.tsx` runs it for rendering only, and owns the grid with it — the route file passes the stored selection straight through and supplies one `onActionPress`, so the `HOME_ACTIONS_PER_ROW` arithmetic sits next to the constant it reads rather than inline in an 800-line screen. A plain `.filter()` in either place leaves the row below its floor, which is what opening the same database on web does to anyone who had picked the camera actions. `VisualSettingsModal` reads the available list through a **ref**: this form state is a snapshot, not a subscription, so putting it in the load effect's deps let a settings change elsewhere re-read disk over the user's in-progress selection and re-persist it — the same rule as `usePlanDraft`.

  **The picker is `components/home/HomeActionsPicker.tsx`, and pick order IS home order.** It replaced a reuse of `OptionsMultiSelector`, the workout-superset selector, which was passed `hideCheckboxes` — so no row could be toggled, the set could only be changed by reordering the whole catalogue and saving `slice(0, 4)` of it, and the grouping affordance leaked through as a "LINK" button that wrote a `groupId` onto home actions nothing reads. `hasGroups={false}` does not suppress that button, because `canGroup` never consults it. Two pure functions carry the rules so they are testable outside React and cannot be re-derived in the UI: `toggleHomeAction` (`constants/homeActions.ts`) applies both bounds and appends a newly picked action at the END — removing and re-picking is how the user reorders — and returns the SAME array reference when a bound refuses, which is the signal `VisualSettingsModal` uses to skip the write; `orderHomeActionRows` (`components/home/homeActions.ts`) puts chosen actions first in pick order so the list reads as the home row does, which is what makes the position badges mean anything. A row a bound refuses renders disabled rather than tappable-but-inert. Labels come from the same `home.actions.*` keys the tiles use, run through `homeActionListLabel`, which collapses the tile's deliberate two-line break for a one-line row rather than making every locale carry the words twice.

- **Navigation destinations are table-driven — adding one is a data edit, not a new JSX branch**: `NAV_ITEM_KEYS` (`constants/settings.ts`) is the ordered, canonical list and `NavItemKey` is **derived** from it (`(typeof NAV_ITEM_KEYS)[number]`), so the type and the enumeration can never drift. Everything else hangs off that:
  - `NAV_DESTINATIONS` (`components/navigation/navDestinations.ts`) holds each destination's icon, bottom-bar `labelKey`, account-menu `menuLabelKey` and `route` — the facts **all three** listing surfaces need. A destination picks its icon and route exactly once.
  - `NAV_SLOTS` (`components/NavigationMenu.tsx`) holds only bottom-bar routing modifiers (`activePath` when it must be broader than the route, `alsoActiveFor`/`replace`/`prefetch`/`navigateWhenActive`); every slot renders through the one `NavSlotButton`.
  - `UserMenuModal` maps `USER_MENU_ORDER` (a `satisfies NavItemKeyList` tuple — the length constraint makes a forgotten destination a build error) and reads icon/label/route from `NAV_DESTINATIONS`; only the per-item icon _tint_ is local to that menu.
  - `VisualSettingsModal` filters `NAV_ITEM_KEYS`; `ALWAYS_AVAILABLE_ITEMS` (`hooks/useNavigationItems.ts`) filters it too, rather than restating it.
  - Availability has **one** definition: `isNavItemAvailable(item, isCycleActive)` exported from `hooks/useNavigationItems.ts`. Cycle navigation is offered only while tracking is enabled (bleeding or symptoms-only); Settings always exposes `CycleTrackingModeSettings` with the same three `CYCLE_TRACKING_CHOICES` as onboarding. Skip pauses without deleting history; changing modes resumes the existing cycle and records a dated context through `CycleTrackingService.setTrackingMode`. Do not create a replacement cycle when changing an existing tracking choice.

  **Do not add another `case` to `renderNavSlot`, another per-destination JSX block to `UserMenuModal`, or another `NavItemKey[]` literal.** The two deliberate exceptions stay explicit branches: `coach` (`route: null` — it opens a modal, so every surface supplies its own handler and it renders `CoachUnreadBadgeIcon` for the unread badge) and `cycle`'s `isCycleActive` gate. The `Record<NavItemKey, …>` maps are compiler-enforced — widening `NAV_ITEM_KEYS` fails the build until each is filled in — whereas a plain array literal silently goes stale, which is why lists are either derived or typed `NavItemKeyList`.

- **Charts**:
  - Always provide a `.web.tsx` counterpart for `victory-native` components to avoid Skia errors.
  - Use absolute positioning for axis labels to maintain consistency across platforms.
  - Use `ChartTooltipContext` (`context/ChartTooltipContext.tsx`) for coordinated tooltip behavior.
- **Segments**: Use `SegmentedControl` for mode switching (e.g., 7D/30D/90D).
- **Surface color**: Components that fade content out to "whatever is behind me" (collapsed accordions, scroll shadows) must read `useSurfaceColor()` from `context/SurfaceColorContext.tsx` instead of assuming `theme.colors.background.primary` or taking the color as a prop. `BottomPopUp` publishes its sheet surface via `SurfaceColorProvider`; any other container that paints its own background should do the same. Related Android constraint: content rendered inside such a fade (e.g. `NutritionQualityData`'s score badges) must not use `elevation` — Android composites elevated views in a separate Z pass that can paint above the later, non-elevated overlay, leaking color through the fade. Use the iOS `shadow*` props alone.
- **Keyboard avoidance**: Any screen or modal that contains a `TextInput` (or any input component wrapping one) inside a scroll container **must** use `KeyboardAwareScrollView` from `react-native-keyboard-controller` instead of RN's plain `ScrollView`. `KeyboardProvider` is already mounted at the app root (`app/app/_layout.tsx`). Two patterns to apply:
  - **Full-screen layouts / screens** (`FullScreenModal` with `scrollable={true}`, plain screens): replace the outermost `ScrollView` with `KeyboardAwareScrollView` and add `bottomOffset={16}`.
  - **Bottom sheets** (`BottomPopUp`): the sheet itself lifts via `marginBottom` in `BottomPopUp.tsx` — no extra work needed for the default `scrollable={true}` case. The lift clears the **whole sheet** (via `computeKeyboardSheetLift` in `components/keyboardSheetLift.ts`), not just the focused input, so submit buttons and footers rendered below the input stay visible; it is capped so the sheet header never leaves the screen, unless a sheet is too tall to clear the keyboard at all, in which case showing the focused input wins. Do not narrow it back to an input-only lift. If you use `scrollable={false}` and add your own inner `ScrollView` with inputs, replace that inner `ScrollView` with `KeyboardAwareScrollView bottomOffset={16}` (see `EditPastWorkoutDataModal.tsx` as an example).
  - Never use RN's `KeyboardAvoidingView` for new code — it has known issues with edge-to-edge on Android (Expo SDK 54+).
  - **Never pass `contentContainerClassName` to `KeyboardAwareScrollView`** — put the padding/gap classes on an inner `View` instead. NativeWind maps that prop only for the components `react-native-css-interop` registers (RN's `ScrollView`, `FlatList`, `VirtualizedList`, `KeyboardAvoidingView`); `react-native-keyboard-controller`'s `KeyboardAwareScrollView` is not one of them, so the classes are dropped with no warning and no type error. `CreateEditPlanModal` shipped with `contentContainerClassName="gap-5 px-4 pb-32 pt-6"` and rendered edge to edge with its last row hidden under the footer. The same goes for padding, margin and gap classes in its plain `className` (`px-4 pb-32` on `ExercisesModal`, `AddUserMetricEntryModal` and `DataLogModal` rendered edge to edge) — keep only layout classes such as `flex-1` there. Enforced repo-wide by the `local/no-keyboard-aware-content-container-class` ESLint rule.

### AI & LLM Integration

- **Gate every AI-powered affordance on `isAiConfigured` (required)**: Any button, menu item, card action, quick action, or settings row whose only purpose is to reach an LLM feature **must** be hidden when no AI provider is set up. Read `isAiConfigured` from `useSettings()` (`hooks/useSettings.ts`) — the reactive check covering the Musclog free-tier gateway, on-device AI, local LLM, Gemini and OpenAI — and conditionally spread/render the affordance. The established idioms:
  - Menu arrays: `...(isAiConfigured ? [ { /* item */ } ] : [])` — see `app/app/nutrition/food.tsx` (`mealMenuItems`), `components/modals/CreateWorkoutModal.tsx`, `app/app/notes.tsx` (`noteMenuItems`).
  - JSX: `{isAiConfigured ? <AiThing /> : null}` (never `&&` — `local/no-jsx-logical-expression` is an error).
  - Components that take the flag as a prop use `isAiEnabled={isAiConfigured}` (`app/app/index.tsx`, `app/app/workout/workouts.tsx`).

  **The one deliberate exception is navigation**: `useNavigationItems.isItemAvailable` returns `true` for `'coach'` regardless of config, and `UserMenuModal` shows the Coach entry unconditionally, because those are discovery surfaces — tapping them opens `AINotConfiguredModal`, which has an "Open AI settings" CTA. A _nav destination_ may advertise AI; an _action inside a menu or sheet_ must not, because it would dead-end. Do not "harmonize" the two.

  Do **not** use `hooks/useAiEnabled.ts` for new code: it only checks Gemini/OpenAI (missing gateway, on-device and local-LLM users), runs once on mount, and is not reactive. It survives in `app/app/progress.tsx` only behind commented-out code.

- **The supported-model lists are the only place a model is retired — never write a model migration**: `GEMINI_MODELS` and `OPENAI_MODELS` (`constants/ai.ts`) are the picker's contents AND the allowlist. `resolveGeminiModel`/`resolveOpenAiModel` (`utils/aiModels.ts`) turn any stored value that is not in the list (empty, shut down, renamed, or dropped on purpose) into `DEFAULT_GEMINI_MODEL`/`DEFAULT_OPENAI_MODEL`; `AiService.getAiConfig` applies them on every call and saves the replacement, and `SettingsContext`/`aiKeyTest` resolve through the same functions, so a retired model can never reach a request and removing an entry retires it for every user on their next AI call. Do not add versioned boot migrations or per-model replacement maps for this. Gemini thinking config is per model family in `GEMINI_MODEL_CAPABILITIES` (`utils/gemini.ts`): 3.5/3.6 Flash accept `minimal`, 3.8 Flash, 3.1 Pro and Gemini 4 list only low/medium/high, and sending a level the model does not list is an API error — re-check it whenever a model is added. Refresh the lists monthly with the `update-ai-models` skill. Pinned by `utils/__tests__/{aiModels,geminiGenerationConfig}.test.ts` and `services/__tests__/AiService.test.ts`.
- **Structured Output**: Use `makeSchemaStrict` in `utils/coachAI.ts` for OpenAI function calling to ensure `additionalProperties: false`. It does **not** populate `required`; every declared property must be added to the schema's `required` array explicitly or strict OpenAI-compatible providers will reject the schema.
- **Prompts**: System prompts are managed in `utils/prompts.ts`. Append custom user prompts from the `ai_custom_prompts` table.
- **AI failures the user can fix have one classification point, and Gemini text one extractor**: `toUserFacingAiError(error, provider)` (`utils/aiErrors.ts`) maps a raw SDK failure to `AiInvalidKeyError` or `AiTimeoutError` (or `null`); `AiCancelledError` is a caller's own cancel. **Gemini answers a wrong key with HTTP 400** (`API_KEY_INVALID` in the payload), not 401 — so `isInvalidApiKeyError` reads the key signal from the message/details and a bare 400 stays an ordinary error; never reduce it to a status check, and never map a gateway, on-device or local failure to a key error (the user did not supply that key). The mapping happens ONCE, in `withLlmRetry` (`utils/coachAI.ts`), which also owns the timeout (`LLM_REQUEST_TIMEOUT_MS`, overridable per call with `CoachAIConfig.timeoutMs`; a caller cancels with `CoachAIConfig.signal`) and never retries an auth error and retries a timeout exactly once. Most `coachAI` functions return `null` on failure, so their catch blocks call `notifyUserFacingAiError` (`utils/aiErrorNotice.ts`: a deduplicated snackbar) before returning `null`; the coach path (`sendViaGemini`/`sendViaOpenAI`) throws the typed error instead and `useChatMessages` renders it with `describeAiError`. Typed errors never reach Sentry (`reportAiError`). **Gemini text goes through `extractGeminiText`** (`utils/gemini.ts`), never `response.text ?? parts[0].text`: when every part is a thought the SDK getter is `undefined` and the old fallback parsed the thought as the answer. **Gemini generation config goes through `buildGeminiGenerationConfig`** and `GEMINI_MODEL_CAPABILITIES`: Gemini 3 takes `thinkingLevel`, 2.5 takes `thinkingBudget`, exactly one per family, and structured extraction asks for the least thinking the model allows unless the user's thinking-mode setting says otherwise. With no key `configureBasicGenAI` now throws `AiInvalidKeyError` instead of returning an empty result. `AiService.getAiConfig` reads every setting in parallel. The "Test key" button (`utils/aiKeyTest.ts`) reports `network`, not `rejected`, for anything that is not a key rejection. Pinned by `utils/__tests__/{aiErrors,llmRetry,geminiText,geminiGenerationConfig,aiKeyTest,aiErrorNotice}.test.ts`.
- **Logging an AI meal takes a date AND a time, and the modal awaits the save**: `LogMealModal`'s `onLogMeal` receives one object (`LogMealData`: `date`, `time`, `mealType`, `portionGrams`) and is awaited — the modal closes only when it resolves and stays open, draft intact, when it throws. The time of day reaches the database as `consumedTime` in the `options` of `NutritionService.logCustomMeal`/`logCustomMealsBatch` and goes through `consumedDateTimeOnDay(date, consumedTime)`; omit it for the long-standing "that day, right now". The coach path threads it through `useChatMessages.markMealAsTracked`. Never floor the result with `localDayStartMs` (see the `nutrition_logs.date` rule).
- **Meal photos open full screen through `ZoomableThumbnail`, and sharing is the share sheet, not the media library**: wrap a thumbnail in `components/ZoomableThumbnail.tsx` (it renders `ZoomableImageModal` inside its own tree, so the viewer is a child of whatever modal holds the thumbnail, never a sibling). The geometry — scale clamp 1–5×, pan bounds, focal-point zoom, double-tap target, swipe-to-close threshold — is pure in `components/zoomableImageMath.ts` (every function is a `'worklet'` so the gesture code can run it on the UI thread) and pinned by `components/__tests__/zoomableImageMath.test.ts`; gestures only call it. Automatic save-to-gallery after logging is in `FUTURE_FEATURES.md` with what it would take.

Never hard-code `github.com/blopa/musclog-app` or the support address in a screen. While `DISCORD_INVITE_URL` is null nothing links to a community server (no website card, no menu item) — a placeholder `#` link is worse than none. ### Platform Specifics

- **Android**: Use namespace imports for image manipulation: `import * as ImageManipulator from 'expo-image-manipulator'`.
- **Web**: Target a mobile viewport (390x844) for correct layout rendering. Web-specific overrides use `.web.tsx` file extensions.
- **A platform sibling may export more than its base module, never less.** Metro picks `.ts` / `.web.ts` / `.ios.ts` / `.android.ts` per platform, but every import site names a symbol without knowing which file it will land in, and TypeScript type-checks the base module whichever variant ships — so a function present in one variant and missing from another is not a type error anywhere. It is a `TypeError: x is not a function` on exactly one platform, at runtime, in a code path CI never executes. v2.12.2 shipped two: `syncDailySteps` existed only in `services/healthConnectFitness.ts`, crashing the home screen on web and iOS on every foreground resume, and `utils/onDeviceAi.web.ts` lacked `sendOnDeviceStructured`. `utils/__tests__/platformModuleParity.test.ts` enforces the rule over `constants/`, `database/`, `hooks/`, `services/` and `utils/`, comparing named **value** exports only (types are erased, so they cannot cause this). A web-only extra such as `restoreReloadTarget` is fine; a deliberate omission goes in that test's `ALLOWED_OMISSIONS` table **with its reason**, so it is a decision rather than an oversight. See `FIXES.md`.
- **`reloadApp()` on web is a URL decision, not a navigation**: `window.location.reload()` re-requests the URL the tab is on, so a restore started from the onboarding landing screen reloads straight back into onboarding on top of an already-onboarded database. `restoreReloadTarget(pathname)` (`utils/app.web.ts`) owns that choice — an onboarding path is `location.replace`d to `/app`, everything else reloads in place, which `app/(website)/progress.web.tsx` relies on. Do not "fix" a landing problem by calling `router.replace` before the reload: expo-router commits its `history.replaceState` on a later tick, so the reload still uses the old URL and the only visible effect is a dashboard flash before the wrong page loads. See `FIXES.md`.
- **Widgets**: Android/iOS home screen widgets live in `widgets/`; see the Home Screen Widgets invariant below.

- **Onboarding has a shared training branch, and answers are applied only when the nutrition plan is accepted**: `app/app/onboarding/training-setup.tsx` is the one screen for both the quick (`mode=quick`, step 2 of 6) and personalized (`mode=personalized`, step 2 of 9) setups, sitting where Health Connect used to be so no step numbers shift. ### Feature Highlights

- **What's new announcements are data**: `data/whatsNew/<x.y.z>.json` holds one release's ordered pages and `info`, `choice`, `featureList`, and `action` blocks; `releases.ts` explicitly imports, validates and sorts them. The registry test requires every JSON file to be registered, valid and translated in all five locales. `whatsNewSeenThroughVersion` in AsyncStorage means **seen through this app version**, never the last announcement version; it only moves forward, including on empty upgrades and downgrades. Backups include it. Fresh onboarding writes it in the same `multiSet` as completion; landing-screen imports opt out so restored records survive and legacy backups get the tour. Restoring a backup without the record allows the tour again after reload. Home checks once per JS session after DB readiness/onboarding, only presents while focused, and suppresses widget camera launches. The intro (`WhatsNewIntro`) is centred, leads with a large icon and lists each page's headline via `pageHeadlineKey` with supporting copy via `pageHeadlineDetailKeys` on an upgrade (the same block's description, or feature-list item labels under broad headings such as “Also new”); its footer is always Back/Skip + Next side by side — Skip takes Back's slot on the first page, never a separate text link. A page may carry `requires` (a `WHATS_NEW_CONDITIONS` entry, today only `cycleTracking`), shown only when that fact holds: `loadWhatsNewContext` (`utils/whatsNew/context.ts`) reads it for the auto flow, the Settings replay uses `MenstrualCycleContext`, the debug preview assumes every condition holds, and omitting `context` hides gated pages. Missing releases merge oldest-first into one intro plus at most six content pages, reserving space for the newest releases first. `supersededIn` removes a page or block at that version; empty pages disappear. Done, Skip, X/back and route actions save the record; killing the app mid-tour does not. Settings replays the newest live release without changing the record. Choices read stored settings and write immediately on tap, with optimistic feedback and failure recovery; untouched choices never write. Workout settings and cardio are nested child modals controlled by `useSubModalState`; route actions save and close before navigating.

  **To add a release:** add its version-named JSON; register its import in `data/whatsNew/releases.ts`; add its `whatsNew.*` keys in all five `lang/locales/*/whatsNew.json` files; run `generate-lang`, translation/locale checks and the What's new tests. Extend the tuples/catalog in `utils/whatsNew/catalog.ts` only when a new icon, setting or action is needed, then fill the compiler-required implementation. `scripts/check-translations.js` scans every `*Key` string in release JSON too, so cleanup preserves these keys. The first file targets **2.13.1** (the first production release with the tour, so every upgrade from an earlier version sees it); release versions remain unchanged until release preparation, and `check-version-sync` warns non-fatally if a file is ahead of the app. Debug → What's new shows/clears/sets the record and previews individual releases before a bump; its explicit record edits reset the session gate.

- **Workout plans and schedule ownership**: `workout_plan_templates` is the only plan-membership store; templates deliberately have no `plan_id`, because one workout may belong to several plans. `workout_plans.cycle_type` selects the membership field that matters: weekly plans use `week_days_json`, rotating plans use `position` and must clear weekdays. Plan fields plus their full membership replacement are one aggregate write through `WorkoutPlanService.savePlan`, which is deliberately the ONLY way to change an existing plan — there is no `updatePlan`/`setPlanMemberships` pair to split them with, because committing a cycle-type change without the weekday clearing it implies leaves weekdays on a rotating plan. JSON and AI program generation likewise goes through `WorkoutTemplateService.createPlanWithTemplates`, which prepares every child template AND the parent plan and commits them in a single `database.batch` — one writer is not enough, because WatermelonDB serialises writers but never rolls back a batch that already landed, so a template-by-template loop that failed on the plan left orphaned workouts behind. `saveTemplate` is built the same way: it reads first, then prepares, then commits one batch. `SaveTemplateData.planIds` preserves a load-bearing distinction: `undefined` leaves memberships alone, while `[]` unfiles the template—never default it to `[]`. Membership diffs performed from `saveTemplate` use `WorkoutPlanService.prepareSyncTemplateMemberships`, which returns `{ activePlanIds, records }` — prepared records because `saveTemplate` already owns the writer and WatermelonDB writers must not nest, plus the membership set the template will have once they commit. Plan liveness is checked for BOTH halves of that diff — an id being added and an id an existing junction row already points at — so a membership left behind by a vanished plan is retired rather than making the workout look planned to a plan that is gone. Calendar ownership is contextual and never mirrored: active weekly memberships supply planned weekdays; `schedules` applies only to templates with zero active plan memberships; a rotating or unscheduled planned workout must not fall back to a dormant standalone schedule. **That rule is enforced on write, not only on read, and on EVERY membership path**: `saveTemplate` resolves membership _before_ writing schedules (via `prepareSyncTemplateMemberships`, or `WorkoutPlanService.getActivePlanIdsForTemplate` when `planIds` is omitted and there are days that would otherwise be written) and skips standalone `schedules` entirely when the template will belong to a plan; and `createPlan`/`savePlan`/`setTemplatePlans` soft-delete the standalone `schedules` of every workout they file, in the same batch, via `WorkoutPlanService.prepareStandaloneScheduleCleanup`. Filing a scheduled workout into a plan from the plan editor used to merely hide its schedule, which then reappeared the moment the workout left the plan. Do not move the schedule block back above the membership block: writing both stores leaves dormant rows that the notification resolver ignores while a membership exists, then silently resurrects if the workout later leaves the plan. `workout_templates.week_days_json` is deprecated compatibility data: normal saves clear it, and editing a legacy row materializes its effective days into standalone `schedules`. `workout_logs.plan_id` is stamped at session start but remains write-only for analytics in this version. Bundled programs create rotating plans and name their workouts by day only. The route-level workout library screen remains an orchestrator; filtering, grouped plan sections, empty/loading states, and card rendering belong in `components/workout/WorkoutLibraryContent.tsx`, which runs `groupTemplatesByPlan` exactly once and renders its flat layouts by passing `plans: []` — do not reintroduce a parallel `filteredTemplates` pass, which has to re-implement the type filter and the search matcher and drifted from both. "Which plans is this workout in?" is one flow, `components/workout/usePlanAssignment.tsx`, shared by the library screen and `CreateWorkoutModal`; a plan created from its picker is seeded with the workout via `CreateEditPlanModal`'s `initialTemplateIds`, so the plan and its first membership are one `createPlan` call rather than a create followed by a second write that can fail on its own. That hook's `selectedPlanIds`/`onChange` are OPTIONAL and its `onConfirm` reports failure by returning `false` — never by throwing. Confirming is reached from a `Pressable`'s `onPress`, which neither awaits nor catches, so a rejection escaping the hook is an unhandled rejection that merely happens to produce the right UI; and a host that persists on confirm and reads the result back off its `memberships` subscription (the library screen) has nowhere to put a selection, so requiring those two props gave it a state slot written twice and never read.

  **The plan editor's form state is a snapshot, not a subscription.** `hooks/usePlanDraft.ts` seeds it exactly once per `planId` via `WorkoutPlanService.getPlanSnapshot`, and `CreateEditPlanModal` holds only presentation. Do not seed it from `useWorkoutPlans()`: that observable re-emits on every membership write anywhere in the app, and with `memberships` in the effect's dependencies each emission replaced the user's half-typed name, chosen icon and reordered workouts with whatever was on disk. `initialTemplateIds` is read through a ref at mount for the same reason — every caller builds it inline (`templateId ? [templateId] : undefined`), so depending on it re-seeds on each parent render. The load effect is keyed on `planId` alone and gated by a `cancelled` flag, so switching plans mid-read cannot let the older snapshot land last.

  **"Which weekday is this workout due on?" is one read: `WorkoutPlanRepository.getResolvedSchedules()`.** It fetches all three calendar stores and hands them to `resolveWorkoutSchedules`. `NotificationService.scheduleWorkoutReminders` and `WorkoutService.getUpcomingScheduledWorkouts` had a copy of that fan-out each — two homes for the rule that plan membership beats a standalone `schedules` row, in code whose whole point is that it must not drift. Neither service issues those queries itself any more.

- **The session re-targets planned sets, and it must say so**: between sets, `WorkoutSessionService.saveSet` rewrites the next planned set and PERSISTS the result (`useWorkoutSessionState` only reads it back; it no longer recomputes, so the screen and the database cannot disagree). Which sets move, and from which, is decided once by `selectRetargets` (`utils/intraSessionRetarget.ts`): `workout_autonomy = manual` re-targets nothing unless the exercise has an explicit progression rule, a set the user typed over (`override`) is left alone, and a skipped set re-targets the next planned set from the last performed working set. The rewrite carries the previous set's actual load over (so a manual change there is not discarded), then recomputes weight or reps, whichever `progressionMode` prefers, to hold the set at its target reps in reserve. All of that arithmetic lives in one pure function, `computeIntraSessionAdjustment` (`utils/setAdjustment.ts`), which returns the new values **and** a `SetAdjustment` describing the change; the hook only applies the result. Keep it that way — the rule is that a number the app changed on the user's behalf is never presented as if they chose it, and the structured reason is what makes the explanation possible. `EnrichedWorkoutLogSet.adjustment` carries it to the UI, where `useAdjustmentMessage` (`components/workout/useAdjustmentMessage.ts`) states it in a sentence — the one phrasing shared by the live session, preview, Next time and Weekly Review — and the "adjusted" marker (an accent underline in Inline, a calculator icon in Guided, cleared once the user types over the number) goes on **the fields `adjustedFields(adjustment)` returns** — never inline a cause check. A `target_rir` change is marked on `adjustment.field` (it previously sat unconditionally on the weight card while the default `reps_first` mode was changing reps, so it pointed at the wrong number), a start adjustment on whatever the plan and the set now disagree about (a progression that resets the reps moves both), and a `carry_over` is deliberately not badged: that load is the user's own from the previous set, not something the app calculated.

The history/projection boundary is `WorkoutProgressionService` (`projectAdHocExercise` for Add/Swap, `projectTemplate` for preview); both use `projectExerciseProgression` and its `computeStartTarget`, so missing RIR and completed-history selection cannot drift, and `progressesLoad` there is the ONE check that keeps cardio, mobility and stretching unprogressed (it used to live only in `applyStartProgression`, so the preview and "Next up" promised changes the session never made). Two coaching rules live in that pair and nowhere else: a deload needs **two** sessions in a row at the same load that failed — average rated RIR 0 for the automatic path (`failedBefore`), below `repMin` for the double-progression and top-set rules (`missedAtSameLoad`) — because one hard day is noise, and the first miss holds instead; and `reps_first` climbs from the PLANNED reps (`repsFirstRange`: plan … plan + 2), falling back to the generic 8–12 / 12–16 range only when `plannedFromHistory` says the "plan" is a copy of last session (Add/Swap), since the generic range walked a 5×5 up to 12 reps. The automatic path progresses when the last session's average rated RIR met the live-session target (`DEFAULT_TARGET_REPS_IN_RESERVE`, 2) AND the planned reps were hit — it used to wait for 3, so a lifter training exactly as prescribed repeated forever. A session whose effort was never rated falls back to double progression on reps alone (`computeUnratedTarget`: climb the plan's range, then add load; hold when there is no plan to judge against) and attaches a `range` rule detail to the adjustment, so the explanation never claims a reps-in-reserve figure nobody recorded. "Last session" means the latest COMPLETED WORKOUT: history reads a wider window of log exercises and orders it by the parent log's `completed_at`, because a log exercise added to an old workout afterwards has a fresh `created_at`. History is read with one batched set query (`fetchByIds`), not one per past session, and its step and rounding come from `loadStepFor` (`utils/loadIncrement.ts`) — which every progression path uses, the between-sets re-targeting in `useWorkoutSessionState` included and `planStartChanges`, which rewrites only a block of STRAIGHT sets: a pyramid or back-off cannot be moved by one number from last time. Each rewritten set records a `StartSetAdjustment` in `workout_log_sets.adjustment_json` (`parseStartAdjustment` drops anything malformed — an explanation that cannot be trusted is dropped, not shown); a Weekly Review lighter week also records `planRepsInReserve` and `droppedSetIds` in the kept sets' prescriptions, which is what lets `revertStartAdjustment` restore the whole plan — dropped sets, loads, reps in reserve and `workingSetCount` — and nothing the user deleted themselves. `WorkoutLog.updateSet` clears it the moment the user edits the weight or reps or performs the set, because the number is then theirs, and `revertStartAdjustment` restores the OTHER number the user could have started with (`revertTargetFor`: last time's after a progression or deload, the plan's after a repeat). **The rest timer has one default**: `resolveRestSeconds` (`utils/restTimer.ts`) replaced three hard-coded fallbacks (60, 60 and a 90 placeholder the ring was drawn against). Haptics fire on the TRANSITION onto a value (`hapticBeat`), never the value itself, or any unrelated re-render would buzz again. With `auto_start_rest_timer` off the session stays put and offers a "Start rest" pill instead of `router.replace`-ing to the timer. - **Exercise search is `exercises.search_text`, built and queried by ONE module**: `utils/exerciseSearch.ts` normalizes (lowercase, strip diacritics, separators → spaces), stems plurals, expands abbreviations (`EXERCISE_ABBREVIATIONS`) and builds the stored word set; `database/exerciseSearchCondition.ts` turns a query into the `Q` condition and `matchesExerciseSearch` is its in-memory twin (website, `findExerciseByName`). Never filter exercises with `Q.like('name', …)` or `name.includes(…)` again. The traps that shaped it: (1) **an index and a query must go through the same normalization**, which is why the column stores words and not names; (2) a catalogue row's `name` is written once, in the language active at first boot, and never re-localized — so a row created as "Agachamento" must still be found by "squat", and `search_text` therefore holds the name in **every** bundled language (`getAllLocaleExerciseNamesBySlug`); (3) **do not use `Q.sanitizeLikeString`** for these patterns — it rewrites every non-ASCII-alphanumeric character to `_`, so a Cyrillic query would match any string of that length; `normalizeExerciseText` already reduces words to letters and digits, which is what makes them LIKE-safe; (4) SQLite `LIKE` is case-insensitive for ASCII only, so Cyrillic case folding has to happen before the query, not in it; (5) `\p{L}` is deliberately not used (nothing else in the app relies on Hermes property escapes). Every writer of the column goes through `computeExerciseSearchText` (`database/exerciseSearchText.ts`): the catalogue sync (which reconciles it with the catalogue fields but keeps it OUT of `isComplete`, because that gates retiring the legacy catalogue and derived search data must not block it), `ExerciseService.createExercise`/`updateExercise`/`duplicateExercise`, `ExerciseAliasService` (alias row and `search_text` change in one batch, so an alias the UI lists is always searchable) and the boot task `ExerciseService.backfillSearchText` (user exercises that predate the column). Rows with a null `search_text` fall back to a plain `name` match until backfilled. Adding an abbreviation is one entry in `EXERCISE_ABBREVIATIONS`. `findExerciseByName` (AI workout import) accepts an exact normalized match or a fuzzy match that is **unambiguous** — it must never guess between several plausible exercises. - **Optical Transfer (device-to-device over light)**: moves Musclog data between devices with no network — one screen streams fountain-coded QR frames, the other camera reads them. Android, iOS, and web can send or receive; Musclog GB is sender-only and exposes two send actions — a whole-database `SHARE DATA` under Settings, and a `SHARE DAY` on the nutrition screen's SELECT menu that sends one day of eating as a non-destructive share (offered only when that day has entries). The app's full send/receive entry point is a `SettingsCard` in `DataSettingsModal`'s Data Portability section → `OpticalTransferModal` → `OpticalSendModal` / `OpticalReceiveModal`; the first onboarding screen also opens `OpticalReceiveModal` directly with `accept="database"`, so a fresh install can receive a full backup without first creating a user and cannot accidentally accept a food, meal or day share. App logic lives in `utils/optical/` (pure, no RN imports, so it runs in the Jest `node` project); Skia and the camera are isolated in `components/optical/`. Game Boy logic lives in `gameboy/src/features/optical/`. **Read the Optical Transfer section in `RESEARCH.md` before touching any of it** — it records the on-device measurements and cartridge constraints the design rests on. The invariants that bite:
  - **`fountain.ts` and `frameProtocol.ts` are FROZEN wire format**, ported verbatim from [decimen-optical-transfer](https://github.com/bashalarmistalt/decimen-optical-transfer)'s **MIT** releases (v0.3.0 and earlier). Upstream relicensed to **AGPL-3.0-or-later at v0.4.0** (2026-08-09), so do not pull fixes or new helpers from v0.4.0+ into `utils/optical/` — that would import AGPL code into this app. See `RESEARCH.md`. The two phones in a transfer can be running app versions months apart and derive every frame's block subset independently with no handshake, so these are compatibility contracts with our own past releases. `dlog()` exists because `Math.log` is implementation-approximated in ECMAScript — replacing it, or shortening its 21-term series, silently breaks every future transfer with no error, just a bar that stops. `utils/__tests__/opticalFountain.test.ts` holds decimen's golden vectors; a failure there is a broken format, not a broken test, and needs a header version bump rather than a re-recorded constant. Jest runs on V8, so the Hermes sweep in the bench screen is the other half of that guarantee. **All format evolution goes in `container.ts`**, whose version byte is checked _after_ reassembly and so can say "update the other phone".
  - **The Game Boy speaks that frozen receiver protocol but never receives.** It sends two compact schemas, each expanded strictly and immediately after `JSON.parse`, before any validation, backup, or destructive wipe: the whole database, marked `_gameBoyExport: 1` and expanded by `utils/optical/gameBoyExport.ts`; and one day of eating, marked `_gameBoyShare: 1` and expanded by `utils/optical/gameBoyDayShare.ts` into an ordinary `nutritionDay` share envelope, which then goes through the SAME `parseShareEnvelope` as any app-built share — the expander gets no privileges the wire does not have. `utils/share/parseIncomingShare.ts` is the single receive entry point that tells the two apart. A day share renders through the same streaming sink and the same food tuple as the database export (so the receiver parses one tuple shape, not two), narrows `scan_references` to that day, and flips exactly two container fields: `payloadKind = 1` and `exportVersion = 0xFFFF`. `data/gameBoyOpticalProtocol.json` is the single wire contract for the export-version numbers, the exercise enum ordinals, the frozen `exerciseSlugs` table order, and the frozen `foodExternalIds` list, all consumed by both the ROM generator and the TypeScript receiver. Never derive any of them from the current popular-exercise subset, reorder existing entries, or duplicate version literals in C; append a new value deliberately and regenerate with `npm run gb:gen-exercises`. The generator rejects catalogue values absent from the contract, and `selectPopularExerciseRows` diffs `exerciseSlugs` against the `isPopular` flag in **both** directions so a re-run of the popularity policy fails the build rather than silently renumbering the table.

    **`exerciseSlugs` position is exercise identity on two wires at once**, which is why it is frozen rather than sorted: a cartridge `.sav` stores a logged set's exercise as that 0-based index, and the optical export sends the same index. It is deliberately NOT `exerciseIndex`, which is alphabetical display order over all 873 catalogue entries and shifts whenever free-exercise-db gains a row — sorting by it would re-point every existing save file and every past export at a different movement. On the receiving side `utils/optical/gameBoyExerciseMapping.ts` turns that index back into `appExerciseId(slug)` (`fx-<slug>`), so an imported Game Boy workout references the bundled catalogue row the app already owns and keeps its localized name, photos and target muscles. The dump therefore carries exercise **identity** only and creates no `exercises` rows for mapped indices; `AppExerciseCatalogueService.sync` runs right after the restore populates the database and owns their content. An index past the end of the frozen list means the cartridge is newer than this build, and only then is a plain user exercise created from the tuple the cartridge sent — never reject the transfer for it. Cartridge history carries calendar days but no times: the receiver maps metrics to device-local midnight and food/workout events to device-local noon, capturing the corresponding offset so imports keep the same displayed day in every timezone. The receiver synthesizes only the app-owned profile defaults the cartridge cannot store (editable name, blank email, default avatar, valid sync UUID, inferred birthday, onboarding/current-user metadata, and the unit-derived manual-carbs convention); it must not fabricate body-fat, cycle, cloud-account, or health-permission data. It uses an uncompressed, unencrypted database container, 292-byte fountain blocks, base44, and fixed QR version 11-L/mask 0. Because GBDK has no floating-point runtime, its robust-soliton calculation is fixed point and omits ambiguous CDF-boundary or >64-degree sequence numbers; arbitrary sequence gaps are legal, and every emitted selection must remain byte-for-byte compatible with `fountain.ts`. Keep `utils/__tests__/gameBoyFountainPort.test.ts`, `utils/__tests__/gameBoyExport.test.ts`, `utils/__tests__/gameBoyDayShare.test.ts`, `utils/__tests__/gameBoyExerciseCatalogue.test.ts` and `utils/__tests__/gameBoyFoodCatalogue.test.ts` with any change; the first pins the C transport constants (including both payload kinds and the share export version) against the app's own `container.ts`/`frameProtocol.ts` values rather than against copied literals, so keep it deriving them. `SHARE DAY` is the ONE partial-share choice the cartridge offers — do not add more, and do not add Game Boy-to-Game Boy receive/schema paths.

    **`foodExternalIds` position is food identity on the same two wires**, for exactly the reasons `exerciseSlugs` is, and it matters more: `ff_load` truncates a bundled food's name to 16 characters (`FF_NAME_VISIBLE`), so "Lettuce, leaf, green, raw" arrives as "Lettuce, leaf, g" and name-based dedupe would miss essentially every bundled food — growing a second, worse-named copy on every share, in a database the day share MERGES into rather than replaces. `utils/optical/gameBoyFoodMapping.ts` resolves an index to the frozen `external_id` plus the full seed row from `data/usda_foundation_foods.json` / `data/common_foundation_foods.json`, so the importer's food dedupe takes its `external_id` branch and reuses the receiver's own copy. `utils/foundationFoodSeed.ts` is the single parse of a seed row, shared with `database/seeders/prod.ts`, so a food cannot mean two things. The list is append-only and `gameboy/tools/gen-foundation-foods.mjs` fails the build if a regenerated table would change an existing entry; two indices MAY share an `external_id` (the USDA set ships rows differing only in `description`) and both resolving to one receiver food is the wanted outcome. A custom food or an index past the end of the list falls back to the tuple the cartridge sends alongside — never reject the transfer for it. The whole-database export path deliberately does NOT use this mapping: it restores into a wiped database where there is nothing to dedupe against, and stamping `external_id` on its foods would make `seedUSDAFoundationFoods` skip seeding on the next boot, leaving the user with only the handful of foods the cartridge referenced.

  - **Game Boy optical buffers are transient SRAM bank-3 scratch only.** Custom foods end at `0x0A2F`; QR workspaces start at `0x0B00`, the binary frame at `0x0F00`, base44 text at `0x1040`, and the 12-block payload cache at `0x1250..0x1FFF`. The streamed exporter may read the documented food-log layout directly, but no optical code may overwrite authoritative profile, food-log, workout-log, metric, or custom-food data. QR version 11 occupies 324 tiles across both CGB VRAM banks; the attribute map must retain `S_BANK` for tiles 256–323 and the renderer must set `LCDCF_BG8000`. The font UI selects signed `0x8800` addressing, under which tile IDs 0–127 resolve to the font at `0x9000` instead of the QR data.
  - **Frames are armored to text with base44, never sent as bytes.** vision-camera's `Code` is `{ value?: string }` — there is no byte array — and MLKit's `rawValue` is null for non-text payloads. The alphabet is QR's alphanumeric set minus space, which keeps symbols in ALPHANUMERIC mode (3.1% cost, vs 25% for base64); space is excluded so no whitespace trimming can eat a frame. Do not switch to byte mode without shipping a native decoder.
  - **The sender cannot measure what limits the transfer, so density is both capped and user-overridable.** `calibrateDevice()` runs on the sending phone, but the constraint lives on the _receiving_ phone's camera (autofocus, sensor, lighting) — and an undecoded frame still counts as sent, so no sender-side measurement can even see the failure. On Android the code-scanner analyzer is a bare `ImageAnalysis.Builder().build()` with no ResolutionSelector, so it runs at CameraX's ~640×480 default and `format` cannot raise it (measured: 640×480). Goodput is nearly density-_invariant_ when encode-bound (QR capacity and encode cost both scale with modules²) while autofocus tolerance collapses as density rises, so density buys nothing and costs reliability — a field transfer at `dense` took **an hour**. Hence both: `calibrateDevice()` only considers presets up to `MAX_RECOMMENDED_OPTICAL_PRESET_ID`, and `OpticalQualityControls` lets the user change speed and code size **while streaming** (speed first — it is free; density restarts the stream, because a new QR version means a new `streamIdentity` and the receiver rebuilds its decoder). `useOpticalSender` retains the packed container for the session so re-slicing is instant. **Do not "optimize" by raising density, and do not move the controls off the streaming screen.**
  - **Never drive the sender's display loop with `setInterval`**, and always `dispose()` the `SkImage`. Both caused a progressive frame-rate collapse on real hardware; see the doc. That loop has exactly one implementation — `hooks/useQrFrameLoop.ts` — shared by `useOpticalSender` and the bench screen (`app/app/test/optical-bench.tsx`). Do not re-implement it in a new screen: the bench is the instrument used to validate these behaviours, so a second copy there would silently stop measuring what ships. `hooks/__tests__/useQrFrameLoop.test.ts` pins the self-scheduling, the all-or-nothing frame cache, and install/arm order-independence.
  - **The frame cache is all-or-nothing** (`planFrameCache`). Looping fewer distinct frames than the receiver needs is a silent, unrecoverable deadlock at ~98%, so a cache that cannot hold a safely loopable set is not built at all.
  - **An in-flight `unpack` is cancelled by generation token, not by clearing state.** `useOpticalReceiver` stays mounted when its modal closes, and unpacking (decompress + verify, plus decrypt when a passphrase is involved) runs long enough for the user to close or rescan mid-flight; `reset` bumps `generationRef` and every publish in `unpack` is gated on it, so a stale continuation drops its result instead of restoring a previously scanned payload over a newer one. Mirrors the sender's `generationRef`.
  - **Receiver progress tracks frames collected, never blocks solved** — LT peeling back-loads, so a blocks-based bar looks stalled and then teleports. And `onCodeScanned` must stay `useCallback(…, [])` writing only to refs: MLKit fires it 15–30×/s and a `setState` there starves the decode.
  - **`restoreDatabase(json)` takes one argument here.** The passphrase lives at the container layer and has already been removed; passing it would try to AES-decrypt plain JSON. Compression happens strictly _before_ encryption — the reverse makes the payload incompressible and the transfer ~9× longer.
  - **Share payloads are non-destructive and deliberately cannot masquerade as exports.** A share envelope must never gain a top-level `_exportVersion`; its rows stay under `records`, its container uses `payloadKind = 1` and the compatibility sentinel `exportVersion = 0xFFFF`, and the destructive receive branch must require `payloadKind === 0` (never “not a share,” because an unknown future kind is not a database). `utils/share/` stays pure for the same reason as `utils/optical/`: envelope parsing and import planning run in the Jest `node` project. Meal shares have no passphrase path, preview before saving, and import in one WatermelonDB writer without resetting or reloading the database.
  - **A `nutritionDay` share is one calendar day of the diary, and it is the only share that can touch data the receiver already has.** `importShareEnvelope` REFUSES it without an explicit `dayMode: 'add' | 'replace'` — there is no safe default, since `add` on an already-logged day double-counts it and `replace` on a hand-edited one discards that work, so the receive screen asks. `replace` soft-deletes the receiver's live logs on the days the incoming rows land on, in the same writer and batch as the inserts, and decides membership from the INCOMING ROWS' own `date`/`timezone` — never from `summary.dayKey`, which is display metadata. Those two columns travel unchanged and nothing rewrites them: `utcNormalizedDayKey` re-applies the stored offset, which is exactly what keeps a day sent from UTC+2 on that same day for a receiver in UTC-5. The kind is deliberately **rootless** (`ShareKindSpec.rootTable: null`, and the parser then requires the envelope to omit `rootTable`/`rootId` — both directions): a day is not a row, and there is no `days` table to anoint one. Do not model it as a meal; `buildLoggedMealShare` already sends a diary SECTION as a recipe into My Meals, which is a different feature. Two columns need care: `logged_*` is encrypted with the SENDER's key, so the builder decrypts it and `ShareKindSpec.encrypt` re-encrypts it here (before the writer opens — every value hits `getEncryptionKey()`, and holding the write lock across that blocks every other write in the app); and `nutrition_logs.external_id` is deliberately NOT shareable, because it is the Health Connect sync key and importing another device's would make this phone's next sync mistake a received log for one it had already synced. `group_id` is neither passed through nor dropped — `ShareKindSpec.regeneratedColumns` mints one fresh id per distinct incoming value, so a shared AI meal stays one meal without colliding with an unrelated local group.

- **The circadian expenditure model has one implementation: `utils/circadianBurn.ts`, ticked by `hooks/useCircadianBurn.ts`.** `BLOCK_FRACTIONS` (`constants/circadian.ts`) splits TDEE across six 240-minute phases; `CIRCADIAN_SEGMENTS` lays them out in minutes-since-midnight order, with `earlySlеep` appearing **twice** because its block straddles midnight. `circadianBurnedKcal(tdee, minutesSinceMidnight)` returns 0 at midnight and exactly `tdee` at the end of the day, so it is a strict partition and can never overstate the day; it stays fractional, and the caller rounds (stat strip, card) or floors (live counter). Three surfaces read it — the home stat strip, `CaloriesBurnedCard`, and `CircadianScienceModal` — and the card and modal each carried their own copy of the segment table, the accumulator and the phase lookup before the strip became the third. Do not add a fourth: `useCircadianBurn` is the only clock, and its `enabled`/`tickMs` options cover the differences (the modal ticks per second and only while visible, everything else per minute).

  The hook drives the clock with `useSyncExternalStore`, not `useState` + an effect: the reading is derived from `Date.now()` on every render, so a surface re-arming after being hidden has no stale copy to resynchronise — and the synchronous `setState` in an effect that resync needed is an ESLint error (`Calling setState synchronously within an effect can trigger cascading renders`). The snapshot is **quantised to `tickMs`**; an unquantised clock reading differs on every render and re-renders forever.

  The Cyrillic `е` in `earlySlеep` is a typo frozen into `BLOCK_FRACTIONS` and into the `progress.circadianPhase.*` / `progress.circadianModal.*` keys in every locale. Renaming it in one place silently loses both the phase's rate and its label, with no type error in the translation files.

  **Today's step count reads through `hooks/useDailySteps.ts`, which must use `observeWithColumns(['value'])`.** The platform sync upserts ONE `daily_steps` row per day, so every reading after the first is an in-place update to a record already in the result set — `observe()` only emits on set membership, so the strip would show the day's first reading and then never move (the same trap as `useNotes`). The query also filters `deleted_at`, and because `getDecrypted()` is async the hook gates each publish on an emission token so a slow earlier decryption cannot land after a newer one.

- **Every deload snaps DOWN to a load that is really lighter, through `loadBelow` (`utils/setProgression.ts`).** Rounding a 10% cut to the nearest loadable weight sends a 10 kg dumbbell's 9 kg straight back to 10 kg, so the "deload" changed nothing and the lifter was held at a load they kept failing, forever. `loadBelow(current, target, step)` walks down one step at a time until the load is at or under the target AND strictly below the current load, and returns the current load when nothing lighter exists (an empty bar, an unloaded exercise) — the caller then holds and must not claim a deload. `deloadedLoad` (automatic, rep-range rules, a lighter week), the linear rule's own `deloadPercent` and a lowered percentage training max all go through it. Never call `step.roundLoad` directly on a deload target.
- **Unloaded bodyweight work only ever adds reps, up to a per-exercise ceiling.** `computeStartTarget` takes `repCeiling` for a bodyweight exercise whose last session had no external load; it climbs one rep a session past the plan's range and, at the ceiling, holds with a `{ kind: 'ceiling' }` explanation telling the lifter to add a vest or belt, use a harder variation or slow the tempo — it never invents external kilograms (it used to add 2.5 kg to push-ups). Once a lifter logs external load on the exercise it progresses like any other. The ceiling is `exercise_user_settings.rep_ceiling` (migration v35), picked from `BODYWEIGHT_REP_CEILING_OPTIONS` (10–50, never typed) in the exercise's preferences. With no pick the default depends on the movement (`defaultRepCeilingFor(loadMultiplier)`): 15 for anything that moves at least 85% of body mass — pull-ups, chin-ups, dips, muscle-ups, glute-ham raises, jumps — and 25 otherwise; no list of names, because for bodyweight work the multiplier IS the fraction of body mass moved. Because the default varies, an explicit pick is stored verbatim even when it equals today's default (`storedRepCeiling`), so a lifter who chose 25 for pull-ups is never moved to 15. Code outside React reads it through `ExerciseUserSettingsService.getResolvers(gym).repCeilingFor(exercise)`, the same single read that resolves units; the hook's `get(id).repCeiling` is the pick only (`undefined` when none) and the caller supplies the movement's default.
- **The percentage rule's training max goes down as well as up.** After `failuresBeforeReset` (default 2) sessions in a row missed reps at the same training max it is cut by `resetPercent` (default 10%) — the 5/3/1 reset — and the misses that caused it cannot trigger another reset, because the streak counts only sessions at the current training max. Both fields are optional in stored JSON: `FIELDS_ADDED_LATER` fills the default for a rule saved before they existed, while an out-of-range value still makes the whole rule untrusted. Never re-estimate the training max from recent sets instead: submaximal sets ratchet it down.

- **The TDEE the app shows and the daily dynamic targets come from `getLatestHistoricalNutritionWindow` (`utils/historicalNutritionParams.ts`)**, used by `useEmpiricalTDEE` and `resolveDailyMacros`/`resolveDynamicGoalPreview`. It always leaves unlogged days out of the intake average (`excludeUnloggedDays`: a forgotten day reads as an average one), while flagged fasting days stay in as 0 kcal through `getRangeNutrients`' `effectiveDayCount`. When the 30 days ending today have too little data, it measures the 30 days ending the day after the last food log (or at the last weigh-in, when weighing stopped first) and marks the result `fromPastWindow`; every surface that shows that TDEE as a number renders `PastTdeeWindowNote` with its dates (`CaloriesBurnedCard`, `NutritionGoalsBody` via `ResolvedMacros.pastEmpiricalWindow`). Never let the window span the gap itself: the trend interpolates across it and the tissue change is spread over months without food. The Weekly Review recommendation (`resolveWeeklyRecommendation`) deliberately never falls back — it judges the reviewed week. Comeback nutrition still uses the formula for its first weeks (see Comeback mode). Pinned by `utils/__tests__/{historicalNutritionParams,dynamicNutritionTarget}.test.ts`.
- Empirical TDEE separates intake coverage (`historicalTotalDays` / `totalDays`) from elapsed weight-anchor days (`historicalWeightChangeDays` / `weightChangeDays`). Food belongs to the half-open weight-anchor interval; a fasting or missing-log denominator must never divide the entire tissue-energy change. `useWeeklyReviewOverview` refreshes evidence on focus and discards obsolete requests; review-status changes alone cannot detect new food or weights. Photo gestures use `fitContain` with actual image dimensions for every pinch, pan and double tap.
