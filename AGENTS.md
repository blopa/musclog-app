- `npm run typecheck`: Run TypeScript type checking
- `npm run check-translations`: Validate translation keys used by the app

- `npm run build-android`: Production build for Android via EAS (AAB for Google Play)

Modal captures reload the fixture between targets because some overlays ignore Escape. A capture failure must fail the suite.
  - The suite persists the theme through the preferences picker after demo seeding (wait out LokiJS's 500ms autosave before unloading the page — the checked radio only proves the synchronous browser mirror) and enables reduced motion; `ConfettiOverlay.web.tsx` must honor `prefers-reduced-motion`.

## Repo Structure: Dual-Purpose (App + Website)

One Expo Router project serves two purposes:

- **`app/app/`** — mobile app screens (iOS & Android). Changes here affect the app only.
- **`app/(website)/`** — the marketing website, rendered on web only. Changes here affect the website only. Services, database and utils are shared by both.

**Website conventions:**

- `.web.tsx` files inside `app/(website)/` are the web implementations; their non-web counterparts are native stubs or redirects. Website components live in `components/website/`. Layout is `app/(website)/_layout.web.tsx`.
- The website is a standard React web app: plain HTML elements and Tailwind/NativeWind classes, **not** React Native primitives.
- **Static SEO** comes from each route's `generateMetadata()` export using `components/website/websiteMetadata.ts` (SDK 58 does not prerender `expo-router/head`). `WebsiteSeo.tsx` updates the same metadata after client language changes. `WebsiteShell` provides the shared public-page chrome, including the production `/` landing page (rendered directly, not as an empty redirect).
- **`components/website/websiteRoutes.json` is the single registry of fixed website routes**: `path`, optional `robots` (omit for indexable), optional `llms` blurb. `scripts/generate-web-seo-files.js` regenerates `public/robots.txt`, `public/sitemap.xml` and `public/llms.txt` on every `npm run web` / `npm run build-android-web` — those three files are generated, never hand-edited, and the route list must not be copied into the generator or `llms.txt`. Adding a fixed public route = the registry entry + its `website.seo.routes.<key>` title/description in each `lang/locales` `website.json`. Blog posts, category listings and pagination are the exception: the generator derives them from the Markdown posts through `components/website/blogRoutes.js`.
- Sitewide `Organization`/`WebSite` JSON-LD is rendered by `WebsiteShell` via `WebsiteStructuredData.tsx`; add page-specific schema there (`FaqPageJsonLd`, `SoftwareApplicationJsonLd`, `BlogPostingJsonLd`) when content maps to a schema.org type. Never fabricate fields like `aggregateRating`.
- **Link to another website page with a plain `<a href>`, not expo-router's `Link`.** On web `Link` renders a react-native-web `Text`, which inherits neither `color` nor typography from HTML ancestors, and `hover:` classes lose to its inline `style`. If you do use `Link`, put every typography and color declaration on the `Link` itself (the nav in `WebsiteWrapper.web.tsx` does, with an explicit inline `color`).
- **Web icon fonts register during root layout rendering** (`registerWebIconFonts` in `app/_layout.tsx`). Expo SDK 57+ imports routes outside its server font context, so a module-scope call crashes static export; keep it inside the render (an effect would omit it from the server HTML).
- **Navigation below `lg` is the header burger menu** (`MobileMenu` in `WebsiteWrapper.web.tsx`); the footer carries only secondary/legal links at every width. A new primary destination is one edit to `MobileMenu`'s `menuLinks`. The panel is **portalled to `<body>`** (the header's `backdrop-blur-md` would otherwise clip a `fixed` backdrop), carries its **own `lg:hidden`** plus a `matchMedia('(min-width: 1024px)')` listener (otherwise growing past the breakpoint leaves body scroll locked), closes on backdrop and Escape rather than a document-level `pointerdown` (the portalled store/QR popovers count as "outside"), and moves focus in on open and back to the trigger on close.
- **Website preferences**: `WebsitePreferences.tsx` owns the single header control for language and theme, with Language/Theme tabs in a portalled, viewport-constrained panel. Theme changes update the browser mirror and app settings. Do not add separate picker pills or duplicate theme options in the burger menu.
- **Popover vertical placement is `computePopoverTop`** (`components/website/popoverPlacement.ts`), shared by `DownloadModal` and `StoreButtons`' QR popover: it flips above the trigger when there is no room below. Height is measured after the first render (it returns a downward position while `popoverHeight` is 0 and settles on the second pass) — do not measure during render. Horizontal placement stays per-component.
- **SDK 58 web document contract**: `app/+html.tsx` must render all `useServerDocumentContext()` attributes/nodes, including `bodyNodes` for hydration, merged with the existing body classes. JSON-LD uses safe direct script markup, never Helmet. Keep static output for GitHub Pages. Web layout insets come from CSS `env(safe-area-inset-*)` via `useAppSafeAreaInsets`; native keeps window insets.

**Blog:**

- Posts live recursively under `app/(website)/posts`; every file/directory segment must be URL-safe (letters, numbers, hyphens, underscores). Frontmatter requires `title`, `date` (`YYYY-MM-DD`), `category`, `tags`; `description` is optional. `category` is a lowercase kebab-case key whose label must exist at `website.blog.categories.<key>` in every `lang/locales/*/website.json`. Category labels link to `/blog/category/<key>` (later pages `/blog/category/<key>/page/<n>`; the first `/blog` page is the bare path, later ones `/blog/page/<n>`).
- Images live under `public/images/blog/` and are referenced as absolute `/images/blog/...`. Run `npm run compress-blog-images` after adding PNG/JPEG assets (caps at 1792px, writes q85 WebP only when smaller, updates Markdown references, removes the source).
- The blog routes (`blog/index.web.tsx`, `blog/page/[page].web.tsx`, `blog/[...slug].web.tsx`, `blog/category/[category]/`) use Expo static data loaders plus `utils/blogPosts.server.ts`; dynamic routes export `generateStaticParams`, and their unsuffixed `.tsx` siblings are native redirects. Expo Router 57+ static manifests keep the unresolved `[...slug]` template, so `loadBlogPostForRoute` must keep handling that literal build-time loader call.
- **`components/website/blogRoutes.js` owns every blog URL shape, the pagination arithmetic, the `SAFE_SLUG_SEGMENT` / `SAFE_CATEGORY_KEY` patterns and the `blogConfig.json` page size.** It is plain CommonJS because `scripts/generate-web-seo-files.js` runs outside the bundle and must read the router's rules. Never rebuild a `/blog/...` path by hand; `utils/__tests__/blogRoutes.test.ts` pins that generator and loaders agree. The page size is `BLOG_POSTS_PER_PAGE` from `blogConfig.json` — change it there only.
- **One component renders every listing page: `BlogListingPage.tsx`** (SEO + `CollectionPage` JSON-LD + `BlogPostListing`), with an optional `category`. `/blog` is a fixed route, so `WebsiteSeo` reads its title/description from `websiteRoutes.json`; a category supplies them from its translated label. Header and metadata copy both come from `useBlogListingCopy`.
- Post Markdown renders server-side with `markdown-it` (`html: false`) and `highlight.js`.
- **The index is `blog/index.web.tsx`, not `blog.web.tsx`.** Expo writes each loader payload as an extensionless file named after the route's context key, so a `blog` file and a `blog/` directory collide (`EISDIR`). Any `foo.tsx` + `foo/[x].tsx` pair that both export loaders has this problem.
- **`BlogPostShare.tsx` must pass `resetButtonStyle={false}` to every `react-share` button** — otherwise react-share's inline styles beat every Tailwind class and the buttons render as bare glyphs, with no type error. Icons are monochrome (`iconFillColor="currentColor"`) and take their brand color on hover via the `--share-color` custom property read by `.blog-share-button` in `global.css`. The shared URL comes from `absoluteUrl` in `websiteMetadata.ts` (no fourth copy of the site origin). Pinned by `components/website/__tests__/BlogPostShare.test.ts`.
- **Dev-only loader path needs `patches/expo-router+58.0.23.patch`**: `useLoaderData` passes the filesystem context key for grouped routes, so in development the client requested a path containing route groups; the patch strips `(group)` segments in development only (production keeps them). `utils/__tests__/expoRouterLoaderPatch.test.ts` pins it. Revalidate index/post navigation in both environments when upgrading Expo Router.
- **Diagrams are ` ```mermaid ` fences, drawn in the browser.** The server renders `<pre class="mermaid">` with the escaped source (readable without JS) and skips highlight.js; `BlogMermaid.tsx`, mounted by `blog/[...slug].web.tsx`, dynamically imports `mermaid` only when needed and draws with `securityLevel: 'strict'`. Colors come from the live `--c-*` custom properties, and a `MutationObserver` on `<html>`'s `style` redraws on theme change — do not hard-code a Mermaid theme.
- **`utils/blogPosts.server.ts` (and `mermaid`) are stubbed out of the native bundle in `metro.config.js`** (`blog-posts-server-stub.js`, `mermaid-stub.js`, resolved whenever `platform !== 'web'`, like `sharp`). expo-router's native `require.context` regex matches `.web.tsx` files, and Metro resolves `import()` statically, so the module's `node:fs/promises` import would otherwise fail the native bundle. The stub throws rather than returning empty posts. **Do not "fix" this with a `blogPosts.server.native.ts` sibling** — Jest's `node` project has `native` in `haste.platforms`, so it would hijack the real parser's tests. Any new web-only module importing Node built-ins needs the same treatment. Pinned by `utils/__tests__/blogPostsServerNativeStub.test.ts`.

## Tech Stack

- **Framework**: React Native (Expo SDK 58) with Expo Router
- **Android release optimization**: `app.json` enables both `enableMinifyInReleaseBuilds` and `enableShrinkResourcesInReleaseBuilds` through `expo-build-properties` (shrinking requires minification; keep both). `android/gradle.properties` is the generated mirror for builds that skip Prebuild; resync it through Prebuild whenever the Expo config changes.
- **EAS upload archives**: the committed `android/` and `ios/` source projects must stay in EAS uploads. `.easignore` excludes only generated build directories/caches, the exact `.git` entry (`.git/` alone does not remove the shallow clone EAS creates), tests, local tooling, `public/`, website-only posts and runtime-fetched exercise images. Validate with `eas build:inspect --platform android --stage archive`.
- **Node version**: EAS reads neither `.nvmrc` nor `engines`, so `eas.json`'s `base` profile pins an exact Node release and every build profile must `extend` it. Bump the Node major in `engines`, `.nvmrc`, `eas.json` and `.github/workflows/*` together (`utils/__tests__/easNodeVersion.test.ts` enforces it). Keep `cli.version` a major-only floor (`>= N.0.0`): the EAS builder's own `eas-cli` lags npm. See `FIXES.md`.
- **Styling**: NativeWind (Tailwind CSS). Do not downgrade `react-native-css-interop` below 0.2.7 (0.2.6 crashed native builds on a literal `box-shadow` in `global.css`); `utils/__tests__/nativewindBoxShadowPatch.test.ts` pins it.
- **Database**: WatermelonDB (SQLite for Native, LokiJS for Web)
- **Charts**: Victory Native (Skia) for Native, Victory (SVG) for Web
- **AI**: OpenAI & Google Gemini (Generative AI)
- **Localization**: i18next with `expo-localization`
- **Health Data**: Health Connect (Android) via `react-native-health-connect`; HealthKit on iOS via `@kingstinct/react-native-healthkit`. **Do not add `expo-health-connect` back**: both packages register the `expo.modules.healthconnect` namespace and release builds fail `:app:mergeDexRelease` with a duplicate `BuildConfig`. `react-native-health-connect`'s own `app.plugin.js` already writes the manifest entries.
- **Error Tracking**: Sentry (`@sentry/react-native`)
- **Food Scanning**: OCR (tesseract.js / rn-mlkit-ocr) and barcode scanning (quagga2 / react-zxing)
- **Camera**: all native camera work goes through `react-native-vision-camera` — the smart camera via the `components/CameraView.tsx` wrapper, video capture on `app/app/test/reps-recording.tsx` via `Camera` directly. **Do not add `expo-camera` (or any second CameraX-based library)**: a newer CameraX wins Gradle resolution and vision-camera crashes at boot with `NoClassDefFoundError`. Two `CameraView.tsx` props are load-bearing for shutter latency and must not be "optimized" away without re-verifying on a **release** build (`npm run build-android-apk-local` + `adb logcat`, filter `CameraView`/`CameraCaptureFlow`; dev builds never reproduced the 25s-shutter incident): `androidPreviewViewType="texture-view"` (the snapshot shutter needs a reliable `getBitmap`; SurfaceView/PixelCopy silently reroutes into the slow takePhoto fallback) and `photoQualityBalance="speed"` (never `"balanced"`, which is CameraX ZSL and stalls for tens of seconds on some devices). Slow or fallback shots surface as Sentry `camera-shutter-*`/`camera-warm-up-*` events.
- **VisionCamera is stubbed on web** in `metro.config.js` (`vision-camera-web-stub.js`): the package throws at module evaluation, and expo-router's `require.context` can reach native-only `.tsx` siblings of `.web.tsx` files. Web camera UI lives in `CameraView.web.tsx` and `.web` route stubs; never import vision-camera from a web-reachable module expecting it to work.
- **Every capture is cropped; barcode scanning has no shutter.** Both entry points of `useCameraCaptureFlow` (shutter and gallery pick) end in `cropAndProcess`, so `process` only receives a cropped image. There is deliberately no "skip the crop" flag (do not reintroduce `cropOnShutter`). Whether a shutter exists is the owner's call: pass or omit `SmartCameraShell`'s `onShutterPress` (`SmartCameraModal` passes `undefined` while `isBarcodeScanning`; `BarcodeCameraModal` never passes one) — the shell must not decide from `cameraMode`. `patches/@bsky.app+expo-image-crop-tool+0.5.1.patch` moves `openCropperAsync` to `Queues.MAIN`; keep it as defense in depth.
- **SecureStore must not block Expo's single module queue (critical).** Every Expo `AsyncFunction`/`Coroutine` on the default queue shares ONE thread (`expo.modules.AsyncFunctionQueue`). `expo-secure-store`'s Android `getValueWithKeyAsync`/`setValueWithKeyAsync` did their Keystore work directly on it, so a cold first access at boot head-of-line-blocked `openCropperAsync` and `launchImageLibraryAsync` — the first gallery pick after boot stalled ~25s (release builds only; Pixel 10 / Android 17). **Fix**: `patches/expo-secure-store+58.0.2.patch` moves those ops onto a dedicated serial queue (`Dispatchers.IO.limitedParallelism(1)`). SecureStore ships as a prebuilt AAR, so the patched `.kt` is ignored unless `package.json` keeps `expo.autolinking.android.buildFromSource: ["expo-secure-store"]` — both pieces are load-bearing; revalidate on every Expo/SecureStore upgrade. Related: `getEncryptionKey()` (`utils/encryption.ts`) coalesces concurrent reads per key (also fixing a fresh-install race that could persist mismatched keys), and `SettingsService.migrateApiKeysToEncrypted` is a `runOnce` boot migration. Do not reintroduce eager duplicate SecureStore reads at startup. Verify with a release build and the `gallery picker` phase timing in `CameraCaptureFlow` logs.
- **Gallery pick uses the system Photo Picker, no permission prompt — one shared entry point.** `utils/galleryImagePicker.ts` exports `pickImageFromGallery` (`ImagePicker.launchImageLibraryAsync` with no `legacy` flag; Android `ACTION_PICK_IMAGES` / iOS `PHPicker` need **no** media-library permission, so never add `requestMediaLibraryPermissionsAsync` back) and `pickAndCropImageFromGallery` (pick + `openCropperAsync` from `utils/file.ts`; `null` if either is cancelled). `legacy: true` was a failed workaround for the stall above and must not return. There is deliberately no `.web.ts` counterpart (expo-image-picker already handles web). **The pick runs at `quality: 1` and takes no quality argument**: every caller re-encodes through `openCropperAsync`, and compressing twice stacks a second lossy pass; the crop step alone chooses output quality (`pickAndCropImageFromGallery(compressImageQuality)`, `useCameraCaptureFlow`'s `quality`), which matters most for OCR/barcode legibility. `CoachModal`, `CreateMealModal`, `CreateCustomFoodModal` and `CreateExerciseModal` call `pickAndCropImageFromGallery`; `useCameraCaptureFlow` calls the two steps separately for per-step timing logs. Never call `ImagePicker.launchImageLibraryAsync` from a new call site.
- **Export**: xlsx + html-to-image for data export. `expo-print` renders the cycle appointment summary to a PDF (print dialog on web); it is native, so adding or upgrading it needs `npm run prebuild` (and `pod install` on iOS).
- **JSX transform**: SDK 58 uses Expo's resolved Babel JSX transform; the old `@babel/plugin-transform-react-jsx` pin is removed. Keep NativeWind, Reanimated and WatermelonDB decorator transforms in the existing Babel configuration.
- **SDK 58 file I/O**: BLE file serialization uses `writeSync` and `readBytesSync` to preserve ordering and complete JSON before sharing (`write` and `FileHandle.readBytes` now return promises); do not replace synchronous calls with un-awaited asynchronous ones. React Native refs use `ViewInstance`, `ScrollViewInstance`, `TextInputInstance`.
- **SDK 58 native compilation** also requires `patches/@nozbe+watermelondb+0.28.0.patch` (Android BuildConfig generation under AGP 9; an iOS `WMDatabaseJSIBridge` TurboModule installing the SQLite JSI bindings, with the legacy `RCTCxxBridge` installer guarded when its header is absent). The adapter and database format are unchanged; remove only once upstream ships equivalent support.
- **Widget versioning**: regenerate native projects after release bumps so the widget extension's Info.plist and Xcode version/build settings match the app; run `check-version-sync` after prebuild.

## Coding Guidelines

### Architecture

- **Blank lines after blocks/functions**: ESLint's autofixable `padding-line-between-statements` requires an empty line before the next statement after a block-like statement, an `if`, or a function declaration. It does not pad inside `if`/`else` chains or before a closing brace. Run `npm run lint:eslint-fix`. (Core rule in pinned ESLint 9; migrate to ESLint Stylistic before ESLint 11.)
- **No barrel files or re-export-only wrappers**: import implementations from their owning files. No `index.ts` aggregators, no files that only re-export, no platform wrappers that merely alias a shared component — unless an external package or framework requires that exact entry point (document it in the file). Mock services by their own path in tests (`jest.mock('@/database/services', …)` now mocks nothing). Generate ids with `randomUUID` from `expo-crypto`, never a hand-rolled `Math.random()` v4.
- **Keep documentation in sync (required)**: when a change alters behavior, architecture, file layout or an invariant, update the relevant root document in the same change: `AGENTS.md` (implementation rules), `CURRENT_FEATURES.md` / `FUTURE_FEATURES.md` (product status), `DESIGN.md` (UI standards), `FIXES.md` (incidents and workarounds), `RESEARCH.md` (durable rationale), `README.md` (project-level usage). A stale filename, function, flag or approach is a bug. Do not create another Markdown plan or one-off report. Exception: `doc/redesign/` holds the active de-slop plan (`DESLOP_PLAN.md`) and audit baseline (`design-baseline.json`) — work a phase from there, mark its findings `fixed` in the baseline in the same change, and fold the resulting rules into `DESIGN.md`. Any user-facing feature added, removed or significantly changed also updates `CURRENT_FEATURES.md` (and `README.md` if the curated overview is affected).
- **Tests are required for every behavior change**: add or update automated tests so they would catch the bug or regression, and run the relevant suite plus type checking and any applicable lint/translation checks before calling the work done. Never weaken, delete or skip a valid test to make a change pass.
- **Layered structure**: Schema (`database/schema.ts`) → Models (`database/models/`) → Repositories (`database/repositories/`, for complex/non-trivial reads) → Services (`database/services/`). Non-database services (AI, notifications, Health Connect sync) live in top-level `services/`. Models must be registered in `database/database-instance.ts`.
- **Calendar day keys**: fields representing a calendar day (`user_metrics.date`, diary pickers) store **local** midnight ms via `utils/calendarDate.ts` (`localDayStartMs`, `localDayHalfOpenRange`, …); never `Date.UTC` or `setUTCHours(0, …)` for those.
- **`nutrition_logs.date` is a consumed datetime**, not a day key: local day + time-of-day in ms. Calendar-day grouping goes through `utcNormalizedDayKey` / `dayKeyRange` (with `dayRangeClauses` from `database/dayKeyQuery.ts` for the widened DB clauses and `range.filterRecords` to trim the overscan), which re-apply the stored `timezone` offset. When writing it, combine day + time with `combineLocalDateAndTime` (or `instantForDateTimeInTimezone` to anchor to a record's stored timezone); use `withCurrentTimeOnDay` for non-interactive "log now for this day". Never floor it with `localDayStartMs`. `created_at` is strictly record creation and `updated_at` the last update — don't read consumed time from them.
- **Encryption**: sensitive metrics (weight, body fat) and nutrition logs use the helpers in `database/encryptionHelpers.ts`.
- **Every decrypt is expensive — count them on any path that reads a range of logs.** Each value is its own `CryptoJS.AES.decrypt` (an MD5 key derivation dominates), synchronously on the JS thread. Decrypt only the fields a path reads (`NutritionLog.getNutrients()` never decrypts the food name and decrypts each macro once — don't reintroduce a `hasSnapshot()` + `getDecryptedSnapshot()` pair); share concurrent reads of the same window (`getLatestHistoricalNutritionWindow` does, in flight only); and never add a boot task that decrypts every row on each launch — make it `runOnce`, or select rows on a plaintext column.
- **Food quality badges (Nutri-Score / Eco-Score / NOVA / labels)**: never inline a provider's field names. Each source normalizes into `FoodDisplayQuality` (`utils/foodDisplayQuality.ts`) once, at its own mapper (`getOffDisplayQuality` in `utils/openFoodFactsMapper.ts`, `getMusclogDisplayQuality` in `utils/musclogProduct.ts`); UI reads them through `getExternalProductDisplayQuality(source, details)` (`utils/externalFoodProduct.ts`) with a source already resolved by `inferBarcodeNutritionSource`/`resolveExternalFoodSource`. `foodRecordDisplayQuality` reads badges off a stored food; `applyDisplayQualityToFoodRecord` writes them on save. USDA resolves to `undefined`.
- **Unit system (metric / imperial)**: the database **always** stores metric (kg, cm, g, kcal); users choose in settings (`SettingsService.getUnits()`). Use `utils/unitConversion.ts`: `displayToKg`/`displayToCm`/`displayToGrams`/`displayValueToMetric(value, metricType, units)` when saving; `kgToDisplay`/`cmToDisplay`/`gramsToDisplay`/`metricValueToDisplay` when reading; `getWeightUnit`/`getHeightUnit`/`getMassUnitLabel`/`metricDisplayUnit` for labels (never hardcode "kg", "lbs", "g", "oz"); `isWeightMetricType` (weight, muscle_mass, lean_body_mass) and `isLengthMetricType` (height, chest, waist, hips, arms, thighs, calves, neck, shoulders) to classify. Macros, kcal, body fat, BMI and FFMI need no conversion. Food serving weights are grams displayed as g or oz (`ServingSizeSelector` handles it). **Every new feature that shows or accepts weight, height, body measurements or serving sizes must use these helpers and be tested in imperial mode.**
- **Carbs vs fiber convention (critical)** — two conventions exist; do not mix them:
  - **Food items / nutrition logs** (`NutritionLog`, `inferCaloriesFromMacros.ts`, `NutritionCharts.tsx`, food DB mappers): `carbs` = total carbohydrates **including** fiber (US label standard). Digestible carbs = `carbs − fiber`; use `digestibleCarbs(carbs, fiber)` from `utils/carbsConvention.ts` (never re-inline `Math.max(0, carbs - fiber)`) for energy and for comparing consumed carbs against the (net) carbs goal, so the carbs bar doesn't double-count fiber's own bar.
  - **The "total incl. fiber" invariant is established at ingestion.** Every food-source mapper must run `carbs` through `totalCarbsForFoodSource(source, …)` before storing (`FOOD_SOURCE_CARBS_CONVENTION` holds each source's convention; a change is a one-line edit):
    - **USDA** (`Carbohydrate, by difference`, 1005) and **US/Canada FDA** labels already include fiber → `'total'`.
    - **EU (Reg. 1169/2011)** declares _available_ carbohydrate (fiber excluded) → `'net'` (total = carbs + fiber).
    - **OpenFoodFacts** stores one `carbohydrates` field with no recorded convention → `'off-mixed'`: (1) prefer `carbohydrates-total`; (2) else reconcile the **stated label energy** against both interpretations (they differ by `4 × fiber` kcal/100g) and keep `carbs` only when the energy clearly fits the total interpretation; (3) else assume EU/net and add fiber. Step 2 is conservative — pass the raw stated kcal, never an inferred one.
    - **Musclog REST API** scrapes Dutch supermarkets ("Koolhydraten" = available carbs) → `'net'`; update the `musclog` entry if its upstream changes.
    - **AI / LLM estimates** → `'net'` (the macro prompt's `kcal = 4·carbs + 2·fiber` note, `utils/prompts.ts`). Every AI persistence path (`NutritionService.logCustomMeal`/`logCustomMealsBatch`, `nutritionAI.ts`, `MyMealsModal`) must run AI carbs through `totalCarbsForFoodSource('ai', …)`.
    - **Manual entry** (`CreateCustomFoodModal`): the `INCLUDE_FIBER_IN_CARBS_SETTING_TYPE` setting (Advanced → Nutrition; seeded from units in `prod.ts`: imperial = include fiber, metric = exclude) says whether typed carbs already include fiber. Convert with `totalCarbsFromSource(manualEntryCarbsConvention(includeFiberInCarbs), …)`; the field label and hint follow the same setting.
  - **Protein is never a share of calories when a weight is known** (`calculateMacros`, `utils/nutritionCalculator.ts`). With body fat opted in, weight_loss/hypertrophy use g/kg FFM; otherwise protein is `PROTEIN_G_PER_KG_BODYWEIGHT` (weight_loss 2.0, hypertrophy/strength 1.8, general 1.6, endurance 1.4; at least 2.0 in any deficit) × `proteinReferenceWeightKg` — the goal weight when set, else current weight capped at a BMI-30 reference for the user's height. When the anchor doesn't fit the calorie budget, `splitAroundProtein` caps protein at `MAX_PROTEIN_CALORIE_SHARE` (75%) and sets `MacroSplit.proteinLimited`; it reserves `MIN_FAT_CALORIE_SHARE` (15%) for fat first. Every caller passes `heightCm`, `goalWeightKg` and `weightGoal`; only a caller with no weight gets the percentage split. The three shares add up to 100 (fats take the rounding remainder).
  - **User nutrition goals** (`NutritionGoalsBody`, saved goals, onboarding results): `carbs` = **net/digestible carbs only**; fiber is a separate additive macro. Total calories = `protein * 4 + carbs * 4 + fats * 9 + fiber * 2`. Never subtract fiber from carbs here.
- **Workout-set lifecycle is independent from RPE**: `workout_log_sets.completion_status` (`planned` | `performed` | `skipped`) is the sole runtime source of truth; `difficulty_level` is an optional 1–10 effort rating and must never be fabricated to make a set count as performed. Progress counts performed + skipped as resolved; volume, analytics, history summaries, PRs and progression use performed sets only. Every new set writer assigns a status explicitly. The nullable schema column and legacy `is_skipped` exist only for upgrade compatibility (native v26 SQL, the run-once web `WorkoutSetStatusMigration`, and `restoreDatabase` for pre-v26 backups); current-format imports pass the strict schema unchanged, and runtime readers never infer lifecycle from RPE or repair rows on access. Code that needs plain set data uses the single `_raw` boundary in `database/workoutLogSetSnapshot.ts`.
- **`loadMultiplier` is a bodyweight-relative load benchmark, not an intensity knob**: the load a trained lifter typically uses on that exercise as a multiple of bodyweight, measured as the app logs it (per hand for dumbbells). Anchors are the frozen entries in `data/legacyExercisesData.json` (Deadlift 1.8, Squat 1.4, Bench Press 1.0, Chest Press Machine 0.9, Lat Pulldown 0.7, Overhead Press 0.6, Barbell Curl 0.42, Leg Press 3.5, Lateral Raise 0.10), mapped by `scripts/exercise-load-multiplier-anchors.js`; family rules are in `scripts/exercise-load-multiplier-policy.js`. Consumers: `utils/workoutEnergyCalculator.ts` (scales mechanical work) and `utils/exerciseGoalProjection.ts` (`estimated1RM / (bodyWeight * loadMultiplier * genderFactor)`, advanced above 1.5).
  - **Derive a new value from the closest movement already in the catalogue, never from the equipment type.** A cable variant takes its anchor's value outright; the only discounts are for real biomechanical differences — unsupported stance (`x0.75`) and unilateral loading (`x0.55`). "It's a cable" and "the stack caps lower" are not reasons (the logged weight is already in every formula). `data/__tests__/exercisesData.test.ts` pins the parity ratios, so a category-wide clamp fails the build.
  - **For a bodyweight exercise the multiplier is the fraction of body mass the movement shifts**, derived from [de Leva (1996)](<https://doi.org/10.1016/0021-9290(95)00178-6>) segment masses (pull-up `1 - 2 x 0.0061 = 0.99`, hanging leg raise `0.41`, quadruped glute kickback `0.20`); the push-up family is `0.70` from [Suprak et al. (2011)](https://pubmed.ncbi.nlm.nih.gov/20179649/) force-plate data. Don't add per-user anthropometrics (body mass and height cancel; sex moves fractions 0.1–6%, under the model's noise). Store sex-neutral values.
  - **A stored `0` means "no displacement to credit" (isometric holds, cardio, stretching, mobility) and must stay a hard zero.** Don't coerce it to `1` in the calculator (a plank would score as a full-bodyweight rep); fix it in the data. `utils/exerciseGoalProjection.ts` is the exception and guards its divisor, since `0` would yield `Infinity` (`?? 1.0` doesn't catch a stored `0`).
- **`muscle_group` holds two vocabularies and readers must handle both**: the bundled catalogue and `CreateExerciseModal` write coarse names (`legs`, `arms`, `core`, `abdomen`, …), while exercises migrated from the legacy database carry fine-grained ones (`quads`, `biceps`, `abs`, …). The `MuscleGroup` union in `database/models/Exercise.ts` enumerates both. **Never match group names yourself** — use `muscleGroupFamily(group)` / `MUSCLE_GROUP_FAMILY` (`database/models/muscleGroupFamily.ts`, WatermelonDB-free so pure code can import it). A hand-written `Set<MuscleGroup>` naming one vocabulary fails silently (`LEG_GROUPS` in `workoutEnergyCalculator` once missed all 60 bundled leg exercises). `MUSCLE_GROUP_FAMILY` is a `Record<MuscleGroup, …>`, so widening the union fails the build until each name's family is declared.
- **The bundled catalogue is the 873-entry free-exercise-db import** (CC0): `data/exercisesData.json` (structure) + `data/exercisesEnUS.json` (English copy), generated by `scripts/generate-exercises-data.js` using `scripts/exercise-catalogue-mapping.js`, `exercise-load-multiplier-anchors.js` and `exercise-load-multiplier-policy.js`. `scripts/exercise-popularity-policy.js` owns the exactly 100 stable slugs selected from usage rankings; the generator emits `isPopular: true` only for those rows (never `false`). Keep that slug-based — don't infer popularity from the alphabetical `exerciseIndex` or fan one generic ranked movement out across local variants. `isPopular` is structural metadata and not persisted. `data/exercises{EsEs,NlNl,PtBr,RuRu}.json` are generated by `scripts/generate-exercise-locales.js` — edit the generators, not the JSON. After regenerating upstream data, immediately run `npm run generate-exercise-locales` and `npm run generate-lang`. Localized copy joins structural data through stable `exerciseSlug`; `exerciseIndex` is only 1-based display order. Every database id is `fx-<__freeExerciseDbId>` from `appExerciseId`, and bundled workout definitions name `exerciseSlug` directly — never derive either from position. `AppExerciseCatalogueService.sync` owns the database projection (structural fields plus the exact active target-muscle link set) before `LegacyExerciseCatalogueMigration` may retire old rows. The legacy 256-entry catalogue (`data/legacyExercisesData.json`) is only for historical migration v18, multiplier anchors and the Game Boy generator; never point runtime seeding or the Game Boy table at the wrong catalogue.
- **Exercise photos follow the catalogue slug**: `scripts/generate-exercise-images.js` writes 512px q65 WebP frames to `public/images/exercises/<slug>/{0,1}.webp`; `buildExerciseImagePath` and `buildExerciseCloudUrl` (`utils/exerciseImage.ts`) are the path/URL sources of truth. Website renderers combine the relative path with `EXPO_BASE_URL` through `withExpoBaseUrl`. Because every filename is `0.webp`/`1.webp`, `exerciseImageCacheKey` must include the slug (`<slug>__0.webp`). Retired illustrations live under `public/images/exercises/legacy/exercise<N>.webp` only for user-owned clones created at cutover. See `FIXES.md`.
- **Translation**: check `lang/`. Every new feature uses translation keys and adds them to all locales. Bundled workout definitions are `data/workoutTemplatesData.json`; copy is in `data/workoutTemplates{EnUS,EsEs,NlNl,PtBr,RuRu}.json`. `scripts/generateLangFile.js` generates `WORKOUT_TEMPLATE_COPIES_BY_LOCALE` in `lang/lang.ts`; `data/workoutTemplates.ts` merges the active locale's copy by array index (falling back to `DEFAULT_LANG`), so every copy file must preserve the definition file's order. Template difficulty is structural (`beginner` | `intermediate` | `advanced`), not in locale files; UI translates the identifier. `__title` in the definition file is a maintainer aid, typed on `RawWorkoutTemplateDefinition` only and stripped by `applyWorkoutTemplateCopies` — don't rename it to `title` or read it.
- **User-visible numbers**: format with `Intl` via `hooks/useFormatAppNumber.ts` (components) or `utils/formatAppNumber.ts` (pure code), using locale `i18n.resolvedLanguage ?? i18n.language`. No `toFixed`, raw `{n}` in JSX, or `toLocaleString()` without an explicit locale for display. Keep `roundToDecimalPlaces` / DB math separate from display.

### WatermelonDB Usage

- **Transactions**: all writes go in `database.write(async () => { ... })`. On web, `unsafeResetDatabase()` must also be in a write block.
- **Avoid deadlocks**: never nest `database.write()`. `@writer` model methods must not be called from inside another write block — reach them through `writer.callWriter(() => record.someWriter())` (or `this.callWriter(...)` from a `@writer` model method), which joins the open transaction.
- **Every soft-deletable model overrides `markAsDeleted` with `@writer`** — never inherit WatermelonDB's. This app soft-deletes by stamping `deleted_at`; the base `Model.markAsDeleted` tombstones for Sync (`_status = 'deleted'`, `deleted_at` untouched) and isn't a `@writer`. Without the override it throws through `callWriter`, silently hides the row from WatermelonDB queries while raw SQL and exports still see it, or throws outside a write block (2.10.5 shipped `WorkoutLog` without it: every delete threw after tombstoning, orphaning exercises and sets). `database/models/__tests__/markAsDeleted.test.ts` pins every table with a `deleted_at` column. Cascades belong in the owning service (`WorkoutService.deleteWorkoutLog`, `WorkoutTemplateService.deleteTemplate`), not the override — `WorkoutPlan` is the one exception and cascades only to its own junction rows. Code that must retire rows in the SAME `database.batch` as their replacements uses `prepareSoftDelete(record, now)` (`database/prepareSoftDelete.ts`) instead of hand-stamping.
- **Read-then-write must be atomic (no TOCTOU)**: when a write depends on a prior read ("insert only rows that don't exist", "seed if missing"), do the read **inside the same `database.write()`**. An outside read is fine only as a best-effort early-out, with the authoritative check repeated inside (the old exercise seeder's outside read caused `UNIQUE constraint failed: exercises.id` in builds 270/272). `AppExerciseCatalogueService.sync` reconciles rows and links in one writer (`database/services/__tests__/exerciseCatalogueServices.test.ts`).
- **A migration and `schema.ts` must declare the same columns, and new measurement columns name their metric unit**: `database/__tests__/migrationSchemaParity.test.ts` diffs them (type, optionality, index), requires every column of a migration-created table to come from a migration, and requires every number column added from v27 on whose name mentions a weight or distance to end in `_kg`, `_g`, `_m` or `_cm`. Its `KNOWN_SHIPPED_DRIFT` lists five v8/v10/v16 columns whose shipped migration disagrees with the schema (a shipped migration can't be edited; fixing them needs a raw-SQL migration, which triggers the pre-migration snapshot and is ignored on web) — never add to that list. Derived columns that a JS boot task fills (`exercises.search_text`) must be selected with a clause matching on both adapters: LokiJS's add-columns step sets existing records' column to `null`, and Loki `eq(null)` also matches a missing property (`database/__tests__/exerciseSearchTextWebMigration.test.ts`).
- **Never pass an unbounded id list to `Q.oneOf` — batch through `database/queryByIds.ts`.** SQLite caps bound parameters per statement. `fetchByIds(table, column, ids, ...clauses)` / `fetchMapByIds(...)` chunk at `MAX_QUERY_IDS` (300), dedupe ids and apply extra clauses to every chunk; `MAX_BATCH_OPERATIONS` (500) sizes `database.batch`. Push soft-delete filtering into the query (`Q.where('deleted_at', Q.eq(null))`). `NutritionService.fetchLiveFoodsByIds` is the nutrition-side wrapper — don't inline another "query foods by id, build a Map, skip deleted". Pinned by `database/__tests__/queryByIds.test.ts`.
- **JSON fields**: use `@json` (e.g. `@json('micros_json')`, `@json('week_days_json')`). Keep a plaintext date field beside encrypted fields when the date is needed for queries.
- **Raw SQL — never open expo-sqlite on `musclog.db` (critical, data loss)**: expo-sqlite and WatermelonDB bundle separate SQLite libraries and POSIX locks don't conflict in-process, so a closing expo-sqlite connection unlinks the live `-wal`/`-shm` files; WatermelonDB keeps committing into the unlinked file and everything since silently vanishes on process kill (June 2026: users lost nutrition logs). Raw SQL while the app runs goes through `rawQueryViaWatermelon` (`database/wmdbRaw.ts`, reads/PRAGMAs) or `database.adapter.unsafeExecute` (writes). The only exception is `preparePreMigrationBackupBeforeAdapter()` in `database/preMigrationCapture.ts` (native-only, imported solely by `database/adapter.ts` before `new SQLiteAdapter`): it reads `user_version` and, **only when a data-touching migration is pending** (`pendingMigrationsCanTouchExistingData`, `database/migrationSafety.ts`; additive-only migrations skip it), writes a `.db` snapshot with **`VACUUM INTO`**, closes the raw connection and lets WatermelonDB open the file. `database/preMigrationBackup.ts` registers that snapshot plus an AsyncStorage sidecar; `database/sqliteBackupConvert.ts` converts the snapshot to the portable JSON export **lazily** (on restore/download), opening the _copy_ and injecting the sidecar. A **different** db file (the snapshot, legacy `workoutLoggerDatabase.db`) may be opened with expo-sqlite; the hazard is the _live_ `musclog.db`. Don't open it during migration callbacks, after boot, or from new paths. Read the `FIXES.md` write-up before adding raw SQLite access.
- **Boot-time DB-ready gate**: `seedProductionData()` calls `unsafeResetDatabase()` on a fresh install, temporarily swapping in an `ErrorAdapter` that throws on any query. Startup code that touches the DB (e.g. in `AppBoot.tsx`) must `await waitForDbReady()` (`database/dbReady.ts`); `seedProductionData()` calls `markDbReady()` when done. Conversely, any `unsafeResetDatabase()` outside seeding (restore, clear data) must first `await waitForBootMigrations()`, because the migration chain starts right after `markDbReady()` (see `FIXES.md`).
- **On web, `AsyncStorage` IS `window.localStorage` — never call `AsyncStorage.clear()`**: it wipes the whole origin, including stored web recovery points (`musclog_backup_data_*`), the backup index and the schema-version marker. Every wipe path uses `database/asyncStorageReset.ts`: `clearAppAsyncStorage(preserved)` and `replaceAppAsyncStorage(pairs, preserved)` skip `isWebBackupStorageKey`. `clearAllAppData()` is the one deliberate exception. **`isWebBackupStorageKey` is also the export filter** (`captureAsyncStorageDump`) — payloads AND bookkeeping — so any new path enumerating AsyncStorage uses that predicate. Pinned by `database/__tests__/asyncStorageBackupExclusions.test.ts`.
- **A restore swaps AsyncStorage over at the end, and writes before it prunes**: clearing it first left `onboardingCompleted`, `seeding_complete` and `currentUserSyncId` missing for the whole restore, so a mid-restore failure got wiped and reseeded on next boot, and `createPreRestoreBackup()` captured an empty `_async_storage_`. Keep the swap after the database is populated and keep `replaceAppAsyncStorage`'s write-then-prune order (`database/__tests__/importDbAsyncStorageOrder.test.ts`).
- **Musclog 1.x has ONE conversion, `MigrationService`, for both the on-device database and a 1.x JSON backup.** A 1.x export is `{ "<old SQLite table>": rows[] }` with no `_exportVersion` (`isLegacyV1Dump`, `utils/legacyV1Backup.ts`), so `restoreDatabase()` hands it to `restoreLegacyV1Database` (`database/legacyV1Import.ts`) before 2.0 validation. That loads the rows into an **in-memory** expo-sqlite database (`:memory:`, never a file) as untyped columns, then resets and seeds via `seedDatabaseContents` (`database/seeders/prod.ts`) with a `MigrationService` built on that source. Keep: load with `withTransactionAsync`, never `withExclusiveTransactionAsync` (a second connection to `:memory:` is an empty database); build the source BEFORE the reset so a bad file fails with current data intact; pass `valuesEncrypted: false` (both 1.x export paths wrote `UserMetrics`/`UserNutrition` plaintext). Every 1.x table `MigrationService` reads is created even when the backup lacks it, with the columns its SQL filters/joins on — a new query naming another column adds it to `REQUIRED_COLUMNS`. Web has no SQLite (`legacyV1Import.web.ts` refuses before anything is wiped). Pinned by `utils/__tests__/legacyV1Backup.test.ts`, `database/__tests__/legacyV1Import.test.ts`, `database/services/__tests__/MigrationServiceLegacyJson.test.ts`.
  - **A 1.x session's sets are in `WorkoutEvent.exerciseData` (JSON `[{ exerciseId, sets }]`), never the `Set` table** (`Set.workoutId` points at the template; 1.x ids start at 1 in both tables, so reading by event id lost ~70% of sets). `scheduled`/`upcoming` events are placeholders and skipped unless they hold sets (`isPerformedWorkoutEvent`); an unmatched nutrition log gets its own food rather than being dropped; plain-text `Chat` rows become `chat_messages`.
  - A converted log's `template_id` is the NEW template id (via `workoutIdToTemplateId`). Its `calories_burned` is filled after the sets exist by `estimateMigratedWorkoutCalories` through `WorkoutService.estimateWorkoutKcal` (1.x stored none), using `loadWorkoutEnergyProfile()` (`database/services/workoutEnergyProfile.ts`) read ONCE per migration and a single `commitPrepared` batch; the arithmetic is the pure `estimateWorkoutKcalFromSets` (`utils/workoutKcalEstimate.ts`). Logs converted before the id fix hold the old numeric id; the run-once `LegacyWorkoutTemplateIdRepair` repoints each orphan (template_id naming no row, deleted included) at the one live template with its workout name, and leaves it alone if several share the name. Hence "sessions of a workout" is a plain `template_id` match everywhere — never add a name-matching fallback to a read.
- **Web recovery points are database dumps, so payloads live in IndexedDB, not localStorage**: `database/webBackupPayloadStore.ts` owns them; only the small metadata index stays in localStorage (an origin's ~5 MB is less than one ordinary export, so `createPreExerciseCatalogueBackup()` failed on every boot and the catalogue cutover could never run on web). Reads still fall back to legacy `musclog_backup_data_*` keys and deletes clear both — keep that fallback.

### Component Design

- **Theme**: use components from `components/theme/` and follow `theme.ts`. Preferences are named palette IDs (`kinetic-depth`, `kinetic-light`, `kinetic-shock`, `kinetic-volt`, `kinetic-blush`) plus `system`; never reduce the stored preference to a boolean. `theme.registry.js` is the canonical catalogue (every ID, mode and primitive palette); `ThemeId`, semantic token trees, CSS/native variables and `THEMES` derive from it. Add a palette there, then run `npm run check-palette`. `DEFAULT_THEME_BY_MODE` is the single answer to "system says light, now what?" — don't spell those IDs elsewhere. `themeMode` is the derived light/dark value for status bars and `dark:` variants. **A new theme is not complete until it is also on the public website (showcase asset/coverage) and in the Game Boy game (`npm run gb:gen-themes`)**; keep identity and palette intent identical across all three.
  - A theme carries no component-level presentation flags: express anything a component would branch on as palette values (a theme wanting a flat summary card sets flat gradient stops). `ThemeProvider` resolves the preference once and every `useTheme*` hook selects from that context. First paint reads the preference from a mirror — the settings mirror on native, `utils/themeMirror` (`localStorage`, replayed as CSS variables by `+html.tsx`) on web. A surface that must pin a palette (the camera viewfinder) wraps in `ThemeScope`; don't create another forced-theme context or read `darkTheme`/`lightTheme` from a component.
  - **Theme app icons**: `npm run generate-theme-icon-backgrounds` applies the palette to the alpha silhouette in `assets/icon-bg-color.png`, composites `assets/icon-bg-glass-effect.png` then `assets/icon-bg-text.png`, and writes `assets/theme-icons/icon-bg-<theme-id>.png` plus an opaque copy in `assets/theme-icons/opaque/` flattened onto `surfaceBase` (iOS rejects transparent icons). Expo's configured icon is the default dark theme's output; the generator doesn't edit `app.json`.
  - **Picking a theme also switches the launcher icon.** Every rule lives in `constants/themeAppIcons.js` (CommonJS, read by the config plugin): the default dark theme is the default icon, every other theme an alternate named by its PascalCase id, and `system` keeps the default icon (the OS can flip light/dark while the app isn't running). `plugins/withThemeAppIcons.js` compiles the alternates (iOS `AppIcon<Name>.appiconset`s + `ASSETCATALOG_COMPILER_ALTERNATE_APPICON_NAMES`; Android adaptive icons + one `.LauncherIcon<Name>` `activity-alias` each, `.LauncherIconDefault` the only one enabled); `modules/theme-app-icon` switches them. `services/themeAppIcon.ts` `syncAppIconWithTheme` is called ONLY from the manual pick in `VisualSettingsModal` (iOS alerts on every switch — never on boot, restore or no-op). **MainActivity is never disabled and has no MAIN/LAUNCHER filter** (it owns the `com.werules.logger://` filter the widgets use and the Health Connect rationale filter — which is why `expo-alternate-app-icons` wasn't used); only aliases toggle, the new one enabled before the old is disabled. **Android applies the switch when the app is next backgrounded** (launchers close the task or drop the shortcut otherwise). **Adding a theme needs `npm run prebuild`** or `setAppIcon` rejects. Pinned by `constants/__tests__/themeAppIcons.test.ts`, `plugins/__tests__/withThemeAppIcons.test.ts`, `services/__tests__/themeAppIcon.test.ts`.
- **Geometry and type are rules** (`DESIGN.md` → Typography; Spacing, shape, and touch). Radii come from `theme.shape.js` (`tag` 4, `inner` 6, `control` 8, `card` 12, `sheet` 16), read by `tailwind.config.js` and `theme.ts`; write `rounded-tag|inner|control|card|sheet|full`, never Tailwind's rem-based size-named radii (native rem 14 vs web 16). Text stops at bold, small text (`xs`–`base`) at semibold, no negative tracking, `tabular-nums` for changing or aligned numbers. Buttons are flat and sized from `components/theme/buttonMetrics.ts` (shared by `Button.tsx` and `Button.web.tsx`); cards carry no shadow. `components/__tests__/deslopGuards.test.ts` (Phase 10) holds each rule at zero.
- **A screen's header is `ScreenHeader`** (`components/theme/ScreenHeader.tsx`) — never a hand-rolled title/back arrow or a native stack header (`headerShown: true`). Place it inside `MasterLayout`, above the scroll view. Pass `destination` (a `NavItemKey`) when the screen shows the bottom bar: the header is `root` while that destination is one of the user's slots and `pushed` (with back) otherwise (`resolveScreenHeaderForm`) — slots are user-configurable, so never hard-code it. Put it **outside** the screen's `AreaLockGate` with a matching `lockArea`, so back works behind a lock while subtitle and actions are hidden. `deslopGuards.test.ts` (Phase 8) lists the screens on it; add new top-level screens there.
- **Controls come from `components/theme/`**: `Button`, `TextButton`, `IconButton`, `Chip`, `ListRow`, `SegmentedControl` (full width or `pill` — never both on one screen; `pill` is the inline toggle and, with `fullWidth`, the form for a secondary preference in a settings list), `NumericTextField` (a typed number held as the user's own string; empty = no value). `DESIGN.md` → Buttons maps each control kind. Don't hand-roll a pill, round icon button or text link with `Pressable` + classes; add a variant to the theme component. **Never give a centered `TextInput` a native `placeholder`** (on Android the caret sits at the far edge of an empty field) — `NumericTextField` draws the placeholder as an overlay and hides it while focused. Pinned by `components/__tests__/themeControls.test.ts`. Use `SegmentedControl` for mode switching (7D/30D/90D).
- **A plain stored setting is a `SettingDefinition`**, not a get/set pair: `SETTINGS` (`constants/settingDefinitions.ts`) names each setting's key, default, `parse` and `serialize` once; `SettingsService.get(SETTINGS.x)` / `set(…)` / `resetToDefaults([...])` and `SettingsContext` (`readSetting(map, …)`, `DEFAULT_STATE` from `defaultValue`) read through it. Add a simple setting as one definition; keep a dedicated method only for real behavior beyond the stored string (asymmetric shape like `getHomeActions`/`setHomeActions`, merging like `updateNotificationPreferences`, encryption). `serialize` may throw to refuse a never-storable value (`reviewWeekday`). Tests stub settings with `settingsGetMock({ … })` (`database/services/__tests__/settingsGetMock.ts`).
- **Settings the first frame needs come from `utils/settingsMirror.ts`, not defaults.** Settings live in the `settings` table, readable only after the database opens (seconds on a large database). Theme, language, units and the app-lock scopes are mirrored to one AsyncStorage entry (`SETTINGS_MIRROR_STORAGE_KEY`): `hydrateSettingsMirror()` starts at module load in `app/_layout.tsx`, `AppDbReadyGate` awaits it (and applies the mirrored language to i18n) before mounting providers, `SettingsProvider` seeds from it, and every emission writes it back (`recordSettingsMirror`). The table stays the authority. Add to `MirroredSettings` only a setting that changes the first screen and is neither secret (AsyncStorage is unencrypted) nor large; the mirror is in `ASYNC_STORAGE_EXCLUDED_KEYS`, so a restore drops it. `LanguageInitializer` does nothing while `isLoading` (the pre-load language is a default; switching to it flashed English). **Lock scopes are read only in the safe direction**: with no mirror, `appLockScopesPending` is true until the table is read, `isScopeLocked(null, …)` locks every scope, and `AppLockOverlay`/`AreaLockGate` draw a neutral cover rather than `LockScreen` (which prompts for auth on mount; most people have no lock). The exception: a database not ready when `SettingsProvider` mounts — `AppDbReadyGate` only does that for an install that hasn't finished onboarding, which can't have a lock. Pinned by `utils/__tests__/settingsMirror.test.ts`, `hooks/__tests__/useSettings.test.ts`, `components/lock/__tests__/lockPending.test.ts`.

- **A platform sibling may export more than its base module, never less.** Metro picks `.ts` / `.web.ts` / `.ios.ts` / `.android.ts` per platform, but TypeScript checks only the base — a function missing from one variant is a runtime `TypeError` on exactly one platform (v2.12.2: `syncDailySteps` only in `services/healthConnectFitness.ts`; `sendOnDeviceStructured` missing from `utils/onDeviceAi.web.ts`). `utils/__tests__/platformModuleParity.test.ts` enforces it over `constants/`, `database/`, `hooks/`, `services/`, `utils/` (named **value** exports only). A deliberate omission goes in its `ALLOWED_OMISSIONS` table **with its reason**. See `FIXES.md`.
- **`reloadApp()` on web is a URL decision, not a navigation**: `window.location.reload()` re-requests the current URL, so a restore started from onboarding reloads into onboarding over an onboarded database. `restoreReloadTarget(pathname)` (`utils/app.web.ts`) owns the choice — onboarding paths are `location.replace`d to `/app`, everything else reloads in place (`app/(website)/progress.web.tsx` relies on it). Don't "fix" it with `router.replace` before the reload (expo-router commits `history.replaceState` on a later tick). See `FIXES.md`.

### Feature Highlights

- **What's new announcements are data**: `data/whatsNew/<x.y.z>.json` holds one release's ordered pages and `info`, `choice`, `featureList`, `action` blocks; `releases.ts` explicitly imports, validates and sorts them. The registry test requires every JSON file to be registered, valid and translated in all five locales. `whatsNewSeenThroughVersion` (AsyncStorage) means **seen through this app version**, never the last announcement version; it only moves forward (including on empty upgrades and downgrades) and is included in backups. Fresh onboarding writes it in the same `multiSet` as completion; landing-screen imports opt out so restored records survive and legacy backups get the tour; restoring a backup without the record allows the tour after reload.
  - Home checks once per JS session after DB readiness/onboarding, presents only while focused, and suppresses widget camera launches. `WhatsNewIntro` is centred, leads with a large icon and lists each page's headline via `pageHeadlineKey` with supporting copy via `pageHeadlineDetailKeys`; its footer is always Back/Skip + Next side by side (Skip takes Back's slot on the first page). A page may carry `requires` (a `WHATS_NEW_CONDITIONS` entry, today only `cycleTracking`): `loadWhatsNewContext` (`utils/whatsNew/context.ts`) supplies it for the auto flow, Settings replay uses `MenstrualCycleContext`, the debug preview assumes all hold, and omitting `context` hides gated pages.
  - Missing releases merge oldest-first into one intro plus at most `WHATS_NEW_MAX_PAGES` (12) content pages, reserving space for the newest releases first. `supersededIn` removes a page/block at that version; empty pages disappear. Done, Skip, X/back and route actions save the record (killing the app mid-tour doesn't). Settings replays the newest live release without changing the record. Choices read stored settings and write immediately on tap, optimistic with failure recovery; untouched choices never write. Workout settings and cardio are nested child modals controlled by `useSubModalState`; route actions save and close before navigating.
  - **To add a release:** add its version-named JSON; register its import in `releases.ts`; add `whatsNew.*` keys in all five `lang/locales/*/whatsNew.json`; run `generate-lang`, translation/locale checks and the What's new tests. Extend `utils/whatsNew/catalog.ts` only for a new icon, setting or action. `scripts/check-translations.js` scans every `*Key` string in release JSON, so cleanup preserves these keys. The single current file is **2.15.2.json**: 2.13.1 and 2.14.2 never reached production (last was 2.12.3), so their pages were folded into it and every upgrade from an earlier version sees all 12 pages. Release versions stay unchanged until release preparation; `check-version-sync` warns non-fatally if a file is ahead of the app. Debug → What's new shows/clears/sets the record and previews releases (its explicit edits reset the session gate).

- **Workout plans and schedule ownership**: `workout_plan_templates` is the only plan-membership store; templates deliberately have no `plan_id` (one workout may belong to several plans). `workout_plans.cycle_type` selects which membership field matters: weekly plans use `week_days_json`; rotating plans use `position` and must clear weekdays.
  - **`WorkoutPlanService.savePlan` is the ONLY way to change an existing plan** (fields + full membership replacement as one aggregate write; no `updatePlan`/`setPlanMemberships` pair, since committing a cycle-type change without clearing weekdays leaves them on a rotating plan). JSON and AI program generation goes through `WorkoutTemplateService.createPlanWithTemplates`, which prepares every child template AND the parent plan and commits them in one `database.batch` (WatermelonDB never rolls back a batch that already landed, so a template-by-template loop that failed on the plan orphaned workouts). `saveTemplate` reads first, then prepares, then commits one batch.
  - `SaveTemplateData.planIds`: `undefined` leaves memberships alone, `[]` unfiles the template — never default it to `[]`. Membership diffs from `saveTemplate` use `WorkoutPlanService.prepareSyncTemplateMemberships`, which returns `{ activePlanIds, records }` (prepared records because `saveTemplate` already owns the writer; plus the membership set after commit). Plan liveness is checked for BOTH halves of the diff (an id being added and one an existing junction row points at), so memberships left by a vanished plan are retired.
  - **Calendar ownership is contextual and never mirrored**: active weekly memberships supply planned weekdays; `schedules` applies only to templates with zero active plan memberships; a rotating or unscheduled planned workout must not fall back to a dormant standalone schedule. **Enforced on write on EVERY membership path**: `saveTemplate` resolves membership _before_ writing schedules (via `prepareSyncTemplateMemberships`, or `getActivePlanIdsForTemplate` when `planIds` is omitted and days would be written) and skips standalone `schedules` if the template will belong to a plan; `createPlan`/`savePlan`/`setTemplatePlans` soft-delete the standalone `schedules` of every workout they file, in the same batch, via `prepareStandaloneScheduleCleanup`. Don't move the schedule block above the membership block (dormant rows would resurrect when the workout leaves the plan).
  - `workout_templates.week_days_json` is deprecated: normal saves clear it, and editing a legacy row materializes its effective days into standalone `schedules`. `workout_logs.plan_id` is stamped at session start but write-only for analytics in this version. Bundled programs create rotating plans and name workouts by day only.
  - The workout library screen stays an orchestrator; filtering, grouped plan sections, empty/loading states and card rendering belong in `components/workout/WorkoutLibraryContent.tsx`, which runs `groupTemplatesByPlan` once and renders flat layouts by passing `plans: []` (no parallel `filteredTemplates` pass). "Which plans is this workout in?" is one flow, `components/workout/usePlanAssignment.tsx`, shared by the library screen and `CreateWorkoutModal`; a plan created from its picker is seeded via `CreateEditPlanModal`'s `initialTemplateIds`, so plan and first membership are one `createPlan` call. That hook's `selectedPlanIds`/`onChange` are OPTIONAL and `onConfirm` reports failure by returning `false`, never by throwing (it's reached from a `Pressable`'s `onPress`, which doesn't catch).
  - **The plan editor's form state is a snapshot, not a subscription.** `hooks/usePlanDraft.ts` seeds it once per `planId` via `WorkoutPlanService.getPlanSnapshot`; `CreateEditPlanModal` holds only presentation. Don't seed from `useWorkoutPlans()` (it re-emits on every membership write and would replace the half-typed form). `initialTemplateIds` is read through a ref at mount (callers build it inline). The load effect is keyed on `planId` alone with a `cancelled` flag.
  - **"Which weekday is this workout due on?" is one read: `WorkoutPlanRepository.getResolvedSchedules()`** (fetches all three calendar stores into `resolveWorkoutSchedules`). `NotificationService.scheduleWorkoutReminders` and `WorkoutService.getUpcomingScheduledWorkouts` must not issue those queries themselves.

- **The session re-targets planned sets, and it must say so.** Between sets, `WorkoutSessionService.saveSet` rewrites the next planned set and PERSISTS it (`useWorkoutSessionState` only reads it back). `selectRetargets` (`utils/intraSessionRetarget.ts`) decides which sets move: `workout_autonomy = manual` re-targets nothing unless the exercise has an explicit progression rule, a set the user typed over (`override`) is left alone, and a skipped set re-targets the next planned set from the last performed working set. The rewrite carries the previous set's actual load over, then recomputes weight or reps (per `progressionMode`) to hold the target reps in reserve. All arithmetic is one pure function, `computeIntraSessionAdjustment` (`utils/setAdjustment.ts`), returning the new values **and** a `SetAdjustment` — a number the app changed on the user's behalf is never presented as their choice. `EnrichedWorkoutLogSet.adjustment` carries it to the UI, where `useAdjustmentMessage` (`components/workout/useAdjustmentMessage.ts`) states it in one shared sentence (live session, preview, Next time, Weekly Review). The "adjusted" marker (accent underline in Inline, calculator icon in Guided, cleared once the user types over) goes on **the fields `adjustedFields(adjustment)` returns** — never inline a cause check. A `target_rir` change is marked on `adjustment.field`, a start adjustment on whatever plan and set now disagree about, and a `carry_over` is deliberately not badged (that load is the user's own).

- **Cycle tracking: encrypted records, one pure model, no phase prescriptions.** Everything personal lives in an encrypted JSON `payload` on `cycle_periods`, `cycle_day_logs`, `cycle_contexts` (v36) plus `menstrual_cycles.config`; only ids and timestamps are plaintext. **Only `database/cyclePayload.ts` and `database/repositories/CycleRepository.ts` touch ciphertext**; everything else sees DTOs (`utils/cycle/types.ts`). The retired plaintext `period_logs` table and `period_flow`/`period_symptoms` metrics are read only by `CycleDataEncryptionMigration` (boot migration, idempotent by data, mandatory recovery backup first, originals **destroyed** in the same batch) and `normalizeCycleDataForImport` for pre-v36 backups; legacy plaintext `menstrual_cycles` columns are blanked and unread. Writes go through `CyclePeriodService`, `CycleDayLogService`, `CycleContextService`, `CycleTrackingService`, `CycleTransferService`; each reads and validates INSIDE its writer (no overlapping periods, one day log per day) and resolves the encryption key before the writer opens. **Encrypt before `prepareCreate`** (assigning after throws).
  - **`utils/cycle/` is pure and is the one model.** `cycleHistory` keeps every cycle and tags those that shouldn't feed predictions (`too_short`, `possible_missed_period`, `user_excluded`, `hormonal_context`, `postpartum_context`, `life_context`) rather than dropping them. `cycleStats` derives confidence from usable cycles AND spread (never raw log count) and owns the prediction window (`window`) and its centre (`predictedLength`, recency-weighted); `medianLength`/`rangeLow`/`rangeHigh` stay the plain facts the UI and appointment summary quote — never centre a prediction on them. Changes must keep `utils/cycle/__tests__/predictionBenchmark.test.ts` passing (hit rate, error AND window width per profile). `cycleTimeline` is the single phase/prediction layout; `cycleSnapshot.buildCycleSnapshot` assembles it for context, reminders and charts.
  - **Phases other than `menstrual` are an ovulation estimate**, so without the fertility opt-in (`showFertility`, default false in `computeCycleTimeline`) the layout is only `menstrual` + `between`. **"Is this period still going?" is one predicate, `isOngoingPeriod`** (`utils/cycle/periodRules.ts`), used by the timeline's phase and the snapshot's `activePeriod`. **The day counter never wraps**: with no new period logged it keeps counting and the prediction becomes `late` (no segments, no phase). **Never compute a date as `start + N * 24h`** — use `addCalendarDays` (`utils/cycle/dates.ts`); across DST the 24h form lands an hour off midnight.
  - **An end date is a fact only when the person gave it.** `endKind` is `open`, `logged`, `estimated` (derived from usual length, only when chosen) or `unknown` (occupies only its start day for overlap). Only `logged` durations feed average period length. `resolveEnd` (`utils/cycle/periodEnd.ts`) is the only place an end is derived.
  - **Context decides which predictions exist** (`contextGuidance`, `utils/cycle/contraception.ts`): a method that usually stops ovulation or no-bleeding tracking suppresses the period prediction, postpartum waits for two periods, the fertile window needs a natural cycle. `CONTRACEPTION_TRAITS` is a `Record` (a new method fails the build until decided). **The fertile-window estimate is opt-in (`cycle_show_fertility`, default off) and always shown with `cycle.fertilityDisclaimer`.**
  - **No phase-based advice anywhere.** No energy labels, hormone cards or intensity multipliers; observations come only from the person's own records (`cycleInsights`: at least three cycles, "X of your last Y", with the days and workout ids behind them, never causal wording). Workout code must not import cycle phase, and the live workout session shows no cycle card (an observation at session start reads as "today will go worse"). The workout observation compares each session only with sessions of the same workout (`WorkoutPoint.workoutKey`) away from period starts, skips Weekly Review lighter-week windows, and needs `MIN_WORKOUT_INSIGHT_CYCLES` (4) comparable cycles.
  - **Pause is not delete.** `MenstrualCycleContext` observes every cycle and splits it into `cycle` (active) and `pausedCycle`; pausing keeps history, `resumeTracking` re-activates, and only a user with no cycle goes through `cycle-setup`. "Delete all cycle data" **destroys** rows (`prepareDestroyPermanently`) because soft-deleted ciphertext is still decryptable.
  - **Privacy surfaces / app lock** (`utils/appLockState.ts` reducer, `AppLockContext`, `AreaLockGate`, `AppLockOverlay`) refuses to enable without a device credential. **What's locked is a set of `AppLockScope`s** (`APP_LOCK_SCOPES`: `app`, `cycle`, `workout`, `nutrition`, `progress`; `AppLockArea` is every scope but `app`), stored comma-separated under the historical key `app_lock_mode` (old `off`/`cycle`/`app` values remain valid serializations). `parseAppLockScopes` is the one reader; `SettingsState` holds only `appLockScopesRaw` and `useSettings().appLockScopes` is parsed in a `useMemo` (primitive-state rule). `scopeRequiresLock(scopes, scope)`: `app` covers every area. **Every screen that shows an area's records is wrapped in `<AreaLockGate area="…">`** (cycle: `cycle.tsx` and its modals; workout: every screen in `app/app/workout/`; nutrition: `nutrition/food.tsx`; progress: `progress.tsx`; Weekly Review holds `workout` and `nutrition`), pinned by `components/__tests__/appLockCoverage.test.ts`. The gate wraps content inside `MasterLayout` so navigation stays reachable; copy per scope is `LOCK_AREA_COPY` (`components/lock/lockAreas.ts`, a `Record`). **Turning any lock on/off requires authenticating first** (`changeLockScope`, `utils/appLockScopeChange.ts`) and the list is read after the prompt. Controls: `AppLockSettings` in Settings → App lock (`AppLockSettingsModal`, hidden on web) and the cycle settings' Privacy section. Not gated by design: Home summary cards, Profile and the AI coach. **`AppLockOverlay` is drawn at the root AND inside `components/theme/Modal`** (a native Modal is its own window) and, with any lock on, draws a blank privacy cover while backgrounded (`isObscured`). **Until lock settings are known, every scope is locked** (`appLockScopesPending`). Every surface rendering cycle records sits behind the cycle lock (`CycleLockGate`; `MenstrualPerformanceChart` returns null while `isLocked('cycle')`). Exports (CSV, PDF summary) are behind the cycle lock and defuse spreadsheet formulas.
  - **Cycle reminders are a contract, planned in one pure pass.** `planCycleReminders` (`utils/cycle/cycleReminders.ts`) plans every kind in `CYCLE_REMINDER_KINDS` (period heads-up, opt-in due day, opt-in neutral "longer than usual" the day after the latest plausible start — never "late", never pregnancy — fertile window, pill, daily check-in, ongoing-period check, backup). Predictions exist only for an estimate the screen would show, so a context change (pregnancy, loss, hormonal method) cancels them on the next reschedule. **All wording comes from `CYCLE_REMINDER_COPY` / `cycleReminderContent`** (`utils/cycle/cycleReminderCopy.ts`) for scheduling AND the settings preview, at three privacy levels (`CycleNotificationStyle`, parsed only via `parseCycleNotificationStyle`): `discreet` (stored name kept, shown as "Private", never says what it's about), `subtle` (names the task, never periods/fertility/pills), `detailed` (states a range, calls it an estimate). The daily check-in (and a continuous pill) is ONE repeating `DAILY` trigger, not 28 one-shots (iOS keeps 64 pending per app, shared with other reminders). A pause (`reminders.pause`) silences everything except `PAUSE_EXEMPT` (the pill); a repeating reminder waits for the reschedule after the pause ends. Cycle reminders use their own Android channel (`cycle`, lock-screen visibility PRIVATE). Permission is asked when a reminder is turned on (`CycleNotificationService.enableCycleReminders`), never at launch. `getCycleDeliveryStatus` feeds the delivery line and test send through ONE `CycleDeliveryState` (`cycleDeliveryState`, `utils/cycle/cycleReminderStatus.ts`: `web`/`unknown`/`noPermission`/`switchedOff`/`ok`); `reminderStatusKind` and `cycleReminderPreviews` are pure there too. `resetCycleSettings` resets every cycle preference in one write (`SettingsService.resetToDefaults`). A tapped reminder opens `/app/cycle?reminder=<kind>` → `ReminderExplainerSheet` ("why did I get this?"). Recording a pregnancy loss offers a 4-week pause (`CycleContextModal`), never applies one silently. Pinned by `utils/cycle/__tests__/cycleReminders.test.ts`, `services/__tests__/NotificationService.test.ts`.
  - **Completion flows.** Optional encrypted-JSON fields include `cycleLengthKnown`, `confirmedLongCycle`, bounded rating definitions, impact/test observations, `reminders`, `backupReminderDays` (no SQL migration needed). A confirmed long cycle bypasses only `possible_missed_period`, never manual, short-interval or physiological-context exclusions. Unknown fallback length suppresses dates only until usable history exists; `cycleTimeline` widens sparse ranges and `historyAnalysis.evaluatePredictions` uses only earlier starts. Confidence is heuristic, not calibrated. Setup context begins today; never infer contraception or pregnancy history from past period dates.
  - **Health provenance and sharing.** `cycleHealth` implementations request cycle permissions only on an explicit read/export action. `CycleHealthImportService` commits a batch of source-ID keyed `observations.health` values; never overwrite self-report or infer period starts from imported flow. `selectedSharing` is an allowlist; date/field selection can't include context, sex, medication, imported health records or unselected notes. Static sharing can't be revoked. `historyAnalysis`/`CycleTrends` work without period anchors and omit missing values rather than treating them as zero.
  - **Manual recovery boundary.** `CycleTransferService.import(null, ...)` creates the cycle and records atomically; never create a placeholder cycle before validating a file. External CSV mapping is explicit and rejects ambiguous dates/flow labels. Backups remain manual: encrypted file creation/sharing requires a user action; reminders never create files or upload. Don't add automatic cloud upload, cloud credentials or a portable cloud-enable flag without a new user request. "Prepared" backup status isn't proof the file was saved off-device.
  - **Education and reminders.** `careGuidance` links are NHS/RCOG education, not diagnosis or triage; symptom/impact presets aren't a validated PMDD scale. Never infer ovulation from an LH entry or basal/skin temperature alone. Daily reminders stay optional even with hidden/suppressed predictions; the pill reminder renews its 28-day horizon of one-shots (skipping pill-free days) on every foreground; period/fertility reminders still need a meaningful visible estimate. Keep app.json's native health permissions and committed manifests/usage descriptions synchronized.
  - **Deleted cycle text doesn't linger; recovery points stay encrypted.** A cleared day log and a removed context are destroyed (`prepareDestroyPermanently`, no undo). A removed period stays soft-deleted for the in-session "Undo"; the boot task `CycleRecordPurge.purgeDeleted` destroys it next launch. Exports drop soft-deleted cycle rows. Automatic on-device recovery points (`createLiveBackupJson`, web `executeLiveBackup`, web pre-migration dump) pass `keepCycleCiphertext`; downloading one goes through `exportPortableRecoveryPoint` / `decryptCyclePayloadsInDump` so it restores anywhere. `CycleDataEncryptionMigration` deletes its own pre-conversion backup (a copy of the plaintext it removes) once every converted record reads back. Pinned in `database/services/__tests__/cycleRecords.integration.test.ts`.
  - **`MenstrualCycleProvider` is the one owner of cycle data, mood included.** It exposes the snapshot's own fields (`timeline`, `predictionStats`, `activePeriod`, …) with no aliases; `today` is local midnight from `hooks/useLocalToday.ts` (a `useSyncExternalStore` that changes only when the calendar day does). Shared mood is observed once there (`moods`, `moodsLoading`, `moodsError`) — don't call `useCycleMoods` from a component. Payloads are schema-checked on decrypt (`CycleRepository`); shapes (`PeriodPayload`, `DayLogPayload`, `ContextPayload`) are declared there once.
  - **Write and observer boundaries.** Existing models are prepared inside `commitPrepared`, with all reads and encryption done before preparation, so adapter rejection restores cached state. The legacy encryption conversion and permanent cycle deletion each use ONE adapter batch/transaction even above `MAX_BATCH_OPERATIONS` (chunking would leave partial state); the migration reads its snapshot inside the writer after the recovery backup and key priming. `MenstrualCycleProvider` captures config ciphertext in immutable observer state (WatermelonDB reuses model objects). `updateConfig` accepts a `CycleConfigPatch` or a synchronous updater returning one; the service reads and merges the latest encrypted config inside the writer, including partial nested reminder edits. UI sends only changed fields, and list add/remove/toggle uses the updater's current config, not a render snapshot.
  - **Journal preferences and portability.** Goals, custom symptom names, quick-log favorites/dismissed suggestions, enabled daily fields and custom field definitions live in encrypted `menstrual_cycles.config` (optional fields; no schema migration); observations (including archived custom labels) stay in each encrypted day payload. Legacy bundled favorites may still be read from `cycle_quick_log`; new choices persist in encrypted config, never plaintext settings. Quick actions use `CycleDayLogService.patch` to merge against the latest day inside its writer; patches preserve observations; zero and false are observations, not emptiness. Mood remains the shared `user_metrics` mood: `CycleDayLogService.save(input, mood)` commits both atomically (`undefined` leaves mood alone, `null` clears that day's moods). Full cycle deletion keeps shared moods and says so. `useCycleMoods` observes shared edits for comparisons/exports.
  - **Cycle-only files.** `cycleTransfer` owns the versioned JSON/CSV parser and strict date/field validation; `cycleMerge` owns preview/commit conflict and overlap rules; `CycleTransferService` re-reads inside its writer and commits once without resetting other tables. Dates travel as YYYY-MM-DD. CSV has supplementary JSON columns for symptom keys and observations, plus mood; readable exports have no password protection. `backupCrypto` authenticates encrypted cycle files before decryption (PBKDF2-SHA256, independent AES/HMAC keys, random salt/IV) — don't use the device-value `encrypt` shortcut. Last-backup preparation time is device-local, excluded from full-app backups.
  - **Comparisons and no bleeding.** `cycleComparison` uses logged starts only (cycle-day alignment and up to 14 days before the next actual start; no predicted phase alignment). Missing values differ from explicit none and unrated presence. No-bleeding mode hides period actions and predictions but retains unexpected bleeding/spotting inputs. Custom symptom labels resolve through `cycleSymptomLabel` everywhere.

- **Offline notifications are planned, not repeated.** `utils/notificationPolicy.ts` (pure) owns every rule about whether and when a local notification may exist (quiet hours, pause, reminder lead time, accountability style, the 14-day workout-reminder window, the nightly overview window, the weekly-goal-at-risk test). `refreshAllNotifications()` (`services/notificationRefresh.ts`) re-plans all of it on boot, every foreground and after a workout. Planners are split by domain — `NotificationService` (workout, goal-at-risk, live session), `NutritionNotificationService` (overview, check-ins, weekly review), `CycleNotificationService` (cycle reminders, own queue) — sharing `cancelScheduledByType`/`loadNotificationPreferences` from `services/notificationScheduling.ts`; don't grow `NotificationService` back past 1k lines or re-inline the cancel-by-`data.type` loop. Reminders are one-off `DATE` triggers, never repeating `WEEKLY`/`DAILY` (a repeating trigger can't skip a day already trained, honour a pause or leave quiet hours; the cycle pill reminder is the precedent). Preferences are ONE JSON setting (`SettingsService.get/updateNotificationPreferences`, merged in the service so quick taps can't clobber each other), not in `SettingsState`. The live session — rest alert, active-workout banner, unfinished-workout nudge — is exempt from quiet hours and pause. Android channels and action categories are named once in `constants/notificationActions.ts`; the rest alert has its own channel and is the only `timeSensitive` notification. Action buttons (`+30s`, `Snooze`) are handled in `utils/notifications.ts`; the unfinished-workout reminder is deliberately NOT cancelled on screen unmount and is cleared by `clearActiveWorkoutLogId`. Permission is requested in context (`RestAlertsPrompt`, after the first completed set), once. Pinned by `utils/__tests__/notificationPolicy.test.ts`, `services/__tests__/NotificationService.test.ts`.
- **Notification buttons, snoozes and explainers** — three rules:
  1. **Cycle buttons are neutral on purpose**: the pill category is _Done / Later / Skip_ (`NOTIFICATION_CATEGORIES.cyclePill`), every other cycle reminder has _Snooze_ (`cycleReminder`) — an action row reading "Taken" would give away a discreet reminder. Done/Skip go through `CycleNotificationService.recordPillAnswer` (waits for the database; merges into today's page inside `CycleDayLogService.patch`; writes `observations.pill` `'taken' | 'skipped'` — never write the answer elsewhere). Later/Snooze re-send the content as a one-shot of type `menstrual-cycle-snooze` (`CYCLE_SNOOZE_NOTIFICATION_TYPE`), **not** `menstrual-cycle`, so the reschedule that replaces ordinary reminders doesn't erase it; that same pass re-checks each snooze with `isSnoozeStillValid` (`utils/cycle/cycleReminders.ts`; a pause silences every kind but the pill, and an estimate is dropped once the prediction is `hidden`/`suppressed`) and reuses the single `getAllScheduledNotificationsAsync` read. Both types route to the cycle screen.
  2. **A workout reminder carries its own explanation**: `scheduleWorkoutReminders` puts `dayIndex`, `reminderTime`, `leadMinutes` and `fromPlan` in `data`; the tap handler turns them into route params with `workoutReminderRoute`, and `parseWorkoutReminderParams` (both in `utils/workoutReminderExplainer.ts`) reads them back for `WorkoutReminderExplainerSheet` (tolerating older reminders that carry only the template). The day/time are the _plan's_, not the lead-adjusted fire time. Its exits go through `SettingsService.updateNotificationPreferences` / `setNotificationsWorkoutReminders` then `refreshAllNotifications`; its `NotificationsSettingsModal` is rendered inside the sheet (`local/no-sibling-modals`). A plan membership has no reminder time (08:00 default), so there's deliberately no "change time" button.
  3. **Rest alerts have three independent settings** (`restAlertSound`, `restHapticStrength`, `restHeadsUpSeconds`; `SETTINGS` definitions mirrored in `SettingsState`): the chime is a channel choice on Android (`rest-timer` vs `rest-timer-quiet`; a channel's sound is fixed at creation) and `content.sound` on iOS; the heads-up is `restPhase(remaining, total, headsUp)` + a `'headsUp'` `hapticBeat` + (backgrounded) a quiet notification (`REST_TIMER_HEADS_UP_NOTIFICATION_ID`) cancelled with the alert and skipped when the rest isn't longer than `headsUp + REST_HEADS_UP_MIN_GAP_SECONDS`. Pass the heads-up to `hapticBeat` only for a rest longer than the window, as `restPhase` gates it. **The work timer** (`hooks/useWorkTimer.ts`, `utils/workTimer.ts`, `WorkTimerBar`) counts down a timed set separately from rest; reaching zero calls `onFinish`, and if that started a rest the hook remembers it so the next set completion passes `autoRest: false` (`consumeRestHandoff`). Its time's-up notification (`WORK_TIMER_NOTIFICATION_ID`) rides the rest-alert switch and sound choice.

- **Gym profiles, plates and exercise restrictions** — three things that look like settings and aren't:
  - `gyms` holds a named equipment set (kilograms like every weight; bar, increment and plate weights cross persistence through `toStoredGymWeightKg`, seven decimals to preserve quarter-pound inputs; `plates_json`/`equipment_json` are raw strings parsed in exactly one place, `snapshotFromGymRow` in `utils/gym.ts`, so a hand-edited or newer row degrades to defaults instead of throwing mid-set). The active gym is the primitive setting `ACTIVE_GYM_ID_SETTING_TYPE` (`activeGymId` on `SettingsState`); `hooks/useActiveGym.ts` joins it with observed gyms, so a deleted gym reads as "none".
  - **Plate math is not greedy**: `platesPerSide` (`utils/plateCalculator.ts`) is a bounded knapsack (one pair each of 20, 15, 10 kg for 25 kg a side: greedy takes 20 and is stuck 5 short; the answer is 15 + 10). Plates load in PAIRS (a stored count of 3 is one pair). `roundToLoadable` is the ONE rounding rule for loads, with or without a gym (takes the resolved `units`): without a gym a bar-loaded lift moves in pairs of the smallest standard plate (2.5 kg / 5 lb); anything else is only tidied to input precision (0.5 kg / 1 lb) — snapping dumbbells to the 2.5 kg grid invented equipment (12 kg → 15, +25%). `loadStepFor`'s `roundLoad` delegates to it, warm-ups load from `defaultGymSnapshot(units)`, and `weightInputStep` keeps the legacy 0.5 step. **Use `StepperInput`, not `NewNumericalInput`, for plate and bar weights** (`NewNumericalInput` is whole numbers only; plates come in 1.25).
  - **Restrictions** (`exercise_restrictions`; kinds `never` > `injury` > `dislike`) have one live row per exercise (`ExerciseRestrictionService.set` replaces); an injury's `expires_at` makes it inactive without deleting (`isRestrictionActive`; the manager shows "healed"). Precedence is in `exerciseExclusionReason` (`utils/exerciseSubstitution.ts`): never/injury, then equipment the gym lacks, exclude; a dislike only demotes and flags. **`ExerciseSuggestionService` is the one answer to "what may the app suggest right now?"** — swap list, AI plan prompt and AI plan response all use it. The prompt is filtered AND the response re-checked (a model can ignore its list): a restricted exercise in a generated plan is swapped for the best same-region substitute the plan doesn't already contain, or dropped. The swap list filters in SQL (`ExerciseListFilters.muscleGroups/equipmentTypes/excludeIds`) so pages stay full, which is why `MAX_EXERCISE_RESTRICTIONS` equals `MAX_QUERY_IDS`.
  - **A swap changes only the session**: `WorkoutLogExerciseService.replaceLogExercise` rewrites a wholly planned log block, or splits pending sets into a new block once any set is performed/skipped (`replaced_exercise_id` keeps the ORIGINAL exercise across repeated swaps, `substitution_reason` records why), and resets only still-planned sets to the new exercise's load (a planned 80 kg bench isn't an 80 kg fly); performed and skipped sets are history. "Just today" and "machine occupied" persist nothing; pain and dislike merely PRE-SELECT an opt-in toggle to remember the choice — never apply it silently. Pinned by `utils/__tests__/{gym,plateCalculator,loadIncrement,exerciseSubstitution}.test.ts` and service tests beside them.
- **Warm-ups, start-of-workout progression and the rest timer.** A set has two independent axes: lifecycle (`completion_status`) and kind (`set_type`). `isWorkingSet` (`utils/workoutSetCompletion.ts`: performed AND not `'warmup'`) is the predicate for "how hard did they train" — volume (`WorkoutLog.calculateVolume`, `calculateSessionVolumeFromSets`), PRs, e1RM, the six `WorkoutAnalytics` queries (which also filter `set_type != 'warmup'` in SQL), progression's `lastSets`, muscle-group set counts, LLM summaries — while `isPerformedWorkoutSet` stays for "what did they do" (history, calories, Health Connect deliberately KEEP warm-ups). In the live session a warm-up is never the "previous set" a working set is re-targeted from, and a planned warm-up is never re-targeted. `set_order` is ONE ordering key for the whole workout, so `WorkoutLogExerciseService.addWarmupSets` shifts every later set (other exercises included) in the same batch; WatermelonDB's `prepareUpdate` mutates immediately, so read the anchor's order into a local before building operations.
  - **Start-of-workout progression** (`WorkoutProgressionService.applyStartProgression`, called by `WorkoutService.startWorkoutFromTemplate` after the template is copied) is gated by `workout_autonomy` (`manual` copies the plan verbatim; `suggest`, the default, progresses). It reads previous sessions in parallel BEFORE its writer (holding the write lock across per-exercise queries blocks every other write), reads and writes the sets it rewrites in ONE writer, skips a workout that has begun or was already progressed (safe twice), and is **best effort — a failure must never stop a workout from starting**. The history/projection boundary is `WorkoutProgressionService` (`projectAdHocExercise` for Add/Swap, `projectTemplate` for preview), both using `projectExerciseProgression` and `computeStartTarget`; `progressesLoad` is the ONE check that keeps cardio, mobility and stretching unprogressed.
  - Coaching rules living in that pair only: a deload needs **two** sessions in a row at the same load that failed — average rated RIR 0 for the automatic path (`failedBefore`), below `repMin` for double-progression and top-set rules (`missedAtSameLoad`) — the first miss holds. `reps_first` climbs from the PLANNED reps (`repsFirstRange`: plan … plan + 2), falling back to generic 8–12 / 12–16 only when `plannedFromHistory` says the "plan" is a copy of last session (Add/Swap). The automatic path progresses when last session's average rated RIR met the live target (`DEFAULT_TARGET_REPS_IN_RESERVE`, 2) AND planned reps were hit. A session whose effort was never rated falls back to double progression on reps alone (`computeUnratedTarget`; holds when there's no plan to judge against) and attaches a `range` rule detail so the explanation never claims an unrecorded RIR. "Last session" means the latest COMPLETED WORKOUT: history orders by the parent log's `completed_at` (a log exercise added later has a fresh `created_at`). History uses one batched set query (`fetchByIds`); step and rounding come from `loadStepFor` (`utils/loadIncrement.ts`) on every progression path (including between-sets re-targeting and `planStartChanges`, which rewrites only a block of STRAIGHT sets — a pyramid or back-off can't move by one number).

With `auto_start_rest_timer` off the session stays put and offers a "Start rest" pill instead of `router.replace`-ing to the timer. - **Exercise search is `exercises.search_text`, built and queried by ONE module.** `utils/exerciseSearch.ts` normalizes (lowercase, strip diacritics, separators → spaces), stems plurals, expands abbreviations (`EXERCISE_ABBREVIATIONS`; adding one is one entry) and builds the stored word set; `database/exerciseSearchCondition.ts` turns a query into the `Q` condition and `matchesExerciseSearch` is its in-memory twin (website, `findExerciseByName`). Why: (1) index and query must share normalization, so the column stores words, not names; (2) a catalogue row's `name` is written once in the boot language and never re-localized, so `search_text` holds the name in **every** bundled language (`getAllLocaleExerciseNamesBySlug`); (3) **don't use `Q.sanitizeLikeString`** (it rewrites non-ASCII-alphanumerics to `_`, so a Cyrillic query would match any string of that length) — `normalizeExerciseText` already reduces words to LIKE-safe letters and digits; (4) SQLite `LIKE` is ASCII-case-insensitive only, so Cyrillic folding happens before the query; (5) `\p{L}` is deliberately avoided (no Hermes property escapes elsewhere). - **Optical Transfer (device-to-device over light)** moves Musclog data with no network: one screen streams fountain-coded QR frames, the other's camera reads them. Android, iOS and web can send or receive; Musclog GB is sender-only with two actions — whole-database `SHARE DATA` (Settings) and `SHARE DAY` (nutrition screen's SELECT menu, offered only when the day has entries; a non-destructive share). The app entry is a `SettingsCard` in `DataSettingsModal`'s Data Portability section → `OpticalTransferModal` → `OpticalSendModal` / `OpticalReceiveModal`; the first onboarding screen also opens `OpticalReceiveModal` with `accept="database"` (a fresh install can receive a full backup but can't accept a food, meal or day share). App logic is `utils/optical/` (pure, no RN imports, Jest `node` project); Skia and camera are isolated in `components/optical/`; Game Boy logic is `gameboy/src/features/optical/`. **Read the Optical Transfer section of `RESEARCH.md` before touching any of it** (on-device measurements and cartridge constraints). Invariants:
  - **`fountain.ts` and `frameProtocol.ts` are FROZEN wire format**, ported verbatim from [decimen-optical-transfer](https://github.com/bashalarmistalt/decimen-optical-transfer)'s **MIT** releases (v0.3.0 and earlier). Upstream relicensed to **AGPL-3.0-or-later at v0.4.0** (2026-08-09): never pull fixes or helpers from v0.4.0+ into `utils/optical/`. The two phones can run app versions months apart and derive every frame's block subset independently with no handshake. `dlog()` exists because `Math.log` is implementation-approximated in ECMAScript — replacing it or shortening its 21-term series silently breaks every future transfer. `utils/__tests__/opticalFountain.test.ts` holds decimen's golden vectors; a failure is a broken format and needs a header version bump, not a re-recorded constant. Jest runs on V8, so the Hermes sweep in the bench screen is the other half of the guarantee. **All format evolution goes in `container.ts`**, whose version byte is checked _after_ reassembly and so can say "update the other phone".
  - **The Game Boy speaks that frozen receiver protocol but never receives.** It sends two compact schemas, each expanded strictly right after `JSON.parse`, before validation, backup or any destructive wipe: the whole database (`_gameBoyExport: 1`, `utils/optical/gameBoyExport.ts`) and one day of eating (`_gameBoyShare: 1`, `utils/optical/gameBoyDayShare.ts` → an ordinary `nutritionDay` share envelope that then goes through the SAME `parseShareEnvelope` as any app-built share). `utils/share/parseIncomingShare.ts` is the single receive entry that tells them apart. A day share uses the same streaming sink and food tuple as the database export, narrows `scan_references` to that day, and flips exactly two container fields: `payloadKind = 1` and `exportVersion = 0xFFFF`. `data/gameBoyOpticalProtocol.json` is the single wire contract for export-version numbers, exercise enum ordinals, the frozen `exerciseSlugs` order and the frozen `foodExternalIds` list, consumed by the ROM generator and the TypeScript receiver. Never derive them from the current popular-exercise subset, reorder entries, or duplicate version literals in C; append deliberately and regenerate with `npm run gb:gen-exercises`. The generator rejects catalogue values absent from the contract, and `selectPopularExerciseRows` diffs `exerciseSlugs` against the `isPopular` flag in **both** directions.
    - **`exerciseSlugs` position is exercise identity on two wires** (a cartridge `.sav` stores a set's exercise as that 0-based index; the optical export sends the same). It's deliberately NOT `exerciseIndex` (alphabetical over all 873, shifts when free-exercise-db gains a row). `utils/optical/gameBoyExerciseMapping.ts` maps an index to `appExerciseId(slug)` (`fx-<slug>`), so an imported workout references the bundled row the app owns (localized name, photos, muscles); the dump carries exercise **identity** only and creates no `exercises` rows for mapped indices (`AppExerciseCatalogueService.sync` runs right after restore). An index past the list means a newer cartridge: only then create a plain user exercise from the tuple sent — never reject the transfer. Cartridge history carries days but no times: metrics map to device-local midnight, food/workout events to device-local noon, capturing the offset so imports keep the same displayed day in every timezone. The receiver synthesizes only app-owned profile defaults the cartridge can't store (editable name, blank email, default avatar, valid sync UUID, inferred birthday, onboarding/current-user metadata, unit-derived manual-carbs convention) and must not fabricate body-fat, cycle, cloud-account or health-permission data. Transport: uncompressed unencrypted database container, 292-byte fountain blocks, base44, fixed QR version 11-L/mask 0. GBDK has no floating point, so its robust-soliton calculation is fixed point and omits ambiguous CDF-boundary or >64-degree sequence numbers; arbitrary sequence gaps are legal and every emitted selection must stay byte-for-byte compatible with `fountain.ts`. Keep `utils/__tests__/{gameBoyFountainPort,gameBoyExport,gameBoyDayShare,gameBoyExerciseCatalogue,gameBoyFoodCatalogue}.test.ts` with any change; the first pins the C transport constants (including both payload kinds and the share export version) against `container.ts`/`frameProtocol.ts`, so keep it deriving them. `SHARE DAY` is the ONE partial-share choice the cartridge offers — don't add more or any Game Boy-to-Game Boy receive path.
    - **`foodExternalIds` position is food identity on the same two wires**, and it matters more: `ff_load` truncates a bundled food's name to 16 characters (`FF_NAME_VISIBLE`), so name-based dedupe misses essentially every bundled food and the day share (which MERGES) would grow a second, worse-named copy each time. `utils/optical/gameBoyFoodMapping.ts` resolves an index to the frozen `external_id` plus the full seed row from `data/usda_foundation_foods.json` / `data/common_foundation_foods.json`, so the importer's dedupe takes its `external_id` branch. `utils/foundationFoodSeed.ts` is the single parse of a seed row, shared with `database/seeders/prod.ts`. The list is append-only and `gameboy/tools/gen-foundation-foods.mjs` fails the build if regeneration would change an existing entry; two indices MAY share an `external_id` and both resolving to one receiver food is wanted. A custom food or an index past the list falls back to the tuple sent alongside. The whole-database export deliberately does NOT use this mapping (it restores into a wiped database; stamping `external_id` would make `seedUSDAFoundationFoods` skip seeding next boot, leaving only the foods the cartridge referenced).
  - **Game Boy optical buffers are transient SRAM bank-3 scratch only.** Custom foods end at `0x0A2F`; QR workspaces start at `0x0B00`, the binary frame at `0x0F00`, base44 text at `0x1040`, the 12-block payload cache at `0x1250..0x1FFF`. The streamed exporter may read the food-log layout directly, but no optical code may overwrite authoritative profile, food-log, workout-log, metric or custom-food data. QR version 11 occupies 324 tiles across both CGB VRAM banks; the attribute map must retain `S_BANK` for tiles 256–323 and the renderer must set `LCDCF_BG8000`. The font UI selects signed `0x8800` addressing, under which tile IDs 0–127 resolve to the font at `0x9000` instead of QR data.
  - **Frames are armored to text with base44, never sent as bytes.** vision-camera's `Code` is `{ value?: string }` (no byte array) and MLKit's `rawValue` is null for non-text. The alphabet is QR's alphanumeric set minus space (keeps ALPHANUMERIC mode, 3.1% cost vs 25% for base64; no whitespace trimming can eat a frame). Don't switch to byte mode without a native decoder.
  - **The sender can't measure what limits the transfer, so density is both capped and user-overridable.** The constraint is the _receiving_ camera (autofocus, sensor, lighting), and an undecoded frame still counts as sent. Android's code-scanner analyzer runs at CameraX's ~640×480 default. Goodput is nearly density-_invariant_ when encode-bound while autofocus tolerance collapses as density rises (a field transfer at `dense` took **an hour**). So `calibrateDevice()` only considers presets up to `MAX_RECOMMENDED_OPTICAL_PRESET_ID`, and `OpticalQualityControls` lets the user change speed and code size **while streaming** (speed is free; density restarts the stream — a new QR version means a new `streamIdentity`). `useOpticalSender` retains the packed container so re-slicing is instant. **Don't raise density by default and don't move the controls off the streaming screen.**
  - **Never drive the sender's display loop with `setInterval`**, and always `dispose()` the `SkImage` (both caused progressive frame-rate collapse on hardware). The loop has one implementation, `hooks/useQrFrameLoop.ts`, shared by `useOpticalSender` and the bench screen (`app/app/test/optical-bench.tsx`) — a second copy would stop the bench measuring what ships. `hooks/__tests__/useQrFrameLoop.test.ts` pins the self-scheduling, the all-or-nothing frame cache and install/arm order-independence.
  - **The frame cache is all-or-nothing** (`planFrameCache`): looping fewer distinct frames than the receiver needs deadlocks silently at ~98%, so an unsafe cache isn't built at all.

- **The circadian expenditure model has one implementation: `utils/circadianBurn.ts`, ticked by `hooks/useCircadianBurn.ts`.** `BLOCK_FRACTIONS` (`constants/circadian.ts`) splits TDEE across six 240-minute phases; `CIRCADIAN_SEGMENTS` lays them out in minutes-since-midnight order, with `earlySlеep` appearing **twice** (its block straddles midnight). `circadianBurnedKcal(tdee, minutesSinceMidnight)` is a strict partition (0 at midnight, exactly `tdee` at end of day), stays fractional, and the caller rounds (strip, card) or floors (live counter). Three surfaces read it (the stat strip, `CaloriesBurnedCard`, `CircadianScienceModal`) — don't add a fourth copy of the segment table, accumulator or phase lookup. `useCircadianBurn` is the only clock; `enabled`/`tickMs` cover the differences (the modal ticks per second only while visible; everything else per minute). The hook uses `useSyncExternalStore`, not `useState` + effect (the reading derives from `Date.now()` each render; a synchronous `setState` in an effect is an ESLint error); the snapshot is **quantised to `tickMs`** (an unquantised clock re-renders forever). The Cyrillic `е` in `earlySlеep` is a typo frozen into `BLOCK_FRACTIONS` and the `progress.circadianPhase.*` / `progress.circadianModal.*` keys in every locale; renaming it in one place silently loses the rate and label.
- **Today's step count reads through `hooks/useDailySteps.ts`, which must use `observeWithColumns(['value'])`.** The platform sync upserts ONE `daily_steps` row per day, so later readings are in-place updates (`observe()` emits only on membership change — same trap as `useNotes`). The query filters `deleted_at`, and because `getDecrypted()` is async the hook gates each publish on an emission token so a slow earlier decryption can't land after a newer one.
- **Food search source**: configurable via `FOOD_SEARCH_SOURCE_SETTING_TYPE` (Open Food Facts, USDA, Musclog barcode DB, local-only).
- **OCR before AI**: when enabled (`USE_OCR_BEFORE_AI_SETTING_TYPE`), images are OCR'd locally before being sent to the LLM, reducing data sent externally.

## Progression sessions and weekly target periods

- **Schema**: additive migration v31 (exercise rule snapshots); v32 (prescription/effort metadata, target modes, dated nutrition target periods, weekly review records); v33 (`workout_log_exercises.superset_slot_id` — split replacements inherit the original slot ID, and superset ordering groups by that slot, falling back to the log block ID, never the movement catalogue ID); v35 (`exercise_user_settings.rep_ceiling`). `database/weeklyReviewSchema.ts` owns the new table definitions shared by migration and schema. Preserve every table and optional column in backups/restores.
- **`WorkoutProgressionService.projectTemplate`** is the shared read-only recommendation projection for preview, Next time and Weekly Review. Start targets are established once. Explicit rule history is scoped to movement + stable template-exercise identity; saving unchanged exercises reuses their rows. Active-session rule copies never follow template edits. Warm-ups are excluded and incomplete prescribed sets can't imply full success.
- **Every deload snaps DOWN to a load that is really lighter, through `loadBelow` (`utils/setProgression.ts`).** Rounding a 10% cut to the nearest loadable weight sends a 10 kg dumbbell's 9 kg back to 10 kg, so the "deload" changed nothing. `loadBelow(current, target, step)` walks down one step at a time until the load is at or under the target AND strictly below current, returning current when nothing lighter exists (an empty bar, an unloaded exercise) — the caller then holds and must not claim a deload. `deloadedLoad` (automatic, rep-range rules, a lighter week), the linear rule's `deloadPercent` and a lowered percentage training max all use it. Never call `step.roundLoad` directly on a deload target.
- **Unloaded bodyweight work only ever adds reps, up to a per-exercise ceiling.** `computeStartTarget` takes `repCeiling` for a bodyweight exercise whose last session had no external load; it climbs one rep a session past the plan's range and, at the ceiling, holds with a `{ kind: 'ceiling' }` explanation (add a vest or belt, a harder variation, or slow the tempo) — it never invents external kilograms. Once external load is logged, it progresses like any other. The ceiling is `exercise_user_settings.rep_ceiling`, picked from `BODYWEIGHT_REP_CEILING_OPTIONS` (10–50, never typed). With no pick the default depends on the movement (`defaultRepCeilingFor(loadMultiplier)`): 15 for anything moving at least 85% of body mass (pull-ups, chin-ups, dips, muscle-ups, glute-ham raises, jumps), else 25 — no name lists. An explicit pick is stored verbatim even when it equals today's default (`storedRepCeiling`). Non-React code reads it via `ExerciseUserSettingsService.getResolvers(gym).repCeilingFor(exercise)`; the hook's `get(id).repCeiling` is the pick only (`undefined` when none) and the caller supplies the default.
- **The percentage rule's training max goes down as well as up.** After `failuresBeforeReset` (default 2) sessions in a row missing reps at the same training max, it is cut by `resetPercent` (default 10%) — the 5/3/1 reset — and the misses that caused it can't trigger another (the streak counts only sessions at the current max). Both fields are optional in stored JSON: `FIELDS_ADDED_LATER` fills defaults for older rules, while an out-of-range value makes the whole rule untrusted. Never re-estimate the training max from recent sets (submaximal sets ratchet it down).
- **A session that doesn't advance a rule hands its state on only while it still belongs to that rule** (`carriedSessionState`: same percentage method, starting training max and reset marker). Otherwise a changed starting max would be hidden from `resolveTrainingMax`, which detects the change by comparing the rule with the one the last session ran under.
