- `npm start`: Start Expo development server
- `npm run start-clear`: Start with cleared cache
- `npm run web`: Start for web development (http://localhost:8081)
- `npm run android`: Run on Android emulator
- `npm run android-device`: Run on physical Android device (no build cache)
- `npm run ios`: Run on iOS simulator/device
- `npm run prebuild`: Run Expo prebuild (clean)
- `npm run lint:all`: Run full linting, formatting, and typecheck suite
- `npm run lint:eslint`: Run ESLint check
- `npm run format`: Format code with Prettier and Tailwind plugin
- `npm run typecheck`: Run TypeScript type checking
- `npm run check-translations`: Validate translation keys used by the app
- `npm run check-locale-consistency`: Validate translation-key parity across locales
- `npm run check-version-sync`: Verify Expo, package, Android, and iOS release versions match

- `npm run build-android`: Production build for Android via EAS (AAB for Google Play)
- `npm run build-android-apk`: Production build as an installable, release-signed APK (for direct download / GitHub release attachment); `build-android-apk-local` builds it locally
- `npm run playwright`: Run Playwright E2E tests (Web)

- `npm run gb:lint`: Run `clang-tidy` on the Game Boy C sources

## Repo Structure: Dual-Purpose (App + Website)

This repository serves two distinct purposes that share the same Expo Router project:

- **`app/app/`** — All mobile app screens (iOS & Android). These are the core product screens: nutrition, workout, profile, progress, settings, onboarding, etc.
- **`app/(website)/`** — The institutional/marketing website (landing page, privacy policy, etc.). This is only rendered on the web platform. Route group `(website)` keeps it isolated from the app routes.

**Key conventions for the website:**

- Files ending in `.web.tsx` inside `app/(website)/` are the web-specific implementations (e.g. `home.web.tsx`). Their non-web counterparts (e.g. `home.tsx`) exist as native stubs or redirects.
- Website components live in `components/website/` (e.g. `StoreButtons`, `WebsiteBackgrounds`, `WebsiteWrapper`).
- Website SEO is mounted once by `app/(website)/_layout.web.tsx` via `components/website/WebsiteSeo.tsx`. `components/website/websiteRoutes.json` is the **single** route registry for fixed website routes: each entry holds the route's canonical `path`, an optional `robots` directive (omit it for indexable routes), and an optional `llms` blurb. Markdown blog post routes are the one derived exception; `scripts/generate-web-seo-files.js` adds their file-derived URLs to the sitemap. `WebsiteSeo.tsx` reads the registry for canonical URLs and robots meta; the generator reads it to regenerate `public/robots.txt`, `public/sitemap.xml` and `public/llms.txt` on every `npm run web` / `npm run build-android-web`. Adding a fixed public route is therefore **two** edits: the `websiteRoutes.json` entry, plus its `website.seo.routes.<key>` title/description in each `lang/locales` `website.json`. Do not reintroduce a second copy of the fixed route list in the generator script or in `public/llms.txt` — those three `public/` files are generated, never hand-edited. Sitewide `Organization`/`WebSite` JSON-LD is mounted once in `_layout.web.tsx` via `components/website/WebsiteStructuredData.tsx`; add a page-specific schema there too (e.g. `FaqPageJsonLd`, `SoftwareApplicationJsonLd`, `BlogPostingJsonLd`) when a route's content maps cleanly to a schema.org type — never fabricate fields like `aggregateRating` that aren't backed by real data.
- Blog source files live recursively under `app/(website)/posts`; every file/directory segment must be URL-safe (letters, numbers, hyphens, or underscores), and frontmatter requires `title`, `date` (`YYYY-MM-DD`), `category`, and `tags`; `description` is optional. `blog/index.web.tsx` and `blog/[...slug].web.tsx` use Expo static data loaders plus `utils/blogPosts.server.ts`; the dynamic route exports `generateStaticParams` from the discovered slugs, and their unsuffixed `.tsx` siblings are the usual native redirects. Post Markdown is rendered server-side with `markdown-it` (`html: false`) and `highlight.js`, so the browser receives safe rendered HTML rather than the parser/highlighter or Markdown source. Two layout constraints:
  - **The index is `blog/index.web.tsx`, not `blog.web.tsx`.** Expo writes each loader payload as an extensionless file named after the route's context key, so `blog` (file) and `blog/` (directory of per-post loaders) would collide and fail the export with `EISDIR`. Any `foo.tsx` + `foo/[x].tsx` pair that both export loaders has this problem; put the index inside the directory.
  - **Catch-all platform variants need `patches/expo-router+57.0.12.patch`.** Expo Router 57.0.12's `getFileMeta` reads a file's platform extension as `split('.')[1]`, which misparses `[...]` (it contains dots) — so `[...slug].web.tsx` was published as a literal route `blog/[...slug].web` on every platform, and `[...slug].native.tsx` silently never applied (native rendered the web page). The patch also strips the platform extension in `getContextKey`, without which `useLoaderData` interpolates `[...slug].web` instead of the slug and the client requests a loader path the export never wrote. Its third hunk removes route groups from the loader path in development only; production keeps them because static export writes loader files under them. `utils/__tests__/expoRouterLoaderPatch.test.ts` pins all three. Keep the patch until the equivalent fixes ship upstream, and revalidate index/post navigation in both environments when upgrading Expo Router.

  Expo Router 57 static manifests retain the unresolved catch-all template alongside generated paths, so `loadBlogPostForRoute` must keep handling the literal `[...slug]` build-time loader call until that behavior changes upstream.

  **`utils/blogPosts.server.ts` is stubbed out of the native bundle, and the `await import()` in the route files is not what does it.** expo-router's native `require.context` regex (`_ctx.android.js`) has an optional `(?:\.ios|\.web)?` group, so it matches `blog/index.web.tsx` and `blog/[...slug].web.tsx` on Android and iOS too — platform selection happens later, when `getRoutes` builds the tree, by which point Metro has already added the files to the graph. Metro also resolves `import()` statically (React Native has no code splitting), so the deliberately-dynamic imports in those loaders still pull the module in, and its `node:fs/promises` import fails the native bundle with `Unable to resolve module node:fs/promises`. `metro.config.js` therefore resolves `blogPosts.server` to `blog-posts-server-stub.js` whenever `platform !== 'web'`, the same way `sharp` is stubbed; this also keeps `gray-matter`, `markdown-it` and `highlight.js` out of the app bundle. The stub throws rather than returning empty posts, and `utils/__tests__/blogPostsServerNativeStub.test.ts` pins both the resolver rule and the stub's export surface. **Do not "fix" this with a `blogPosts.server.native.ts` platform sibling** — the Jest `node` project uses `@react-native/jest-preset`, whose `haste.platforms` includes `native`, so that file would hijack `utils/__tests__/blogPosts.server.test.ts` and test the stub instead of the real parser. Any new web-only module that imports Node built-ins needs the same treatment.

- The website uses standard HTML elements (`<div>`, `<section>`, `<a>`) and Tailwind/NativeWind utility classes — **not** React Native primitives.
- **Link to another website page with a plain `<a href>`, not expo-router's `Link`.** On web `Link` renders a react-native-web `Text`, which starts a fresh style context: it inherits neither `color` nor `font-size`/`font-weight` from its HTML ancestors, and `group-hover:`/`hover:` classes on it lose to the inline `style` prop that any base color must therefore be set with. The blog list's post titles shipped near-black on a dark card for exactly this reason — an `<h2 className="text-white text-3xl">` wrapping a `Link` styles nothing. The nav in `WebsiteWrapper.web.tsx` still uses `Link` with an explicit inline `color`; that pattern works only because those links need no hover-color change. Reach for `<a>` first, and if you do use `Link`, put every typography and color declaration on the `Link` itself.
- When working on website files, treat them as a standard React web app, not a React Native app.
- Website layout is in `app/(website)/_layout.web.tsx`; it wraps pages with the nav/footer chrome.

**When making changes:**

- Changes to `app/app/` affect the mobile app only.
- Changes to `app/(website)/` affect the public website only.
- Shared logic (services, database, utils) lives outside both and is used by both platforms.

## Tech Stack

- **Framework**: React Native (Expo SDK 57) with Expo Router
- **Styling**: NativeWind (Tailwind CSS). `patches/react-native-css-interop+0.2.6.patch` adds a missing `return` to `parseDeclaration`'s `case "box-shadow"`: without it the switch falls through into `case "aspect-ratio"`, which reads `value.ratio[0]` off a box-shadow value and throws `TypeError: Cannot read properties of undefined (reading '0')` — with a stack trace pointing at `parseAspectRatio`, nowhere near the real culprit. Only a **fully parsed** literal `box-shadow` in `global.css` trips it; Tailwind's own `shadow-*` utilities compile to `box-shadow: var(--tw-shadow), …`, and lightningcss leaves anything containing `var()` unparsed, so they take a different branch. The crash also only hits **native** — `expo export:embed` runs the CSS through css-to-rn, while the web build goes through PostCSS — so a literal box-shadow can look fine on web for weeks and then break the next Android build. Pinned by `utils/__tests__/nativewindBoxShadowPatch.test.ts`; keep the patch until it lands upstream.
- **Database**: WatermelonDB (SQLite for Native, LokiJS for Web)
- **Charts**: Victory Native (Skia) for Native, Victory (SVG) for Web
- **AI**: OpenAI & Google Gemini (Generative AI)
- **Localization**: i18next with `expo-localization`
- **Health Data**: Health Connect (Android) via `react-native-health-connect`. **Do not add `expo-health-connect` back**: it is the same author's _standalone_ config plugin from before `react-native-health-connect` shipped its own, and as of rnhc 4.x both packages register an autolinked Expo module under the **identical** `expo.modules.healthconnect` namespace, so `:app:mergeDexRelease` fails with `Type expo.modules.healthconnect.BuildConfig is defined multiple times` (release-only — the duplicate class never surfaces in a dev/debug bundle). `react-native-health-connect`'s own `app.plugin.js` (listed in `app.json` `plugins`) writes the exact same `ACTION_SHOW_PERMISSIONS_RATIONALE` intent-filter + `ViewPermissionUsageActivity` alias into the manifest, so nothing is lost by dropping the standalone plugin.
- **Error Tracking**: Sentry (`@sentry/react-native`)
- **Food Scanning**: OCR (tesseract.js / rn-mlkit-ocr) and barcode scanning (quagga2 / react-zxing)
- **Camera**: all native camera work goes through `react-native-vision-camera` — the smart camera (barcode / AI food scanning) via the `components/CameraView.tsx` wrapper, and video capture on the reps-recording test screen (`app/app/test/reps-recording.tsx`) using the `Camera` component directly. **Do not add `expo-camera` (or any second CameraX-based library) back**: vision-camera 4.7.3 links against CameraX-internal classes from its pinned CameraX version, and a second library pulling a newer CameraX (e.g. 1.6.0, which removed `Camera2CameraInfoImpl`) wins Gradle resolution and crashes the app at boot with `NoClassDefFoundError` (see git history: `plugins/withCameraXVersionPin.js` briefly worked around exactly this). Two `CameraView.tsx` props are load-bearing for shutter latency and must not be "optimized" away without re-verifying on a **release** build (`npm run build-android-apk-local` + `adb logcat`, filter `CameraView`/`CameraCaptureFlow` — the historical 25s-shutter incident never reproduced in dev builds): `androidPreviewViewType="texture-view"` (the snapshot shutter needs a reliable `getBitmap`; SurfaceView/PixelCopy has device-specific null/black failures that silently reroute into the slow takePhoto fallback) and `photoQualityBalance="speed"` (never "balanced" = CameraX ZSL, which stalls for tens of seconds on some devices and silently downgrades on others, masking the stall in dev). Every shutter press emits phase telemetry; slow or fallback shots surface as Sentry `camera-shutter-*`/`camera-warm-up-*` events.
- **Every capture is cropped; barcode scanning has no shutter at all**: both entry points of `useCameraCaptureFlow` (`hooks/useCameraCaptureFlow.ts`) — a shutter capture and a gallery pick — end in the same `cropAndProcess` step, so the user can trim the shot and `process` only ever receives a cropped image. There is deliberately **no** "skip the crop" option: barcode scanning reads the live preview and offers no manual capture, so the one case that would have wanted it cannot occur. Whether a shutter button exists is the owner's call, expressed by passing or omitting `SmartCameraShell`'s optional `onShutterPress` — `SmartCameraModal` passes `undefined` while `isBarcodeScanning`, `BarcodeCameraModal` never passes one (it only uses `pickFromGallery`). Do not reintroduce a `cropOnShutter`-style flag, and do not make the shell decide this from `cameraMode`. `patches/@bsky.app+expo-image-crop-tool+0.5.1.patch` also moves `openCropperAsync` to `Queues.MAIN` (it only does `startActivityForResult`, a Main-thread op anyway, so it never waits behind the shared background queue described below); keep that patch as cheap defense-in-depth even though the SecureStore fix removes the underlying contention.
- **First gallery pick after boot stalled ~25s — root cause was SecureStore head-of-line-blocking Expo's single-threaded module queue (critical)**: on the **first** gallery pick within ~25s of a cold boot, tapping "load from gallery" showed a ~25s spinner before the picker/crop UI appeared (observed Pixel 10 / Android 17); the second pick — and any pick after idling ~25s post-boot — was instant. A lazy per-call cold start cannot be cleared by merely _waiting_ 25s, which disproves the earlier "one-time native init inside `openCropperAsync`/the system picker" theory. **Confirmed mechanism**: every Expo `AsyncFunction`/`Coroutine` on the default queue runs on ONE shared background thread — `expo.modules.AsyncFunctionQueue`, a single `HandlerThread` (`AppContext.modulesQueue`; see expo-modules-core `AppContext.kt`). `expo-secure-store` 57.0.1's `getValueWithKeyAsync`/`setValueWithKeyAsync` are `Coroutine`s whose `getItemImpl`/`setItemImpl` do **no** `withContext`/`Dispatchers` switch, so their Android Keystore/SharedPreferences work (slow on a cold first access — Keystore init + RSA/AES keygen) runs **directly on that shared thread**, head-of-line-blocking every other default-queue function — including the crop tool's `openCropperAsync` and expo-image-picker's `launchImageLibraryAsync`. Boot reads SecureStore (encryption key + `SettingsService.migrateApiKeysToEncrypted`), so the cold Keystore stall lands exactly when the user first opens the gallery. Corroborated by [expo/expo#34531](https://github.com/expo/expo/issues/34531). **Fix**: `patches/expo-secure-store+57.0.1.patch` moves SecureStore's Android async ops onto a dedicated serial I/O queue (`Dispatchers.IO.limitedParallelism(1)`), off the shared thread. **SDK 57 ships SecureStore as a prebuilt AAR** (`local-maven-repo/…/expo.modules.securestore-57.0.1.aar`), so the patched `.kt` is ignored unless `package.json` keeps `expo.autolinking.android.buildFromSource: ["expo-secure-store"]` — both pieces are load-bearing; revalidate on every Expo/SecureStore upgrade. Two supporting boot-load reductions: `getEncryptionKey()` (`utils/encryption.ts`) coalesces concurrent reads per storage key (also fixes a latent fresh-install race that could generate/persist mismatched keys → undecryptable data), and `SettingsService.migrateApiKeysToEncrypted` is now a `runOnce` boot migration. Do not reintroduce eager duplicate SecureStore reads at startup. The stall only ever reproduces on a **release** build — verify with `npm run build-android-apk-local` + `adb logcat` (filter `CameraCaptureFlow` for the `gallery picker` phase timing).
- **Gallery pick uses the modern system Photo Picker, no permission prompt — one shared entry point app-wide**: `utils/galleryImagePicker.ts` exports `pickImageFromGallery` (calls `ImagePicker.launchImageLibraryAsync` with no `legacy` flag, opening Android `ACTION_PICK_IMAGES` / iOS `PHPicker` — both return only the user-picked item through a temporary content grant and need **no** media-library permission, so callers must not add a `requestMediaLibraryPermissionsAsync` check back in) and `pickAndCropImageFromGallery` (composes `pickImageFromGallery` with `openCropperAsync` from `utils/file.ts`, returning the cropped path or `null` if either step is cancelled). `legacy: true` (the old `ACTION_GET_CONTENT` document UI) was a failed workaround for the stall documented below (the picker component was never the cause) and must not be reintroduced. `pickImageFromGallery` has no platform-specific behavior — expo-image-picker works the same way on web (a hidden `<input type=file>`) — so unlike `openCropperAsync` it deliberately has **no** `.web.ts` counterpart; do not reintroduce one. **`pickImageFromGallery` takes no quality argument and picks at `quality: 1`**: every caller re-encodes through `openCropperAsync`, so compressing at the pick step too would stack a second lossy pass (a requested `0.8` actually landing at ~`0.64`). The crop step is the single place output quality is chosen — `pickAndCropImageFromGallery(compressImageQuality)` and `useCameraCaptureFlow`'s `quality` option both mean exactly that. This matters most on the smart-camera path, where the photo must stay legible for OCR and barcode decoding. Every gallery-pick entry point in the app shares these two functions — `CoachModal` (chat image attachments — previously used `expo-document-picker`'s file browser, which felt inconsistent with the rest of the app), `CreateMealModal`, `CreateCustomFoodModal`, and `CreateExerciseModal` call `pickAndCropImageFromGallery` directly; `hooks/useCameraCaptureFlow.ts` (`pickFromGallery`, smart camera modals) calls `pickImageFromGallery` and `openCropperAsync` separately because it needs distinct phase-timing logs and error messages for each step — so every "pick from gallery" flow in the app has the identical picker + crop UX. Do not call `ImagePicker.launchImageLibraryAsync` directly from a new call site; add it to `pickAndCropImageFromGallery`'s callers instead. `useCameraCaptureFlow`'s `pickFromGallery` still logs the `gallery picker` phase timing (`adb logcat`, release build) so a residual queue stall would still surface.
- **Export**: xlsx + html-to-image for data export features
- **Dependency pin**: `@babel/plugin-transform-react-jsx` is pinned exactly (`7.29.7`, in `optionalDependencies`) — added during the SDK 57 upgrade without a recorded reason; every consumer (`babel-preset-expo`, `@react-native/babel-preset`) currently dedupes to it. Treat it as a suspected workaround: on the next Expo upgrade, try removing it, verify `npm ls @babel/plugin-transform-react-jsx` still resolves a single copy, and confirm the app bundles.

## Coding Guidelines

### Architecture

- **No barrel files or re-export-only wrappers**: Import implementations directly from their owning files. Do not create `index.ts` aggregation modules, files whose only purpose is to re-export another module, or platform wrappers that merely alias a shared component. A barrel is allowed only when an external package boundary or framework API explicitly requires that exact entry point; document that requirement in the file.
- **Keep documentation in sync (required)**: When a change alters behavior, architecture, file layout, or any invariant, update the docs in the same change — this `AGENTS.md`, the relevant files under `docs/`, `README.md`, and any code comments that name files/functions you moved or renamed. Treat a doc that names a file, function, flag, or approach that no longer matches the code as a bug to fix, not to leave. If a `docs/` plan describes an approach that was superseded, rewrite it to reflect what was actually built (or mark it superseded) rather than leaving the stale plan. Do not add docs for trivial changes, but never let an existing doc drift out of date.
- **Feature list sync (required)**: Whenever a new user-facing feature is added or an existing one is removed or significantly changed, update `FEATURES.md` to reflect it. If the change also affects the high-level summary in `README.md` (Key Features section), update that too. `FEATURES.md` is the source of truth for the complete feature list; `README.md` contains a curated subset — both must stay accurate.
- **Tests are required for every behavior change**: Every new feature, bug fix, or change to existing behavior must include appropriate automated test coverage. Add a new regression test or update the existing tests so they verify the intended behavior and would catch the bug or regression. Run the relevant test suite, along with type checking and any applicable lint or translation checks, and make sure it passes before considering the work complete. Never weaken, delete, or skip a valid test merely to make a change pass; update expectations only when the intended behavior has genuinely changed.
- **Layered Structure**: Schema (`database/schema.ts`) -> Models (`database/models/`) -> Repositories (`database/repositories/`) -> Services (`database/services/`).
- **Repositories**: Complex queries live in `database/repositories/` (e.g., `WorkoutLogRepository`, `MenstrualCycleRepository`). Prefer repositories over direct model queries for non-trivial reads.
- **App Services**: Non-database services (AI, notifications, Health Connect sync) live in top-level `services/`.
- **Data Persistence**: Use WatermelonDB for local storage. Ensure models are registered in `database/database-instance.ts`.
- **Calendar day keys**: Fields that represent a calendar day (`user_metrics.date`, diary pickers) store **local** midnight ms. Use `utils/calendarDate.ts` (`localDayStartMs`, `localDayHalfOpenRange`, etc.); do not use `Date.UTC` or `setUTCHours(0, …)` for those stored values.
- **`nutrition_logs.date` is a consumed datetime**, not a day key: it stores the local **datetime** (day + time-of-day) the food was consumed in ms, so the time-of-day is preserved. Calendar-day grouping/filtering still goes through `utcNormalizedDayKey` / `dayKeyRange` (with `dayRangeClauses` from `database/dayKeyQuery.ts` for the widened DB clauses and `range.filterRecords` to trim the overscan), which re-apply the stored `timezone` offset and strip to Y/M/D, so day-based reads are unaffected. When writing it, combine the picked day + time with `combineLocalDateAndTime` (or `instantForDateTimeInTimezone` to anchor to a record's stored timezone); use `withCurrentTimeOnDay` for non-interactive "log now for this day" paths. Never floor it with `localDayStartMs`. `created_at` is strictly the record-creation instant and `updated_at` the last-update instant — do not read consumed time from them.
- **Encryption**: Sensitive metrics (weight, body fat) and nutrition logs must be encrypted/decrypted using helpers in `database/encryptionHelpers.ts`.
- **Food quality badges (Nutri-Score / Eco-Score / NOVA / labels)**: Never re-inline a provider's field names (`nutriscore_grade`, `ecoscore_grade`, `nova_group`, …). Each source normalizes into `FoodDisplayQuality` (`utils/foodDisplayQuality.ts`) exactly once, at its own mapper — `getOffDisplayQuality` (`utils/openFoodFactsMapper.ts`), `getMusclogDisplayQuality` (`utils/musclogProduct.ts`) — and UI reads them through `getExternalProductDisplayQuality(source, details)` in `utils/externalFoodProduct.ts`, passing a source already resolved by `inferBarcodeNutritionSource`/`resolveExternalFoodSource` rather than re-sniffing product shapes. `foodRecordDisplayQuality` reads the badges back off a stored food (or a mapped search result); `applyDisplayQualityToFoodRecord` writes them on the save path. USDA carries no quality data and resolves to `undefined`.
- **Unit system (metric / imperial)**: The database **always** stores metric values (kg, cm, g, kcal). Users choose metric or imperial in settings (`SettingsService.getUnits()`). Conversion helpers live in `utils/unitConversion.ts`:
  - **Saving user input → DB**: Convert display values to metric with `displayToKg`, `displayToCm`, `displayToGrams`, or the generic `displayValueToMetric(value, metricType, units)`.
  - **Reading DB → display**: Convert metric to display with `kgToDisplay`, `cmToDisplay`, `gramsToDisplay`, or the generic `metricValueToDisplay(value, metricType, units)`.
  - **Unit labels**: Use `getWeightUnit(units)`, `getHeightUnit(units)`, `getMassUnitLabel(units)`, or `metricDisplayUnit(metricType, units)` — never hardcode "kg", "lbs", "g", "oz" in UI.
  - **Type classification**: `isWeightMetricType(type)` (kg↔lbs: weight, muscle_mass, lean_body_mass) and `isLengthMetricType(type)` (cm↔in: height, chest, waist, hips, arms, thighs, calves, neck, shoulders).
  - **No conversion needed**: Macros (protein, carbs, fat, fiber) are always in grams, calories in kcal, body fat / BMI / FFMI are unitless — these stay the same in both systems.
- **Carbs vs fiber convention (critical)**: There are two conventions in the codebase — **do not mix them**:
  - **Food items / nutrition logs** (`NutritionLog`, `inferCaloriesFromMacros.ts`, `NutritionCharts.tsx`, food DB mappers): `carbs` = total carbohydrates **including** fiber, matching the US nutrition label standard. Digestible carbs = `carbs − fiber`. Use `digestibleCarbs(carbs, fiber)` from `utils/carbsConvention.ts` (never re-inline `Math.max(0, carbs - fiber)`) for energy and for comparing consumed carbs against the (net) carbs goal — the carbs progress bar must show digestible carbs so it doesn't double-count fiber, which has its own bar.
  - **Source carbs are not all "total" — normalize at ingestion** (`utils/carbsConvention.ts`): the "carbs = total incl. fiber" invariant is **established at ingestion**, not assumed. All food-source mappers **must** run `carbs` through `totalCarbsForFoodSource(source, …)` before storing (it looks the source's convention up in `FOOD_SOURCE_CARBS_CONVENTION`, so a convention change is a one-line edit). Per-source conventions, verified against the standards (June 2026):
    - **USDA** `Carbohydrate, by difference` (1005) already includes fiber → `'total'` (no transform, but still routed through the helper for a future-proof entry point). <https://fdc.nal.usda.gov/>
    - **US/Canada (FDA)** "Total Carbohydrate" is by-subtraction and includes fiber. [21 CFR 101.9(c)(6)](https://www.ecfr.gov/current/title-21/section-101.9)
    - **EU (Reg. 1169/2011, Annex I)** declares _available_ carbohydrate (fiber **excluded**, fiber counted at 2 kcal/g) → `'net'` (total = carbs + fiber). <https://eur-lex.europa.eu/eli/reg/2011/1169/oj> · [US-vs-EU explainer](https://blog.trustwell.com/how-carbs-are-calculated-in-different-countries)
    - **OpenFoodFacts** stores a single `carbohydrates` field without recording the convention, so it is mixed → `'off-mixed'`, resolved in three steps: (1) prefer `carbohydrates-total`; (2) else reconcile the **stated label energy** against both interpretations (they differ by exactly `4 × fiber` kcal/100g) and keep `carbs` as-is only when the energy clearly fits the total interpretation; (3) else assume EU/net and add fiber. Step 2 is conservative — pass the raw stated kcal, never an inferred one. [openfoodfacts-server#5675](https://github.com/openfoodfacts/openfoodfacts-server/issues/5675)
    - **Musclog REST API** scrapes EU (Dutch) supermarkets (Albert Heijn, Lidl, Jumbo, …) mapping the label "Koolhydraten" (available carbohydrate) → `carbs` → `'net'`. If its upstream ever changes, update the `musclog` entry in `FOOD_SOURCE_CARBS_CONVENTION`.
    - **AI / LLM estimates** (`'ai'` → `'net'`): the macro-estimation prompt's energy note (`kcal = 4·carbs + 2·fiber`, `utils/prompts.ts`) is the net convention, so the model returns net carbs. Every AI persistence path (`NutritionService.logCustomMeal`/`logCustomMealsBatch`, `nutritionAI.ts`, `MyMealsModal`) **must** run AI carbs through `totalCarbsForFoodSource('ai', …)` before storing.
    - **Manual entry** (`CreateCustomFoodModal`): the user picks, via the `INCLUDE_FIBER_IN_CARBS_SETTING_TYPE` setting (Advanced settings → Nutrition; seeded from units in `prod.ts` — imperial/US label = include fiber, metric/EU label = exclude), whether the typed carbs field already includes fiber. Convert with `totalCarbsFromSource(manualEntryCarbsConvention(includeFiberInCarbs), …)` before saving; the field label + hint copy follow the same setting.
  - **User nutrition goals** (`NutritionGoalsBody`, saved goal records, onboarding results): `carbs` = **net/digestible carbs only** (fiber is a separate, additive macro). Total calories = `protein * 4 + carbs * 4 + fats * 9 + fiber * 2`. Never subtract fiber from carbs in this context.
  - **Food serving weights**: Stored in grams, displayed as g or oz. Use `gramsToDisplay`/`displayToGrams` and `getMassUnitLabel`. The `ServingSizeSelector` component handles this automatically.
  - **Every new feature** that displays or accepts weight, height, body measurements, or food serving sizes **must** use these conversion helpers. Test with imperial mode enabled.
- **`loadMultiplier` is a bodyweight-relative load benchmark, not an intensity knob**: it is the load a trained lifter typically works with on that exercise, expressed as a multiple of bodyweight and measured the way the app logs it (per hand for dumbbells). The scale is anchored by the entries already in `data/exercisesData.json`: Deadlift 1.8, Squat 1.4, Bench Press 1.0, Chest Press Machine 0.9, Lat Pulldown 0.7, Overhead Press 0.6, Barbell Curl 0.42, Leg Press 3.5, Lateral Raise 0.10. Both consumers depend on that reading — `utils/workoutEnergyCalculator.ts` scales mechanical work by it, and `utils/exerciseGoalProjection.ts` computes `estimated1RM / (bodyWeight * loadMultiplier * genderFactor)` and calls the lifter advanced above 1.5.
  - **Derive a new value from the closest movement already in the catalogue, never from the equipment type.** A cable variant takes its anchor's value outright; the only permitted discounts are for a real biomechanical difference — unsupported stance (`x0.75`, stance and anti-rotation become the limiter) and unilateral loading (`x0.55`). Being a cable is not itself a reason to discount, and "the stack caps out lower" is not either: the logged weight is already in every formula, so discounting the multiplier for it double-counts. The cable catalogue originally carried a flat 0.5 ceiling for every movement, putting Cable Chest Press at 0.3 against Chest Press Machine's 0.9 and Cable Belt Squat at a third of the Belt Squat Machine it mirrors. `data/__tests__/exercisesData.test.ts` pins the parity ratios and the two discount directions, so a category-wide clamp fails the build.
  - **For a bodyweight exercise the multiplier is not a benchmark — it is the fraction of body mass the movement actually shifts**, and it is derived, not estimated. Segment masses come from [de Leva (1996)](<https://doi.org/10.1016/0021-9290(95)00178-6>), adjusting Zatsiorsky-Seluyanov: a pull-up lifts the whole body less the hands (`1 - 2 x 0.0061 = 0.99`), a hanging leg raise lifts both legs (`2 x (thigh+shank+foot) = 0.41`), a quadruped glute kickback one leg (`0.20`). The push-up family is measured on force plates instead — [Suprak, Dawes & Stephenson (2011)](https://pubmed.ncbi.nlm.nih.gov/20179649/) report 69% of body mass at the top of the ROM and 75% at the bottom, so it is stored as `0.70`. **Do not add per-user anthropometrics to this**: body mass and height cancel out of the derivation (the fractions are fractions _of_ body mass, and `workoutEnergyCalculator` already multiplies by `weightKg` and `heightCm`), and sex moves the fractions only 0.1–6% — under the model's own noise floor, with `genderFactor` already applying a blanket adjustment. Store sex-neutral values.
  - **A stored `0` means "no displacement to credit", and it must stay a hard zero.** It is reserved for isometric holds (plank, side plank, wall sit, hollow body hold) and cardio: the model is `mass x distance x reps` and a hold has no distance. Coercing a non-positive multiplier to a neutral `1` in the calculator — the first attempt at the bodyweight fix — scores a plank like a full-bodyweight rep, so the fix belongs in the data, not in a fallback. `utils/exerciseGoalProjection.ts` is the exception and still guards its divisor, because there `0` would produce `Infinity` and tier every such goal as advanced (`?? 1.0` does not catch a stored `0`).
- **`muscle_group` holds two vocabularies and readers must handle both**: the bundled catalogue and `CreateExerciseModal` write the coarse names (`legs`, `arms`, `core`, `abdomen`, … — `EXERCISE_JSON_MUSCLE_GROUPS` in `database/services/ExerciseService.ts`), while exercises migrated from the legacy database carry fine-grained ones (`quads`, `biceps`, `abs`, …). The `MuscleGroup` union in `database/models/Exercise.ts` is the single place both are enumerated. **Never match group names yourself** — go through `muscleGroupFamily(group)` / `MUSCLE_GROUP_FAMILY` in `database/models/muscleGroupFamily.ts` (a separate, WatermelonDB-free file so pure consumers can import it as a value), which collapses both vocabularies into one body region. A hand-written `Set<MuscleGroup>` that names only one vocabulary is a silent, total failure rather than a type error: `workoutEnergyCalculator`'s `LEG_GROUPS` listed only the fine-grained names, so all 60 bundled leg exercises — every one stored as `legs`, none as `quads` — fell through to the generic branch and lost both the longer leg displacement and the `0.88x` bodyweight contribution. Because `MUSCLE_GROUP_FAMILY` is a `Record<MuscleGroup, …>`, widening the union fails the build until the new name's family is declared, and every consumer stays correct for free.
- **Translation**: Check the `lang` directory for translation files. Any new feature implemented must use translation keys and add new keys to the translation files for all available languages. Bundled workout definitions live in `data/workoutTemplatesData.json`; locale-specific copy lives in `data/workoutTemplatesEnUS.json`, `workoutTemplatesEsEs.json`, `workoutTemplatesNlNl.json`, `workoutTemplatesPtBr.json`, and `workoutTemplatesRuRu.json`. `scripts/generateLangFile.js` discovers those copy files and generates `WORKOUT_TEMPLATE_COPIES_BY_LOCALE` in `lang/lang.ts`; `data/workoutTemplates.ts` uses that catalog to merge the active locale's copy by array index and fall back to `DEFAULT_LANG`, so every locale copy file must preserve the definition file's order. Template difficulty is structural data using the lowercase identifiers `beginner`, `intermediate`, and `advanced`; locale files must not duplicate it, and UI translates the identifier only when rendering its label. The definition file's `__title` is a maintainer reading aid only — it is typed on `RawWorkoutTemplateDefinition` (never on `RawWorkoutTemplate`) and `applyWorkoutTemplateCopies` strips it, so titles can only come from the locale copy files; do not rename it back to `title` or read it anywhere.
- **User-visible numbers**: Format with `Intl` via `hooks/useFormatAppNumber.ts` (components) or `utils/formatAppNumber.ts` (pure code), using locale `i18n.resolvedLanguage ?? i18n.language`. Do not use `toFixed`, raw `{n}` in JSX, or `toLocaleString()` without an explicit locale for display. Keep `roundToDecimalPlaces` / DB math separate from display.

### WatermelonDB Usage

- **Transactions**: All writes must be wrapped in `database.write(async () => { ... })`.
- **Avoid Deadlocks**: Never nest `database.write()` calls. Methods decorated with `@writer` should not be called from within another write block.
- **Read-then-write must be atomic (no TOCTOU)**: When a write's contents depend on a prior read (e.g. "insert only the rows that don't already exist yet", "seed if missing"), do that read **inside the same `database.write()`** as the write — never read outside the writer and then write. WatermelonDB serialises write blocks, so a read outside the writer leaves a time-of-check/time-of-use window where two concurrent runs both observe the pre-write state and issue conflicting writes. This bit us in production (builds 270/272): `ExerciseService.syncAppExercises` read the existing exercises outside its writer, so a re-entrant boot could re-insert a bundled exercise's fixed primary key and throw `sqlite error 1555 (UNIQUE constraint failed: exercises.id)`. If you need a cheap early-out, an outside read is fine **only** as a best-effort optimization — repeat the authoritative check inside the writer (see `syncAppExercises`). Guarded by `database/services/__tests__/ExerciseService.test.ts`.
- **Web Compatibility**: On web, `unsafeResetDatabase()` must also be wrapped in a write block.
- **JSON Fields**: Use the `@json` decorator for complex object fields (e.g., `@json('micros_json')`, `@json('week_days_json')`). Keep a plaintext date field alongside encrypted fields when the date is needed for DB queries.
- **Raw SQL — never open expo-sqlite on `musclog.db` (critical, data loss)**: expo-sqlite and WatermelonDB bundle separate SQLite libraries, and POSIX locks never conflict within one process — so an expo-sqlite connection that **closes** always thinks it's the last connection and unlinks the live `-wal`/`-shm` files under WatermelonDB. WatermelonDB then keeps committing into the unlinked file and every commit since the unlink silently vanishes when the process is killed (June 2026 field incident: users lost nutrition logs, no tombstones). Any raw SQL while the app is running must go through `rawQueryViaWatermelon` in `database/wmdbRaw.ts` (reads/PRAGMAs) or `database.adapter.unsafeExecute` (writes). The only native exception that may open expo-sqlite on `musclog.db` is `preparePreMigrationBackupBeforeAdapter()` in `database/preMigrationCapture.ts` (a native-only module imported solely by `database/adapter.ts` before `new SQLiteAdapter`); it reads `user_version` and, **only when a data-touching migration is pending** (purely-additive `createTable`/`addColumns` migrations skip the snapshot so upgrade boots stay fast — gated by `pendingMigrationsCanTouchExistingData` in `database/migrationSafety.ts`), writes a consistent `.db` snapshot with **`VACUUM INTO`** (near-instant — the WAL is folded in, so a session killed with uncheckpointed commits is still captured; far faster than reading every row to JSON, which used to stall upgrade boots for minutes), then closes the raw connection and lets WatermelonDB open the file. `database/preMigrationBackup.ts` registers that `.db` snapshot and, when captured successfully, an AsyncStorage sidecar from the same boot moment. The snapshot is converted to the portable JSON export format **lazily** — only if the user restores or downloads it — by `database/sqliteBackupConvert.ts`, which opens the _copy_ (a different file, so rule #4 below applies), never the live DB, and injects the captured sidecar instead of reading live AsyncStorage (or omits AsyncStorage if no sidecar exists). That isolation is deliberate — the runtime backup module imports no expo-sqlite at all, so the invariant is structural. A **different** db file (the `.db` snapshot, the legacy `workoutLoggerDatabase.db`) may be opened with expo-sqlite at runtime — the hazard is specific to the _live_ `musclog.db`. Do not open expo-sqlite on `musclog.db` during migration callbacks, after boot, or from new paths. Full incident write-up and root cause: `docs/DATABASE_DURABILITY.md` — read it before adding any raw SQLite access.
- **Boot-time DB-ready gate**: `seedProductionData()` calls `unsafeResetDatabase()` on a fresh install, which temporarily swaps the real adapter for an `ErrorAdapter` that throws `"Cannot call database.adapter.underlyingAdapter while the database is being reset"` on any query. Any code that runs at app startup (e.g. inside a `useEffect` in `AppBoot.tsx`) and touches the DB **must** await `waitForDbReady()` from `database/dbReady.ts` before issuing queries. `seedProductionData()` calls `markDbReady()` when it finishes (both the fast-path and the full reset+seed path).

### Component Design

- **Theme**: Use components from `components/theme/` and follow `theme.ts` conventions.
- **Navigation destinations are table-driven — adding one is a data edit, not a new JSX branch**: `NAV_ITEM_KEYS` (`constants/settings.ts`) is the ordered, canonical list and `NavItemKey` is **derived** from it (`(typeof NAV_ITEM_KEYS)[number]`), so the type and the enumeration can never drift. Everything else hangs off that:
  - `NAV_DESTINATIONS` (`components/navigation/navDestinations.ts`) holds each destination's icon, bottom-bar `labelKey`, account-menu `menuLabelKey` and `route` — the facts **all three** listing surfaces need. A destination picks its icon and route exactly once.
  - `NAV_SLOTS` (`components/NavigationMenu.tsx`) holds only bottom-bar routing modifiers (`activePath` when it must be broader than the route, `alsoActiveFor`/`replace`/`prefetch`/`navigateWhenActive`); every slot renders through the one `NavSlotButton`.
  - `UserMenuModal` maps `USER_MENU_ORDER` (a `satisfies NavItemKeyList` tuple — the length constraint makes a forgotten destination a build error) and reads icon/label/route from `NAV_DESTINATIONS`; only the per-item icon _tint_ is local to that menu.
  - `VisualSettingsModal` filters `NAV_ITEM_KEYS`; `ALWAYS_AVAILABLE_ITEMS` (`hooks/useNavigationItems.ts`) filters it too, rather than restating it.
  - Availability has **one** definition: `isNavItemAvailable(item, isCycleActive)` exported from `hooks/useNavigationItems.ts`. Do not re-inline a `item === 'cycle' && !isCycleActive` check; three copies previously drifted.

  **Do not add another `case` to `renderNavSlot`, another per-destination JSX block to `UserMenuModal`, or another `NavItemKey[]` literal.** The two deliberate exceptions stay explicit branches: `coach` (`route: null` — it opens a modal, so every surface supplies its own handler and it renders `CoachUnreadBadgeIcon` for the unread badge) and `cycle`'s `isCycleActive` gate. The `Record<NavItemKey, …>` maps are compiler-enforced — widening `NAV_ITEM_KEYS` fails the build until each is filled in — whereas a plain array literal silently goes stale, which is why lists are either derived or typed `NavItemKeyList`.

- **Charts**:
  - Always provide a `.web.tsx` counterpart for `victory-native` components to avoid Skia errors.
  - Use absolute positioning for axis labels to maintain consistency across platforms.
  - Use `ChartTooltipContext` (`context/ChartTooltipContext.tsx`) for coordinated tooltip behavior.
- **Segments**: Use `SegmentedControl` for mode switching (e.g., 7D/30D/90D).
- **Surface color**: Components that fade content out to "whatever is behind me" (collapsed accordions, scroll shadows) must read `useSurfaceColor()` from `context/SurfaceColorContext.tsx` instead of assuming `theme.colors.background.primary` or taking the color as a prop. `BottomPopUp` publishes its sheet surface via `SurfaceColorProvider`; any other container that paints its own background should do the same. Related Android constraint: content rendered inside such a fade (e.g. `NutritionQualityData`'s score badges) must not use `elevation` — Android composites elevated views in a separate Z pass that can paint above the later, non-elevated overlay, leaking color through the fade. Use the iOS `shadow*` props alone.
- **Keyboard avoidance**: Any screen or modal that contains a `TextInput` (or any input component wrapping one) inside a scroll container **must** use `KeyboardAwareScrollView` from `react-native-keyboard-controller` instead of RN's plain `ScrollView`. `KeyboardProvider` is already mounted at the app root (`app/app/_layout.tsx`). Two patterns to apply:
  - **Full-screen layouts / screens** (`FullScreenModal` with `scrollable={true}`, plain screens): replace the outermost `ScrollView` with `KeyboardAwareScrollView` and add `bottomOffset={16}`.
  - **Bottom sheets** (`BottomPopUp`): the sheet itself lifts via `marginBottom` in `BottomPopUp.tsx` — no extra work needed for the default `scrollable={true}` case. The lift clears the **whole sheet** (via `computeKeyboardSheetLift` in `components/keyboardSheetLift.ts`), not just the focused input, so submit buttons and footers rendered below the input stay visible; it is capped so the sheet header never leaves the screen, unless a sheet is too tall to clear the keyboard at all, in which case showing the focused input wins. Do not narrow it back to an input-only lift. If you use `scrollable={false}` and add your own inner `ScrollView` with inputs, replace that inner `ScrollView` with `KeyboardAwareScrollView bottomOffset={16}` (see `EditPastWorkoutDataModal.tsx` as an example).
  - Never use RN's `KeyboardAvoidingView` for new code — it has known issues with edge-to-edge on Android (Expo SDK 54+).
  - **Never pass `contentContainerClassName` to `KeyboardAwareScrollView`** — put the padding/gap classes on an inner `View` instead. NativeWind maps that prop only for the components `react-native-css-interop` registers (RN's `ScrollView`, `FlatList`, `VirtualizedList`, `KeyboardAvoidingView`); `react-native-keyboard-controller`'s `KeyboardAwareScrollView` is not one of them, so the classes are dropped with no warning and no type error. `CreateEditPlanModal` shipped with `contentContainerClassName="gap-5 px-4 pb-32 pt-6"` and rendered edge to edge with its last row hidden under the footer. Enforced repo-wide by the `local/no-keyboard-aware-content-container-class` ESLint rule.

### AI & LLM Integration

- **Gate every AI-powered affordance on `isAiConfigured` (required)**: Any button, menu item, card action, quick action, or settings row whose only purpose is to reach an LLM feature **must** be hidden when no AI provider is set up. Read `isAiConfigured` from `useSettings()` (`hooks/useSettings.ts`) — the reactive check covering the Musclog free-tier gateway, on-device AI, local LLM, Gemini and OpenAI — and conditionally spread/render the affordance. The established idioms:
  - Menu arrays: `...(isAiConfigured ? [ { /* item */ } ] : [])` — see `app/app/nutrition/food.tsx` (`mealMenuItems`), `components/modals/CreateWorkoutModal.tsx`, `app/app/notes.tsx` (`noteMenuItems`).
  - JSX: `{isAiConfigured ? <AiThing /> : null}` (never `&&` — `local/no-jsx-logical-expression` is an error).
  - Components that take the flag as a prop use `isAiEnabled={isAiConfigured}` (`app/app/index.tsx`, `app/app/workout/workouts.tsx`).

  **The one deliberate exception is navigation**: `useNavigationItems.isItemAvailable` returns `true` for `'coach'` regardless of config, and `UserMenuModal` shows the Coach entry unconditionally, because those are discovery surfaces — tapping them opens `AINotConfiguredModal`, which has an "Open AI settings" CTA. A _nav destination_ may advertise AI; an _action inside a menu or sheet_ must not, because it would dead-end. Do not "harmonize" the two.

  Do **not** use `hooks/useAiEnabled.ts` for new code: it only checks Gemini/OpenAI (missing gateway, on-device and local-LLM users), runs once on mount, and is not reactive. It survives in `app/app/progress.tsx` only behind commented-out code.

- **Structured Output**: Use `makeSchemaStrict` in `utils/coachAI.ts` for OpenAI function calling to ensure `additionalProperties: false`. It does **not** populate `required`; every declared property must be added to the schema's `required` array explicitly or strict OpenAI-compatible providers will reject the schema.
- **Prompts**: System prompts are managed in `utils/prompts.ts`. Append custom user prompts from the `ai_custom_prompts` table.
- **Foundation foods in every prediction**: All LLM functions that predict food or meal macros (`trackMeal`, `generateMealPlan`, `estimateNutritionFromPhoto`, etc.) **must** read `SettingsService.getSendFoundationFoodsToLlm()` and pass the result to both the system prompt (`getFoundationFoodsPrompt()`) and the function schema (add `foodId` to ingredient properties). This applies to any new prediction feature too.
- **Foundation food matching**: When foundation foods are enabled, the LLM may match ingredients to existing DB foods and return their `foodId` with **zero macros** — it expects the caller to look up real values. Always call `NutritionService.normalizeAiMealIngredients(ingredients)` on the result before saving or displaying. For ingredients with a `foodId`, reuse the existing food record directly instead of calling `FoodService.createCustomFood`.

### Feature Highlights

- **Workout plans and schedule ownership**: `workout_plan_templates` is the only plan-membership store; templates deliberately have no `plan_id`, because one workout may belong to several plans. `workout_plans.cycle_type` selects the membership field that matters: weekly plans use `week_days_json`, rotating plans use `position` and must clear weekdays. Plan fields plus their full membership replacement are one aggregate write through `WorkoutPlanService.savePlan`, which is deliberately the ONLY way to change an existing plan — there is no `updatePlan`/`setPlanMemberships` pair to split them with, because committing a cycle-type change without the weekday clearing it implies leaves weekdays on a rotating plan. JSON and AI program generation likewise goes through `WorkoutTemplateService.createPlanWithTemplates`, which prepares every child template AND the parent plan and commits them in a single `database.batch` — one writer is not enough, because WatermelonDB serialises writers but never rolls back a batch that already landed, so a template-by-template loop that failed on the plan left orphaned workouts behind. `saveTemplate` is built the same way: it reads first, then prepares, then commits one batch. `SaveTemplateData.planIds` preserves a load-bearing distinction: `undefined` leaves memberships alone, while `[]` unfiles the template—never default it to `[]`. Membership diffs performed from `saveTemplate` use `WorkoutPlanService.prepareSyncTemplateMemberships`, which returns `{ activePlanIds, records }` — prepared records because `saveTemplate` already owns the writer and WatermelonDB writers must not nest, plus the membership set the template will have once they commit. Plan liveness is checked for BOTH halves of that diff — an id being added and an id an existing junction row already points at — so a membership left behind by a vanished plan is retired rather than making the workout look planned to a plan that is gone. Calendar ownership is contextual and never mirrored: active weekly memberships supply planned weekdays; `schedules` applies only to templates with zero active plan memberships; a rotating or unscheduled planned workout must not fall back to a dormant standalone schedule. **That rule is enforced on write, not only on read, and on EVERY membership path**: `saveTemplate` resolves membership _before_ writing schedules (via `prepareSyncTemplateMemberships`, or `WorkoutPlanService.getActivePlanIdsForTemplate` when `planIds` is omitted and there are days that would otherwise be written) and skips standalone `schedules` entirely when the template will belong to a plan; and `createPlan`/`savePlan`/`setTemplatePlans` soft-delete the standalone `schedules` of every workout they file, in the same batch, via `WorkoutPlanService.prepareStandaloneScheduleCleanup`. Filing a scheduled workout into a plan from the plan editor used to merely hide its schedule, which then reappeared the moment the workout left the plan. Do not move the schedule block back above the membership block: writing both stores leaves dormant rows that the notification resolver ignores while a membership exists, then silently resurrects if the workout later leaves the plan. `workout_templates.week_days_json` is deprecated compatibility data: normal saves clear it, and editing a legacy row materializes its effective days into standalone `schedules`. `workout_logs.plan_id` is stamped at session start but remains write-only for analytics in this version. Bundled programs create rotating plans and name their workouts by day only. The route-level workout library screen remains an orchestrator; filtering, grouped plan sections, empty/loading states, and card rendering belong in `components/workout/WorkoutLibraryContent.tsx`, which runs `groupTemplatesByPlan` exactly once and renders its flat layouts by passing `plans: []` — do not reintroduce a parallel `filteredTemplates` pass, which has to re-implement the type filter and the search matcher and drifted from both. "Which plans is this workout in?" is one flow, `components/workout/usePlanAssignment.tsx`, shared by the library screen and `CreateWorkoutModal`; a plan created from its picker is seeded with the workout via `CreateEditPlanModal`'s `initialTemplateIds`, so the plan and its first membership are one `createPlan` call rather than a create followed by a second write that can fail on its own.
- **Weekly Progress Check-ins**: Managed via `NutritionCheckinService`. Periodic targets are generated upon goal setting. Trends are analyzed based on 7-day rolling data (weight, calories, activity).
- **Exercise Reordering**: Workout log exercises have an `order` field. Use `ExerciseService.reorderWorkoutLogExercises()` to persist new order. Works on both in-progress and past workouts.
- **Superset / Exercise Grouping**: Workout log exercises and sets share a `group_id` (optional). Exercises with the same `group_id` are treated as a superset.
- **Meal Grouping**: Nutrition log entries share a `group_id` to display AI-generated or saved meals as a single meal item instead of individual ingredients.
- **Fasting Days (opt-in)**: Gated behind `ENABLE_FASTED_DAY_SETTING_TYPE` (`enable_fasted_day`, default off; Advanced settings → Nutrition). Lets the user flag a day with **no logged food** as an intentional fast, persisted in the `fasted_days` table (one soft-deletable row per day, `date` + `timezone` stamped like `nutrition_logs` so `utcNormalizedDayKey(date, timezone)` shares the exact bucket space). All access goes through `FastedDayRepository` (`markFasted`/`unmarkFasted`/`isFasted`/`getFastedDayKeys`/`getAllFastedDayKeys`). **Unified denominator rule** (only applied when the setting is on): every historical macro/calorie **average** divides the period total by the `effectiveDayCount` from `getNutritionDayCoverage()` (`database/nutritionDayCoverage.ts`) = **distinct days with logged food ∪ distinct flagged fasted days**. Unflagged empty days (a forgotten log) are excluded; a flagged fasted day is a real 0-kcal day included in the denominator. This makes the previously-inconsistent divisors converge across `NutritionService.getRangeNutrients` (home weekly card + AI range), `getHistoricalNutritionParams` / empirical TDEE, `ProgressService.calculateInsights` (fasted days are injected into `nutritionDaily` as 0-kcal entries, so averages/weekly/correlation/mood/empirical-TDEE all count them), and `NutritionCheckinService.getCheckinMetrics`. Fasted days also count as logged days for `getMacroLoggingStreak`/`getNutritionStreak` (streak preserved); mark/unmark busts the `MACRO_STREAK_STATE` cache. UI lives in the food diary (`app/app/nutrition/food.tsx` + `components/nutrition/FastingDayCard.tsx`): the mark/unmark affordance appears only on empty, non-future days when the feature is on (for the current day it is offered only from 20:00 local time — `FASTING_DAY_TODAY_MIN_HOUR` in `hooks/useFastingDay.ts` — so a not-yet-eaten morning isn't prompted as a fast), confirmed via `ConfirmationModal`. When the setting is **off**, every calc site keeps its exact legacy behavior and no `fasted_days` rows are consulted.
- **Optical Transfer (phone-to-phone over light)**: moves a whole profile between devices with no network — one screen streams fountain-coded QR frames, the other camera reads them. Entry point is a `SettingsCard` in `DataSettingsModal`'s Data Portability section → `OpticalTransferModal` → `OpticalSendModal` / `OpticalReceiveModal`. All logic lives in `utils/optical/` (pure, no RN imports, so it runs in the Jest `node` project); Skia and the camera are isolated in `components/optical/`. **Read `docs/OPTICAL_TRANSFER.md` before touching any of it** — it records the on-device measurements the design rests on. The invariants that bite:
  - **`fountain.ts` and `frameProtocol.ts` are FROZEN wire format**, ported verbatim from [decimen-optical-transfer](https://github.com/bashalarmistalt/decimen-optical-transfer)'s **MIT** releases (v0.3.0 and earlier). Upstream relicensed to **AGPL-3.0-or-later at v0.4.0** (2026-08-09), so do not pull fixes or new helpers from v0.4.0+ into `utils/optical/` — that would import AGPL code into this app. See `docs/OPTICAL_TRANSFER.md`. The two phones in a transfer can be running app versions months apart and derive every frame's block subset independently with no handshake, so these are compatibility contracts with our own past releases. `dlog()` exists because `Math.log` is implementation-approximated in ECMAScript — replacing it, or shortening its 21-term series, silently breaks every future transfer with no error, just a bar that stops. `utils/__tests__/opticalFountain.test.ts` holds decimen's golden vectors; a failure there is a broken format, not a broken test, and needs a header version bump rather than a re-recorded constant. Jest runs on V8, so the Hermes sweep in the bench screen is the other half of that guarantee. **All format evolution goes in `container.ts`**, whose version byte is checked _after_ reassembly and so can say "update the other phone".
  - **Frames are armored to text with base44, never sent as bytes.** vision-camera's `Code` is `{ value?: string }` — there is no byte array — and MLKit's `rawValue` is null for non-text payloads. The alphabet is QR's alphanumeric set minus space, which keeps symbols in ALPHANUMERIC mode (3.1% cost, vs 25% for base64); space is excluded so no whitespace trimming can eat a frame. Do not switch to byte mode without shipping a native decoder.
  - **The sender cannot measure what limits the transfer, so density is both capped and user-overridable.** `calibrateDevice()` runs on the sending phone, but the constraint lives on the _receiving_ phone's camera (autofocus, sensor, lighting) — and an undecoded frame still counts as sent, so no sender-side measurement can even see the failure. On Android the code-scanner analyzer is a bare `ImageAnalysis.Builder().build()` with no ResolutionSelector, so it runs at CameraX's ~640×480 default and `format` cannot raise it (measured: 640×480). Goodput is nearly density-_invariant_ when encode-bound (QR capacity and encode cost both scale with modules²) while autofocus tolerance collapses as density rises, so density buys nothing and costs reliability — a field transfer at `dense` took **an hour**. Hence both: `calibrateDevice()` only considers presets up to `MAX_RECOMMENDED_OPTICAL_PRESET_ID`, and `OpticalQualityControls` lets the user change speed and code size **while streaming** (speed first — it is free; density restarts the stream, because a new QR version means a new `streamIdentity` and the receiver rebuilds its decoder). `useOpticalSender` retains the packed container for the session so re-slicing is instant. **Do not "optimize" by raising density, and do not move the controls off the streaming screen.**
  - **Never drive the sender's display loop with `setInterval`**, and always `dispose()` the `SkImage`. Both caused a progressive frame-rate collapse on real hardware; see the doc. That loop has exactly one implementation — `hooks/useQrFrameLoop.ts` — shared by `useOpticalSender` and the bench screen (`app/app/test/optical-bench.tsx`). Do not re-implement it in a new screen: the bench is the instrument used to validate these behaviours, so a second copy there would silently stop measuring what ships. `hooks/__tests__/useQrFrameLoop.test.ts` pins the self-scheduling, the all-or-nothing frame cache, and install/arm order-independence.
  - **The frame cache is all-or-nothing** (`planFrameCache`). Looping fewer distinct frames than the receiver needs is a silent, unrecoverable deadlock at ~98%, so a cache that cannot hold a safely loopable set is not built at all.
  - **An in-flight `unpack` is cancelled by generation token, not by clearing state.** `useOpticalReceiver` stays mounted when its modal closes, and unpacking (decompress + verify, plus decrypt when a passphrase is involved) runs long enough for the user to close or rescan mid-flight; `reset` bumps `generationRef` and every publish in `unpack` is gated on it, so a stale continuation drops its result instead of restoring a previously scanned payload over a newer one. Mirrors the sender's `generationRef`.
  - **Receiver progress tracks frames collected, never blocks solved** — LT peeling back-loads, so a blocks-based bar looks stalled and then teleports. And `onCodeScanned` must stay `useCallback(…, [])` writing only to refs: MLKit fires it 15–30×/s and a `setState` there starves the decode.
  - **`restoreDatabase(json)` takes one argument here.** The passphrase lives at the container layer and has already been removed; passing it would try to AES-decrypt plain JSON. Compression happens strictly _before_ encryption — the reverse makes the payload incompressible and the transfer ~9× longer.
  - **Share payloads are non-destructive and deliberately cannot masquerade as exports.** A share envelope must never gain a top-level `_exportVersion`; its rows stay under `records`, its container uses `payloadKind = 1` and the compatibility sentinel `exportVersion = 0xFFFF`, and the destructive receive branch must require `payloadKind === 0` (never “not a share,” because an unknown future kind is not a database). `utils/share/` stays pure for the same reason as `utils/optical/`: envelope parsing and import planning run in the Jest `node` project. Meal shares have no passphrase path, preview before saving, and import in one WatermelonDB writer without resetting or reloading the database.
  - **A share row may only carry the columns its table declares.** `ShareKindSpec.columns` is a per-table allowlist and `planShareImport`'s `sanitizeRow` reduces every incoming row to it (plus `id`) before anything reaches `assignRawColumns`, which assigns each key onto a WatermelonDB model instance. This is a security boundary, not tidiness: a share arrives over a camera from a phone we do not control, so without it a crafted row could set `collection` or shadow a method like `markAsDeleted` on the model being built. A denylist of control fields is not enough — it would have to anticipate every property worth shadowing. Unknown columns are dropped silently rather than rejected, because the two phones in a transfer can be months apart in app version and a column this build has never heard of is the expected shape of that. `utils/__tests__/shareKindColumns.test.ts` pins the allowlist against the real schema in both directions, so a new column cannot be silently unshareable and a removed one cannot linger.
  - **Receiving a share reuses what the phone already has; adding a table to a share means declaring its dedupe identity.** `ShareKindSpec.dedupe` names a strategy per table and `DEDUPE_RESOLVERS` (`database/share/importShareEnvelope.ts`) owns the query behind each one. A **food** matches on `external_id` → `barcode` → exact `name` + `brand` + macros, every branch also requiring the same `nutrition_basis` (per-100 g and per-serving rows carry the same numbers meaning different things). A **portion** matches on `name` + gram weight + `kind` + `scope`, and **not** on `source` — `forcedColumns` stamps every imported portion `custom`, so matching on it would make the second receive duplicate every `basic` portion the first receive localized. Portion lookup is **scoped by owner**: an unowned portion is matched against the receiver's unowned ones, a portion owned by a **reused** food against that existing food's portions, and one owned by a new food or by the meal is always created (there is no existing owner to borrow from — the meal is the share's root and is always new). Resolution walks `ShareKindSpec.tables` in order and a resolver may read the resolutions before it, which is how a portion learns its owning food was reused — so `foods` staying ahead of `food_portions` is a dependency for dedupe, not only for foreign keys. Pinned by `database/share/__tests__/importShareEnvelope.test.ts`, whose query mock evaluates clauses so owner scoping cannot silently regress into "any portion with that name".
  - **An optional field in a share envelope is absent, never `null`, and only two parse failures mean "the sender is newer".** WatermelonDB reads an unset optional column back as `null` (not `undefined`, whatever the model's `?: number` says) and `JSON.stringify` keeps a null while dropping an undefined, so a builder that copies a model getter straight into the envelope ships explicit nulls that `parseShareEnvelope` rejects. v2.11.0 did exactly that for the meal summary's `preparedWeightGrams`/`recipeServingsCount`/`servingGrams` and broke nearly every meal share. Builders run optional numbers through `optionalNumber()`; the parser reads `null` as absent via `readOptional()` (which deletes the key, so the returned envelope matches its declared type) so an updated phone can still receive from a v2.11.0 one. **Fixtures must use `null`, not `undefined`, for an unset optional column** — the original tests read the builder's in-memory object, where the distinction is invisible, so `database/services/__tests__/mealShare.test.ts` now pins builder → `JSON.stringify` → `parseShareEnvelope` end to end. Separately, `MusclogShareError`'s codes split into "this build is behind" (`unsupported-envelope`, `unsupported-kind`) and "the payload is broken" (`malformed`, `not-a-share`, `too-large`); `OpticalReceiveModal` shows `receive.tooNew` only for the first pair and `share.unreadable` otherwise. Rendering `tooNew` for every failure is what made the null bug present as "update this phone" on two phones running the identical build.
  - **The food barcode scanners probe for optical frames and must swallow the first one.** `SmartCameraModal` (barcode mode) and `BarcodeCameraModal` both scan `qr`, so a sending phone feeds fountain frames into `useBarcodeScanner`, which used to look each one up as a product barcode and dead-end in "food not found". `utils/optical/frameProbe.ts` (`OpticalFrameProbe`) catches them: it base44-decodes and reads only the header — never a payload, and deliberately **not** via `OpticalReceiver`, which would allocate an `LTDecoder` and half-receive a transfer the scanner has no intention of finishing. `observe()` returns `'ignored' | 'frame' | 'detected'`, and **both `'frame'` and `'detected'` must suppress the lookup** — including the very first frame, which arrives below the prompt threshold; letting it through opens the food-not-found sheet, tears the camera down, and the second frame never arrives. `'detected'` fires at most once per stream (MLKit calls back 15–30×/s, so re-announcing thrashes React state), needs two frames sharing a `streamIdentity`, and a dismissal is remembered per identity. The offer opens `OpticalReceiveModal` with `accept="share"`: the probe cannot tell a meal from a database (`payloadKind` only exists after reassembly), and a full restore wipes the phone — not something to offer from a food camera. `useOpticalStreamOffer` returns the notice and the modal as separate elements because they go in `SmartCameraShell`'s `noticeSlot` and its `children` respectively; the modal must never be a sibling of the camera modal (`docs/modals-problem-on-ios.md`). `components/optical/OpticalCameraHintCard.tsx` is shared with the receive screen's no-signal hint so the two cannot drift, and takes positioning from the caller — floated over the feed on the receive screen, in flow above the controls in the shell, where an absolute card would sit on the shutter.
- **Notes (scratchpad)**: Free-text notes (`notes` table, optional `title` + required `body`) the user jots down while cooking without committing to a nutrition log. Screen is `app/app/notes.tsx`; data goes through `NoteService` and the `useNotes` hook. Three invariants worth keeping:
  - **Plaintext on purpose.** Unlike `saved_for_later_groups.note` (encrypted via `encryptOptionalString`), `notes.title`/`notes.body` are stored unencrypted so the paged list query stays SQL-side (`WHERE deleted_at IS NULL ORDER BY created_at DESC LIMIT n`, backed by the `created_at` index). Adding encryption means rewriting the list query **and** adding decrypt/re-encrypt branches to `database/exportDbCore.ts` + `database/importDb.ts`. `created_at` is a plain record-creation instant — deliberately no `date`/`timezone` day-key pair, since a note is not bucketed by calendar day.
  - **`useNotes` must use `observeWithColumns`, not `observe`.** The query's `sortBy`/`take` clauses force WatermelonDB's _reloading_ observer, which dedupes emissions by record identity; an in-place `.update()` reuses the same `Model` instance, so `observe()` would never emit and an edited note would silently stay stale on screen. Guarded by `hooks/__tests__/useNotes.test.ts`. Pagination grows a single `Q.take(limit + 1)` window (the `+1` is the `hasMore` probe) — do **not** copy `hooks/useExerciseGoals.ts`'s sentinel-observe + `loadInitial()` pattern, which resets the user's "Load more" progress on every edit.
  - **The list query has exactly one definition: `NoteService.notesQuery(limit)`.** It returns the WatermelonDB `Query` (not fetched rows) precisely so `useNotes` can `observeWithColumns` it while the service still owns the query shape. Do not re-inline `Q.where('deleted_at', …)` / `Q.sortBy('created_at', …)` in the hook or a screen — a service copy and a screen copy previously drifted into two different pagination models (offset `Q.skip` vs the growing window). `LATEST_NOTE_COUNT` and `NOTES_INITIAL_LIMIT` (`hooks/useNotes.ts`) are likewise derived, not duplicated: the screen slices on `LATEST_NOTE_COUNT`, and the page size is `LATEST_NOTE_COUNT + NOTES_BATCH_SIZE`.
  - **The "Track this" menu item is gated on `isAiConfigured`** and spread out of `noteMenuItems` when no provider is set up — see the AI-affordance gating rule under _AI & LLM Integration_.
  - **`useCoach().openCoach` takes an optional options object** (`{ composerText?, intention?: ChatIntention }`) so a note can open the coach with `TRACK_MEAL` armed and the note text prefilled. **Never pass `openCoach` directly as an `onPress` handler** — React Native supplies a `GestureResponderEvent` as the first argument, which would be read as `options`. Wrap it (`() => openCoach()`), as `components/MasterLayout.tsx` does for `NavigationMenu`. The `intention` is forwarded to `useChatMessages` as `initialIntention` (see the coach-intentions rule — that hook is the only writer of `CHAT_INTENTION_KEY`). The prefill shares one render path with the failed-send restore — `SeededComposer`'s `seedText`, which must reach **both** `renderComposer` and `renderSend`, since the latter derives the Send button's enabled state from it.
- **Coach intentions are one registry, and `useChatMessages` is their only persister**: `CHAT_INTENTIONS` (`constants/chat.ts`) is the ordered canonical list of armable intentions — the five that park a pending prompt and run on the next send — and `ChatIntention` is **derived** from it, so the union and the enumeration cannot drift. The chip row maps `CHAT_INTENTIONS` directly; there is deliberately no second order array to go stale. Each intention is configured exactly once in `components/coach/coachIntentions.ts` (`idPrefix`, `promptKey`, `icon`/`iconColor`, chip `labelKey`, banner `bannerLabelKey`), and the `Record<ChatIntention, …>` typing makes the compiler demand the config, so callers index it with no fallback branch — that is why the armed banner reads `bannerLabelKey` instead of a `switch`.
  - **Only `useChatMessages` writes `CHAT_INTENTION_KEY`**, through `setIntention(intention)` / `clearIntention()`, and it reads the key once in its load effect. An `initialIntention` argument (from `openCoach({ intention })`) is seeded **inside that same effect**, so there is exactly one writer per mount. Do not add a second writer — an effect in `CoachModal` doing its own `AsyncStorage.setItem` races the hook's read and can silently lose the arm.
  - `CoachModal` owns only the chat-visible half: `parkIntentionPrompt` posts the parked message, `armIntention` = `setIntention` + park, `disarmIntention` = `clearIntention` + unpark, `toggleIntention` picks between them for the chips. **Do not hand-roll another arm/toggle handler** — five copy-pasted ones (~85 lines) is what this replaced. Arm and disarm are separate primitives on purpose: an externally requested intention needs a plain arm, and routing it through a toggling handler would clear it instead.
  - Note `promptKey`/`labelKey`/`bannerLabelKey` are held in a table rather than inside literal `t('…')` calls, which `scripts/check-translations.js` only sees because `*Key:` fields and `components/**/*.ts` are both in its scan config — keep them there when adding similar registries.
- **Mood Tracking**: Daily mood prompt (configurable via `SHOW_DAILY_MOOD_PROMPT_SETTING_TYPE`). Mood is correlated with calories, workout volume, and macros in the progress charts.
- **Home Screen Widgets**: Android widgets live in `widgets/` (`NutritionWidget`, `SmartCameraWidget`). Widget data is refreshed via helpers in `widget-update-helpers.ts`.
- **Home summary card choice**: The top of the home screen shows either the `DailySummaryCard` or the `WeeklyStreakCard`, chosen via `HOME_SUMMARY_CARD_SETTING_TYPE` (`'daily_summary' | 'weekly_streak'`) in the Interface/Visual settings. The streak card's current streak counts consecutive calendar days with a logged food ending **yesterday** (the current day is excluded), computed timezone-aware via `NutritionService.getMacroLoggingStreak()`. The best streak is the longest current streak ever observed, persisted in the `MACRO_STREAK_STATE` AsyncStorage key and only ever grown (never recomputed historically). `utils/macroStreak.ts` (`getMacroStreak`, surfaced by the `useMacroStreak` hook) recomputes from the DB at most once per local day and caches both values for the rest of the day. `WeeklyStreakCard` gets workout progress from `useWeeklyWorkoutProgress`: completed workouts are counted by `completed_at` over the rolling 7 local calendar days ending today, and goal dots are shown only when the user has an active consistency exercise goal.
- **Food Search Source**: Configurable via `FOOD_SEARCH_SOURCE_SETTING_TYPE`. Options include Open Food Facts, USDA, Musclog barcode DB, and local-only.
- **OCR Before AI**: When enabled (`USE_OCR_BEFORE_AI_SETTING_TYPE`), images are processed locally with OCR before being sent to the LLM, reducing data sent to external services.
- **Custom AI Prompts**: Users can create multiple context-specific system prompts (general, nutrition, exercise) and toggle which are active. Stored in the `ai_custom_prompts` table; appended in `utils/prompts.ts`.
- **iOS Health**: HealthKit integration via `@kingstinct/react-native-healthkit` (in addition to Health Connect on Android).
